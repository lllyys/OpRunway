# 分析标准

八个维度适用于当前与新增社区任务 skills。按职责和调用关系分组，
现有技术栈名称仅作为被分析对象，不作为固定分类。
每个维度说明责任方、规则依据、数据来源、产物及检查方式。

## 一、定位与职责边界

说明 skill 解决的问题、触发条件、支持范围和上下游。
区分用例生成、开发者自测、验收执行、证据复核、最终结论等职责。
维护者关注责任是否重叠或缺失；使用者关注选哪个入口及需要提供什么。

## 二、每个 skill 的输入与输出

逐个 skill 建立输入表和输出表，关联的一组 skills 也分别列出。
仅给组级总表会掩盖各入口的责任，不能替代逐项说明。

| 表 | 必须解释的字段 |
| --- | --- |
| 输入 | 名称、内容与格式、来源、必选或条件必选、默认推断、约束、实际读取方 |
| 输出 | 路径或名称、内容与作用、生成方、后续消费方、完成条件、失败时保留内容 |

区分外部输入、脚本派生值、用户选择和环境探测结果。
输出分为中间产物、交付任务包、执行证据和最终报告，说明生命周期及复用条件。
对重建、覆盖和版本绑定只展开会影响参考一致性或证据有效性的部分。

## 三、任务包的组成与文件职责

按真实包结构列出主要文件及目录，采用以下字段说明：

| 字段 | 说明 |
| --- | --- |
| 文件或目录 | 实际名称、命名模式或条件性成员 |
| 内容与作用 | 用例描述、输入数据、参考输出、参考耗时、检查程序或身份清单等 |
| 生成方与读取方 | 谁写入，谁在哪一环节读取；附调用位置 |
| 数据状态 | 冻结保存、现场生成、脚本副本、权威实现或仅供说明 |
| 缺失影响 | 阻塞、降级、跳过、证据不足或不影响结论，以实际规则为准 |

说明开发者如何部署和使用任务包，accept 是否直接消费同一份产物。
特别核对包内检查脚本是执行入口、生成模板、自测副本还是验收权威实现。
任务自带测试件、纯脚本包、动态参考等分支按实际材料说明，保留各自数据来源。

## 四、用例设计与覆盖

追踪任务书要求到测试场景、用例及结果集合的映射。
说明正常、边界、异常、不同 dtype 和规模的构造方式，以及任务自带测试件的覆盖检查。
解释组合生成、抽样、筛选、去重和性能子集如何改变覆盖范围。
区分脚本强制检查、统计提示和依赖执行者判断的要求，避免把统计退出成功写成覆盖充分。
说明缺场景、生成失败和无法匹配的用例如何进入最终报告及结论。

## 五、精度判断标准

按接口或 dtype 分支说明精度方法，以检查实现为证据。
先区分数值精度、确定性、接口状态和输出结构四类检查，再解释各自条件。

- 比较对象：被测输出与 golden、参考实现、原输入矩阵关系，或其他明确对象。
- 方法与公式：逐位一致、逐元素容差、误差统计、残差、正交性或任务特定性质。
- 参考来源：精度、执行设备、输入构造、随机种子、冻结时机及验收时的消费方式。
- 通过条件：阈值与单位、来源、特殊值规则、多输出与批量聚合、空输入处理。
- 证据边界：参考不可用、被测执行失败或检查异常时的实际状态与后续处理。

对逐元素容差写清绝对误差与相对误差的组合规则。
对误差统计写清计算轴、归约与容许超限比例。
对残差写清数学关系、归一化方法、计算精度及参考阈值的来源。
区分参考生成时的逐位稳定性检查与被测输出的数值精度条件。
多个输出或 batch 的聚合方式需要明确，单个代表内容通过不能推导未检查部分通过。

## 六、性能采集与判断

说明从被测调用到耗时数据，再到参考匹配与结论的完整过程：

- 采集工具、实际入口及计时范围：kernel、完整接口、Host 或 Device。
- 调用内容：输入准备、数据搬运、因子准备等是否计时，如何隔离目标调用。
- 采样协议：预热、重复次数、kernel launch 数量、重放、计时单位与统计方法。
- 多 kernel 处理：求和或平均的层次，一次接口调用如何还原为单次耗时。
- 参考来源及匹配：设备、shape、dtype、布局、版本和计时范围是否可比。
- 判断公式与来源：倍率方向、阈值、逐例与总体聚合，缺参考或采集失败的处理。

区分测量成功、性能达标和总体验收通过。
工具退出成功不自动证明采集完整；核对漏采、截断、错误 kernel 及失败执行的处理。
对计时范围不一致的情况，分别说明现有脚本如何判断，以及分析发现的可比性限制。
具体数值从被分析版本读取，不把某组 skill 的默认阈值推广到其他对象。

## 七、任务包与开发者工程的实际调用链

按数据传递追踪下面的角色，使用实际文件、入口或接口名绘图：

任务用例 → 输入构造 → 测试驱动 → 适配层 → 开发者算子接口 → 输出与状态 → 检查程序。

每组至少一张图展示核心调用关系，标明检查程序的执行位置与结果比较方。
角色可由同一程序承担，按实际实现合并节点；缺失的环节明确标注。
说明构建由谁发起，任务包如何部署到工程，执行驱动实际读取哪份用例。
追踪参数、输入与输出的转换及归属，指出参考计算与被测计算分别在哪个位置执行。
核对源码、构建产物、加载库和实际接口的身份检查；将约定支持与本次交付验证分开。
源码或执行证据不足时，保留调用约定与未验证说明，不绘制成已接通的链路。

## 八、casegen—开发者—accept 的闭环

用一张闭环图连接任务要求、casegen、任务包、开发者工程、自测、accept、报告和修复。
单独说明以下关系，缺少的角色按现状标记：

- 交付：任务包如何到达开发者和验收方，哪些文件与规则共用，哪些重新生成。
- 一致性：两侧的用例、输入、参考和检查规则如何对应，版本变化如何影响旧证据。
- 归因：环境、任务包、调用适配、算子执行与数值失败分别返回哪一责任方。
- 修复：重新构建、重新生成或重新验收的触发条件；新旧证据如何区分。
- 结论：期望集合是否完整，失败与缺证据如何汇总，自测通过能否支持正式结论。

图中保留正常交付、结果回传与失败返回路径，避免展开每条命令。
报告分别列出现行机制、已验证范围、未验证项及维护建议。
分析完成的检查依据是八个维度均有证据或明确缺口，不是把闭环画成全部成功。
