**日期**：2026-08-06
**代码基线**：`.claude/worktrees/oprunway19`（`9209756`）
**性质**：**只跑不改**。本次没有修改任何代码，只做一次可复现的实测。
**为什么要做**：aclnnRoll 试跑时 `acc-spec-extractor` 写下一句未经验证的论断——
「`aclIntArray` 属性槽 `aclnn_runtime` 和 `cpp_extension` 都不支持」，orchestrator 采信后把
`runner_form` 从 `cpp_extension` 改成 `cpp`，整轮从此不可能产出验收裁决。这份记录验证那句话。

## 结论（先给答案）

**三选一里是 (b)：`cpp_extension` codegen 不 raise，它生成标量 `int64_t` 去对接 `aclIntArray*`。**

那句论断因此是**半对半错，而且错的那一半比论断本身更糟**：

| 通路 | 论断说 | 实测 | 判定 |
|---|---|---|---|
| `aclnn_py`（`aclnn_runtime/aclnn_runner.py`） | 不支持 | 解析 `const aclIntArray* shifts` 当场 `AclnnRunnerError`，**真 fail-closed** | 论断**属实** |
| `cpp_extension`（`cpp_extension_codegen.py`） | 不支持 | **不 fail-closed**：生成 `int64_t shifts` + Torch schema `int shifts`，生成物里**没有** `aclCreateIntArray`、没有任何数组类型 | 论断**错**，实际是**静默错型** |

⚠ 但**流水线层面**结论要说全：`cpp_extension` 也走 CP-C0 的 `preflight_aclnn.py`，
那里有**两道**门（签名解析 + slot ctype 对账）会把 Roll 拦在 CP-C0。
所以「当前 `cpp_extension` 跑不了 aclIntArray 算子」这个**结果**成立，
但**原因和论断说的完全不是一回事**——不是 codegen 拒绝，是隔壁的门替它挡的。
**这个区别直接决定步骤 7 的改法与落地顺序**（见文末「对步骤 7 / 10 的影响」）。

### 生成成功，退出码 0

```
{

  "runner_form": "cpp_extension",

```

### 生成物全文（`csrc/oprunway_extension.cpp`）

```cpp
// Generated by OpRunway. Do not hand-edit.
#include <torch/library.h>
#include <torch/extension.h>
#include "npu_cpp_extension.h"

std::vector<at::Tensor> invoke_v0(const at::Tensor& x, int64_t shifts, int64_t dims, const at::Tensor& out)
{
    const c10::OptionalDeviceGuard device_guard(device_of(x));
    EXEC_NPU_CMD_EXT(aclnnRoll, x, shifts, dims, out);
    return {out};
}

TORCH_LIBRARY(oprunway_f71a3dd73a6c11c7, m)
{
    m.def("invoke_v0(Tensor x, int shifts, int dims, Tensor out) -> Tensor[]");
}

TORCH_LIBRARY_IMPL(oprunway_f71a3dd73a6c11c7, PrivateUse1, m)
{
    m.impl("invoke_v0", &invoke_v0);
}
```

**这就是判据本身**：`int64_t shifts, int64_t dims` 是**标量**，签名要的是 `const aclIntArray*`。
Torch schema 写的是 `int shifts`（标量 int），**不是** `int[] shifts`。

### 判据 1 · 生成物里没有任何数组机制

```
'aclCreateIntArray' in 生成物: False
'aclDestroyIntArray' in 生成物: False
'aclIntArray'       in 生成物: False
'at::IntArrayRef'   in 生成物: False
'std::vector<int64_t>' in 生成物: False
'int[]'             in 生成物: False
```

(b) 与 (c) 的分界就在这里：**光看「生成成功」分不出来，必须看生成物**。结论是 (b)。

### 判据 2 · A 节：spec 里**根本没有**能表达数组属性的写法

把 `shifts` 的 `dtype` 换成各种数组写法，全部被 `_attr_type`（`cpp_extension_codegen.py:71`）
按 `_ATTR_CPP_TYPES`（`:32`）拒掉：

```
dtype=['int_array']   -> 拒: attr 'shifts' dtype 须为单值 ['bool','float32','float64','int32','int64']
dtype=['int64_array'] -> 拒: 同上
dtype=['aclIntArray'] -> 拒: 同上
dtype=['list[int]']   -> 拒: 同上
dtype=['int64[]']     -> 拒: 同上
```

**所以 spec 作者没有第二个选项**：要么写 `int64`（→ 静默生成标量），要么整份 spec 过不了 codegen。
这不是「作者填错了」，是**受控词表里压根没有数组类型**。

### 判据 3 · B 节：codegen 从头到尾**没看过属性的取值**

`_attr_type` 只读 `param["dtype"]`，`default` / `attr_matrix` 一眼没看：

```
default=[1]     -> cpp_type='int64_t' schema_type='int'（未拒）
default=[1, 2]  -> cpp_type='int64_t' schema_type='int'（未拒）
default=1       -> cpp_type='int64_t' schema_type='int'（未拒）
default=None    -> cpp_type='int64_t' schema_type='int'（未拒）
```

⚠ 这一条特别值钱：**spec schema 明文允许 `list[int]` 属性**——
`spec_schema_template.jsonc:251-254` 写着「`"default": <标量 或 list[int]>`……
`output_size` / `kernel_size` 这类既是数组、又决定输出形状的属性用数组」。
也就是说「这是个数组」这个信号**确实在 spec 里**，只是 codegen 把它整个丢掉了。

### 判据 4 · list 取值本身合法，但「它是数组」这件事没人往下传

⚠ **先纠正一个容易写过头的说法**（本节初稿写成「完全不看值 / 穿过全部确定性校验」，**不准确**，
已按 2026-08-06 审修门 Medium#2 改正）：**取值层是有闸的**——
`gen_cases._check_attr_value`（`:1718`）明确放行 `list[int]`、并拒空数组 / bool / 浮点 / 嵌套；
`attr_matrix` 路径在 `:1778` 调它，`default` 列表在 `:1796-1798` 也补调。
`[1]` 是**合法输入**，它通过是对的，不是漏检。

真正的缺陷在**下一跳**：**「这个 attr 是数组」这个已知事实，到 ctype 与 C++ 类型选择那一层就断了**。

```
gen_cases._check_attr_value([1])        -> 通过（list[int] 合法，正确行为）
gen_cases._attr_ctype({dtype:[int64]})  -> 'int64'   # 只读 dtype token，数组身份在这里丢失
gen_cases._build_aclnn_call             -> {"role":"attr","name":"shifts","ctype":"int64","value":[1]}
                                           # ⚠ ctype 说标量，value 是数组，两者自相矛盾且无人对账
cpp_extension_adapter.build_invocation_plan -> 原样收下，写进 invocation plan
cpp_extension_driver.materialize_invocation:251 -> args.append(slot["value"])   # 直接塞进 torch.ops 调用
```

`gen_cases._attr_ctype`（`:2504`）的 docstring 明确说它防的是「attr 的 C 标量宽度拼错」——
它**假定了 attr 一定是标量**，所以 `ctype='int64'` 与 `value=[1]` 这组**内部矛盾的 slot**
在 Python 侧一路无人置疑。**缺的不是取值校验，是 ctype ↔ 取值形态的一致性校验。**

## `aclnn_py` 那半句：属实

`aclnn_runtime/aclnn_runner.py:257-259`，`"*" in tok` 那道 fail-closed 确实拦住：

```
'const aclTensor* x'       -> {'name':'x','role':'in','ctype':'tensor','const':True}
'const aclIntArray* shifts'-> AclnnRunnerError: aclnn 形参 'const aclIntArray* shifts' 是指针/数组形态
                              （非 aclTensor/aclScalar）——域外接口能力，fail-closed
'const aclIntArray* dims'  -> AclnnRunnerError: 同上
'aclTensor* out'           -> {'name':'out','role':'out','ctype':'tensor','const':False}
```

整份 `aclnnRollGetWorkspaceSize` 声明过 `parse_aclnn_signature` → 同一条 `AclnnRunnerError`。
marshal 侧 `_ATTR_CTYPES`（`:404`）受控词表也只有 `['bool','float32','float64','int64']`，
**全是值传递的标量**，没有句柄类型。所以 `aclnn_py` 是**真** fail-closed，不是假门。

## 这份实测对步骤 7 / 10 的影响

### 步骤 7 必须改**四层**，其中一个中间态是真 fail-open

计划书步骤 7 表里 `cpp_extension` 那一行标着「按步骤 3 的实测结果定」。**答案是：必须改。**

`cpp_extension` 目前之所以「跑不了 aclIntArray」，靠的**不是 codegen 自己的门**，而是 CP-C0
`preflight_aclnn.py`——它对 `runner_form == "cpp_extension"` **也生效**
（`:155-158` 只让**精确的 `"cpp"`** 早退，`:159-166` 把词表外的形态一律 BLOCKED），
并在 `:218` 调 `parse_aclnn_signature(text)`，撞的正是 `aclnn_runner.py:257` 那条 fail-closed。

⚠ **但 preflight 里是两道门串着，不是一道**（本节初稿写成「唯一挡板」，**错**，
已按 2026-08-06 审修门 High#1 改正）：

| # | 门 | 位置 |
|---|---|---|
| ① | 签名解析拒绝 `aclIntArray*` | `aclnn_runner._classify_param:257` |
| ② | slot ctype ↔ 签名 ctype 逐项对账 | `preflight_aclnn:239-242` 组 slot（ctype 由 `gen_cases._attr_ctype` 给）→ `aclnn_runner._validate_slots_against_signature:1272-1275` |

**所以「只改 `_classify_param` 立刻 fail-open」这个说法不成立**：那一改之后签名侧变成
`int_array`、slot 侧 `_attr_ctype` 仍给 `int64`，门 ② 当场 `int64 != int_array` fail-closed。
**只改解析器仍然是干净的 BLOCKED。**

🔴 **真正危险的是这个中间态**——改了 ①②**两侧**却没动 codegen：

> 一旦 `_classify_param` 返回 `int_array` **且** `gen_cases._attr_ctype` 也学会返回 `int_array`，
> 门 ① 门 ② **同时**放行 → preflight 判 `READY_WAIT_NPU_TRUST_GATE`，
> 而 `cpp_extension_codegen` **一行没改，照旧生成 `int64_t`**。
> 这时既没有门拦、生成物又是错型——**这才是 fail-open**。

`_attr_ctype` 与 codegen 类型选择**必须同批落地**；先改 `_attr_ctype`、把 codegen 留到下一批，
就是亲手制造上面那个窗口。

四层清单：

| 层 | 位置 | 要做什么 |
|---|---|---|
| 签名解析（两通路共用） | `aclnn_runtime/aclnn_runner.py:257` | 在 `"*" in tok` 之前认 `aclIntArray` → `{"role":"attr","ctype":"int_array"}` |
| `aclnn_py` marshal | 同文件 `_ATTR_CTYPES:404` 附近 | `int_array` **不走** `_ATTR_CTYPES`（非值传递）：`aclCreateIntArray` / `aclDestroyIntArray`，生命周期覆盖两段式全程 |
| slot ctype | `gen_cases._attr_ctype:2504` / `_build_aclnn_call:2550` | ctype 词表加 `int_array`，并补 **ctype ↔ 取值形态一致性**校验（现在 `ctype='int64'` + `value=[1]` 这种自相矛盾的 slot 无人拦，见判据 4）。⚠ **与下一行同批** |
| **`cpp_extension` codegen** | `cpp_extension_codegen.py:32/39` 的 `_ATTR_CPP_TYPES` / `_ATTR_SCHEMA_TYPES`、`:71` 的 `_attr_type`、`:152` 的 `_cpp_arg`、`:163` 的 `_schema_arg` | 加数组类型分支：C++ 侧收 `at::IntArrayRef`（或等价），Torch schema 写 `int[]`，并让 `EXEC_NPU_CMD_EXT` 拿到 `aclIntArray*`。⚠ **与上一行同批** |

**门 ② 是改造期间的安全网，别顺手放宽它**——它是唯一会在 `_attr_ctype` 与签名不同步时报警的东西。

🟡 **顺带查出一处仓规散文漂移（不在步骤 3 范围内，只记账、本轮不改）**：

| 出处 | 说法 |
|---|---|
| `plugin/acc-common/preflight_aclnn.py:155-166`（**代码，权威**） | 只有精确的 `"cpp"` 早退；`cpp_extension` 与 `aclnn_py` **都要跑** |
| `plugin/skills/acceptance-workflow/SKILL.md:209` | 「`runner_form ∈ {"aclnn_py","cpp_extension"}`，primary 亲自」——与代码一致 ✅ |
| `plugin/AGENTS.md:134` | 「`preflight_aclnn.py`（**仅 `aclnn_py` 形态**）」——**与代码不符** ❌ |

⚠ **这只是散文漂移，不要写成「已经存在一条会跳过预检的执行分支」**（本节初稿如此断言，
**属推测**，已按 2026-08-06 审修门 Medium#3 改正）：同一份 `plugin/AGENTS.md` 在 `:202` 又强制

### 步骤 10 不会因为这一条堵死 Roll，但**也不会自动救活它**

步骤 10「只保留 `cpp_extension`」之后，Roll **仍然会停在 CP-C0**（preflight 的门 ①），
**不是**停在 codegen。所以：

- 步骤 10 单独做完 → Roll 依旧 BLOCKED，只是理由栏换个位置；
