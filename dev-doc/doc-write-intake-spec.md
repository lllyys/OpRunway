## 1. 术语与引用索引

本节集中给出全文用到的名词；未在此处定义的骨架 key（形如 `3.2.random_strategy`）
一律指 `plugin/skill/repo-task-doc-write/references/taskdoc-elements.json`（下称**骨架**）
`elements` 里的同名要素。

**外部定义的引用**：

| 名词 | 定义处 |
| --- | --- |
| T1–T5 五阶段 | skill `SKILL.md`「五个阶段」表 |
| L0–L4 门禁层、L3 答复记录检查 | `scripts/_checks.py` 的 `LAYERS` 与 `check_human_reply_recorded` |
| `decision_owner`、`agent_may_propose`、`required`、`condition` | 骨架 `elements` 字段 |
| provided / inferred 分类 | `dev-doc/doc-write-element-classification.md` |
| 红线 A–D | skill `CLAUDE.md`「四条红线」表 |
| golden | `references/golden-task-doc.md`（过全门禁的黄金任务书） |
| golden decisions | `tests/fixtures/decisions_golden.json` |
| defect fixtures | `tests/fixtures/defects/` |
| defect-map | `plugin/docs/development/taskdoc-source/defect-map.md` |

**本文定义**：

- **intake 表**：T1 一次性收人输入的表格模板。**必填面** = provided 13 条 + 随机算子
  前提；**可选面** = 任何 inferred 项。
- **pending / 待问**：调度器判定尚需人有效拍板的要素集合。**done = pending 为空**，
  无其他隐藏条件。
- **候选总审**：T3 把全部 pending 连同**实际候选内容**一次呈现、人一轮回复。
- **有效拍板**：明确的准、改或给值。「还不知道」「暂不决定」类答复不是有效拍板，
  该项保持待问；原话可保存作过程记录，但不使项完成。
- **原话凭据 vs 确认内容**：`human_reply` 存人的原话，是**凭据**；被确认的**内容**
  （如最终签名文本）另有可机读载体（载体由 plan 定）。机械比对只吃确认内容，
  不解析原话。
- **条件三态**：条件项的调度侧判定——适用 / 不适用 / 无法判断。
- **快速路径**：前提一次有效、候选一轮全部接受、其间无上游变更、落稿后无人工
  改动引入新条件——此时恰 2 次输入。不满足假设时轮数自然增加，不算违约。
- **编号体系**：FR = 功能需求，INV = 不变量，A/B = 验收判据的 A、B 两阶段，
  I = 不变量核对项。

## 2. 功能需求

**FR1 intake 模板**：新增 `assets/intake-template.md`。必填面逐 key 列出（均为骨架
key）：`1.background`、`1.language`、`1.repo`、`2.2.project_mode`、`2.1.baseline`、
`3.1.hardware`、`3.1.cann_version`、`3.1.third_party`、`3.3.baseline_env`、
`3.3.criterion`、`3.4.memory`、`5.pr_target`，外加随机算子前提（非骨架要素）。
`3.3.case_table` 归可选面（Mr.0 裁定 2026-09-17：任务书模板 §3.3 明写「也可以在
测试用例文件中提供」，intake 时点常无标杆数据；未填则落批次追问，骨架必填性不变）。事实类留空白格供贴原始材料，决定类给取值选项；可选面允许预填
任何 inferred 项。每行的填写判据引用任务书模板原文，不另造第二套说法。

**FR2 映射与有效拍板**：intake 每个非空格的原话都逐字保存——构成有效拍板的记入
`human_reply`，不构成的（「暂不决定」类）记入过程记录字段（字段名由 plan 定），
两者均标出处 intake；空格跳过。只有 `human_reply` 使该项完成。部分批准
（「除 X 外都同意」）：X 保持待问，其余按本轮展示的内容记录。

**FR3 批次全覆盖**：骨架 `question_batches` 收编全部 41 条 human 要素
（39 always + 2 conditional），每批 1–6 项；`template`/`agent` 归属项不入批。
ratchet 测试锁「每条 human 要素恰属一个批，非 human 不入批」。

**FR4 全量总审**：`next_questions.py` 加 `--all`：一次输出全部 pending 批次的完整
detail（名称、section、可否给候选、failure），无遗漏、无重复；`--all --json` 可用；
现有单批模式与 `--json` 字段保留。总审呈现给人的除 detail 外必须含每项的
**实际候选内容**；整体同意只覆盖本轮明确展示的内容。

**FR5 条件求值（调度侧；门禁侧实现不变）**

求值时机与输入：总审呈现前，调度器对「已确认内容 + 本轮全部候选内容」（即将
落稿的文本面）求值条件，条件项与其它项**同轮**呈现——快速路径由此闭合。
T4 之后只有人工改动文档引入新信号时才出现新条件，此时回 T3 补答（属缺口路径）。

- **随机性——三个事实分开**：①信号命中（机械事实：对将落稿的文本扫信号词，
  与门禁同一份词表与判据）；②算子是否随机（人拍板的事实）；③`3.2.random_strategy`
  已有效拍板（记录事实）。规则：信号命中 → 该项进待问；其有效拍板 =
  四策略之一（随机算子）**或**「不涉及 + 理由」（非随机算子）——后者落稿进 §3.2
  后正是门禁 `check_random_strategy_when_signaled` 接受的形态，调度与门禁由此
  收敛，无需改文档消信号词。golden 的现有形态（非随机 + 正态分布描述 +
  不涉及说明）是合法路径，重复调度不得再追问。人工裁定关闭的是待问项，
  不改变门禁的机械判定。
- **签名一致性**：比较输入 = 两侧各**一份**经人确认的最终文本（基线接口内容、
  签名内容；载体由 plan 定，`human_reply` 原话不做解析源，不要求人重复抄写）。
  判定优先级唯一：①任一侧缺失、解析不完整、或存在多份未定稿文本 → **无法判断**；
  ②两侧完整解析 → 完整对应成立 ⇒ 一致；存在任何差异（数量、命名、顺序、
  部分重合）⇒ 不一致。完整解析下不存在「部分重合 → 无法判断」分支。
- **三态闭合**：「适用」与「无法判断」的条件项进待问；对该项的有效拍板（含
  「不适用 + 理由」的人工裁定）关闭它。**输入不变且已有效拍板的项不得重复追问；
  缺信息的项保持待问并如实呈现**——追问由缺口驱动，不由调度器制造循环。

**FR6 收尾兜底**：pending 非空而无可呈现批次时（FR3 后理论不可达，仍兜底），
文本模式输出剩余项清单与下一步指引，退出码 0，不抛异常。

**FR7 上游失效与存量记录**

- 失效规则：**已确认的上游内容发生变化，所有受其影响的下游确认失效**，重新生成
  候选、重新确认；答复原话相同而候选内容已变，同样失效。代表场景：工程模式变 →
  签名、自验工具失效；基线变 → 签名与 §2.4 各列失效；dtype 面变 → 阈值表失效；
  值域变 → 生成规则失效。反例：无依赖的项不失效（背景变更不动阈值表）。
- 失效的可观察性：失效记录必须回到**未答**状态，且对任何版本的调度器（含回滚后
  只认「非空 `human_reply`」的旧版）都表现为未答——载体由 plan 定，此行为是硬约束。
- 存量记录兼容：只有原话、无确认内容的旧记录仍视为已答（不重开旧流程）；被用作
  条件比较输入时因缺确认内容 → 该条件「无法判断」。
- 有效拍板、确认内容、失效可观察性三项契约属**阶段 A** 交付（A4 依赖它们），
  阶段 A 不依赖阶段 B。

**FR8 SKILL.md 与簿记**：五阶段表 T1/T3 改写、命令区补 `--all`、失效规则明文化。
`manual-checklist.md` 重渲核对——批次不参与该视图，预期输出逐字节不变，作为
无漂移证据。defect-map 补 D1/D2/D3；落地后 `dev-doc/oprunway-changes-brief.md`
记摘要。

## 3. 不变量

- INV1 拍板面零缩减：权限与记录要求（`decision_owner`、`agent_may_propose`、
  L3 要求）与现状完全一致。旧流程漏问的项开始被问是缺陷修复，不算拍板面变化。
- INV2 红线 B/C/D 原样。
- INV3 `_checks.py` 零改动（diff 为空）。
- INV4 判据、必填性、批次这三类**数据**只能落骨架，不得写死进脚本（这是
  「骨架是唯一可编辑对象」的准确范围；按本 spec 修改脚本行为不受此条限制）。
- INV5 载入预算，计量集合明确为：`SKILL.md` 自身 ≤ 12 KB；每个阶段的最小载入 =
  `SKILL.md` + 该阶段指令链出的全部 `references/*.md` 字节和 ≤ 32 KB。
  `assets/intake-template.md` 按需读取不入常驻链，单独记录实测字节数。
  lint 不计 assets，故以 `wc -c` 实测核对，不以 lint 通过替代。
- INV6 无 intake、无 `--all` 时批次循环可用，CLI 与 `--json` 既有字段语义不变。
- INV7 `_signature.py` 为门禁共享件：若 plan 决定改它，门禁侧行为必须逐字节不变
  （golden 与全部 defect fixtures 的门禁输出回归）；否则调度侧解析放独立模块。

## 4. 验收判据（两阶段，先 A 后 B，各自独立通过）

**阶段 A · 调度正确性（D1/D2/D3 + 条件 + 记录契约）**

- A1 批次覆盖：ratchet 测试绿——41 条 human 恰各属一批，非 human 不入批。
- A2 D3：批内全答、批外欠答（旧骨架 fixture 构造）不崩、退出码 0、指引可推进。
- A3 条件·随机：无 doc + 前提「随机」→ `3.2.random_strategy` 入待问；golden 场景
  （非随机、正文含分布描述、§3.2 写「不涉及+理由」且已拍板）→ 不追问、门禁过；
  信号命中且未拍板 → 入待问，以「不涉及+理由」或四策略之一拍板后关闭。
- A4 条件·签名：两侧完整且完整对应 → 不出现；两侧完整且有差异（含部分重合、
  重排）→ 入待问；任一侧缺失/解析不完整/多份未定稿 → 以「无法判断」入待问；
  有效拍板（含「不适用+理由」）后关闭，done 可达。
- A5 记录契约：有效拍板判定生效（「暂不决定」不完成）；失效记录对新旧两版调度器
  都表现为未答；仅有原话的存量记录仍算已答、用于条件比较时判「无法判断」。
- A6 兼容：无新参数时 CLI 输出与 `--json` 既有字段语义同现状（缺陷修复除外）。

**阶段 B · 交互层（intake + 总审）**

- B1 快速路径端到端：intake 必填面全填有效 → `--all` 总审一轮全部接受（条件项
  同轮呈现并拍板）→ done → T4 落稿 → T5 五层退 0 并取得 sha256 匹配封条；
  人输入恰 2 次。缺口路径验「最终全部解决、无死循环」，不验轮数。
- B2 条件闭环端到端：初始无 doc、前提「非随机」、候选生成规则含「正态分布」→
  调度器以候选文本求值、`3.2.random_strategy` 同轮入总审、以「不涉及+理由」
  拍板 → T4 → T5 过。仍为 2 次输入。
- B3 映射：原话逐字保真；空格跳过；「暂不决定」不完成；部分批准只完成展示且
  被接受的项；拒绝/更正项重新生成后再确认。
- B4 `--all`：全部 pending 无遗漏无重复；detail 字段齐；`--all --json` 可用。
- B5 失效：FR7 四个代表场景逐一验「下游失效并重走确认」；反例场景验「不失效」。
- B6 交付核对：intake 模板必填面与 FR1 的 key 集合逐项一致，判据行可溯到任务书
  模板原文；SKILL.md 新段与模板里每个自造术语首现处有就地定义或链接。

**不变量核对（两阶段各跑一次）**

- I1 骨架字段对照：`decision_owner`/`agent_may_propose`/`required`/`condition`
  全字段 diff 为零（只允许 `question_batches` 变）。
- I2 `_checks.py` diff 为空；golden 与全部 defect fixtures 的门禁输出逐字节不变。
- I3 预算实测：按 INV5 的计量集合 `wc -c` 核对。
- I4 全部现有测试 + 新增测试绿；`doc_style_lint.py` 过。
