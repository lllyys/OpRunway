# 接一条新验收线的方法论

拿到一组新任务书和它们的目标仓，怎么判断该适配现有 skill 还是新起一条、harness 自产到
哪一档、落地按什么顺序做。本文抽自 blas、sparse、ATK 三条既有线与 0923 solver 批次的摸底，
每条都有仓内先例可查。

**这件事的形状：** 输入是任务书（判据与交付契约）与目标仓（被测工程的实际形态），输出是
一条能在零上下文下跑完的验收通路。中间的全部工作，是把两者之间的落差消化掉。

两份配套文档，本文不重复它们的内容：

- 谁产任务书、谁产用例、谁产 harness，各自产物能不能当证据——[acceptance-roles.md](acceptance-roles.md)
- 0923 solver 批次按本文走一遍的实况与证据——[solver-0923-context.md](solver-0923-context.md)

## 一、摸底：七个问题

按序问，后一问依赖前一问。每个答案都要带出处（文件路径加行号，或任务书原话）。

**凭印象记的结论到评审时会塌。** 本文初稿被推翻的三处判断，全是归纳原文归纳出来的。

1. **哪些槽已经被别人填了？** 任务书谁写的、用例谁造的、harness 由谁交。这条决定后面
   全部工作是「生产」还是「核验」，所以排第一。
2. **交付形态是什么？** aclnn 两段式、kernel 直调的 handle API、还是框架接入。判别法不看
   措辞看对标：对标 cuSolver/cuBLAS/cuSPARSE 这类句柄式 C 库的是 kernel 直调，
   对标 `aclnnXxx` 的才是两段式。
3. **验收粒度是什么？** 一接口一任务，还是一族多接口不可拆。它决定任务包定义与 A5 要不要
   跨包聚合。
4. **判据逐条抄原文。** 精度看标杆来源、容差形态、判法；性能看**计时对象**、采样口径、
   统计量、标杆来源；另有内存门与契约门。不要归纳——归纳会把「或」写成「且」，
   也会把「kernel 耗时」写成「API 墙钟」。
5. **包里给的用例是哪一类？** 精度用例、性能用例，还是都不是。判别看字段有没有期望值、
   容差、golden 路径；但**没有这些字段只说明它不是现成的精度用例**，不等于不能由 shape
   构造输入再算参考。
6. **被测工程的测试形态是什么？** harness 怎么驱动、构建入口、绑卡方式、执行契约
   （谁调谁、传不传参、判 PASS 看什么）。
7. **标杆从哪来？** 三种答案通向完全不同的通路，这一条最容易看错：

| 标杆形态 | 谁产 | 验收侧怎么办 | 先例 |
| --- | --- | --- | --- |
| 本机可产 | 我们 | 正常采集 | blas 的 `gpu_baseline.csv` |
| 任务书给死一张表 | 任务方 | **只能引用，产不出来** | `external-perf.md` |
| 要求开发者实测填入 | 开发者 | 核其口径与出处，不合就留白 | 0923 |

第三种最容易被误判成第二种：表里写着「待测」就不是给死的表，责任在开发者，随包数据只是
参考而非答案。

## 二、落差表：把「不能」逐格勾出来

把现有线的能力逐项对着任务书要求勾，产出「能 / 不能 / 改数据就能」三类格子。
`external-perf.md` 那张能力对照表是成品范例，结论落成一句可判定的话：有一条落在「不能」上，
A4 就是两步。

**落差要分三层记，消化成本差一个数量级。**

| 层 | 是什么 | 消化方式 | 先例 |
| --- | --- | --- | --- |
| **L0 数据** | 域惯例：列名、状态词表、入口头、绑卡开关、库路径 | registry 加一档 profile，引擎不动 | `blas` → `sparse_frame` |
| **L1 模型** | 用例模型能不能表达：依赖链、输入恢复、族级不可拆、workspace 门 | 扩投影原语或扩 IR | sparse 的 `case_controls` |
| **L2 物理** | 两边报的数是不是同一个物理量 | 换量具，或判定这批数据不可用 | 见下 |

L0 是填表，L1 是改引擎，L2 是换量具。落差全在 L0，适配几乎必赢。

**判 L2 只有一句话：两边报的数，是不是同一个物理量。** 但问之前先分清这个问题问的是谁——
问我们的量具，还是问别人给的数据。这两件事的结论完全不同：

- 落差在**我们的量具**上：现有采集方式测不出任务书要的那个量，只能换量具或另起通路。
- 落差在**别人给的数据**上：我们的量具没问题，不可用的是那批数据，处理方式是核口径、
  标注差异或留白。

**把这两件事混起来，会得出「现有量具不适用、必须另起采集通路」的错误结论。**
判之前先把任务书的计时对象抄原文，再把量具实际报的量查出来，两边并排看。

## 三、两个耦合的决策

### 3.1 轴 A：适配现有线，还是新起一条

四个候选，不要临时发明第五个：

- **A1 原 skill 内参数化**——域差异塌进声明数据，引擎不开分枝。
- **A2 复用另一条既有线**——把新域接到形态更近的那条上。
- **A3 新建平行 skill**——按需复用已独立的工具，run 链自写。
- **A4 抽共享核心 + 按域 skill**。

**先过一道权限筛：候选必须是我们能单方面执行的。** 依赖目标仓维护者合入才成立的做法
（典型是「给目标仓补一套测试 frame」）不是候选，只能作为上游建议提出来——权限模型见
[acceptance-roles.md](acceptance-roles.md) 第二节。

打分之前先过「能不能塌进数据」的四个机械问法，任何一条答「不能」，A1 就要重估：

1. 域差异能不能只进数据，引擎里不出现域名词、不开 if-domain？
2. 新东西能不能映射到已有的有限投影原语？**需要新原语就不是纯适配。**
3. 所有消费者（表头、行物化、轴、边界键、性能键、README）能不能读同一份 IR？
4. 单算子只能选 profile 填事实，不能自己发明投影？

第 2 条最常被含糊过去。判法：把新域要的东西写成一句话，看它是不是「已有原语的某个取值」。
是取值就是 L0，需要新动词就是 L1。

**两条不随域变化的成本判词**（来自 2026-09-01 的 sparse 裁决与 2026-09-21 的 solver 评审）：

- **新建平行 skill 的真实成本是「重复买隔离」**：引擎与各项机制一式两份，双修复与漂移是
  永久成本，不是一次性搬运费。但这条只在**确实会复制两套完整实现**时成立——按需复用
  已独立的工具、只自写 run 链，不落这个成本。
- **抽共享核心的前提是有两个真实消费者证明同一个接口够用**。边界没有实证时，
  抽取是在预测未来需求，迁移足迹却已经付出。

### 3.2 轴 B：harness 的调用器从哪来

| 档 | 我们出什么 | 需要仓里有什么 | 仓内先例 |
| --- | --- | --- | --- |
| **① 消费自带** | 只出判据器 | 能认得出、读得懂的调用入口 | blas-accept 的 A2′ |
| **② 注入 overlay** | harness 源码，装进开发者工程检出 | 按名注册的构建挂钩；有 frame 则大幅省事 | `repo-task-blas-harness-gen` |
| **③ 独立执行器** | 整个执行器，不碰仓的测试树 | 只要公开头 + 可链接的库 | `run_cxx.py` + `standalone_runner/` |

选档的两条独立轴：

- **仓的 frame 强度**决定调用器能不能低成本复用。对照组 ops-blas：`test/frame/` 九个共享头
  （含 `csv_loader.h` 与 `verify.h`），70 个算子目录下 69 个 `_param.h`、74 张 CSV、
  99 个 `_test.cpp`，开发者只填 per-op 三件加一个 golden。
- **golden 的可审性**决定判据器能不能直接消费。ops-blas 的 `sasum_golden.h` 共 36 行、
  核心一句 `cblas_sasum(n, x, incx)`，一眼审完。

**档② 不是「改目标仓」。** overlay 追加进开发者的工程检出，不碰既有文件、可整体回滚、
不经过维护者。装不装得进去只看仓的测试注册机不机械——ops-blas 与 ops-solver 都是按名
`add_subdirectory`，追加目录就够。

真正决定档② 划不划算的是**装进去的东西要自带多少**：

- **仓有 frame**（ops-blas）：per-op 只需薄薄几件，驱动、读表、比对都在仓里的共享头里。
  blas-harness-gen 走的就是这条，它绑定具体 revision 的 frame ABI，明写「只声明对该
  revision 兼容」——frame 面两个月改过六次，所以安装 preflight 的 revision 与 fingerprint
  校验是硬门。
- **仓没有 frame**：per-op 文件得自带驱动、golden 与比较，那已经是一个完整执行器，
  只是住在人家的 `test/` 目录下、用人家的构建脚本编。

**所以无 frame 时，档② 与档③ 的差别收缩成部署位置，不是工作量。** 两边都是我们写全套，
取舍轴变成「借不借上游的构建系统」：借，省掉自配编译链，但受其既有执行约定约束、工程
结构一变就要重新适配；不借，只依赖公开头与可链接的库，边界最稳但环境自理。

**档③ 的代价不在执行器本身。** 现成的 `run_cxx.py` 按 aclnn 两段式写死（搜
`aclnn…GetWorkspaceSize`、要求尾参 `uint64_t*` / `aclOpExecutor**`），换一种 API 形态就要
新写后端；真正的大头是 golden 与**输入恢复**（见第六节最后一条）。

### 3.3 为什么必须一起判

两轴互相隐含工作量，各自取最优会得出组合起来不成立的答案：

- 档② 要求先有符合六件契约的任务包，选它就隐含先做一套该域的 case-gen。
- 档③ 的现成件只覆盖精度，选它就隐含自建性能采集。
- 轴 A 的每条路线都默认倾向某一档：A1 倾向 ①/②，A2 倾向 ③，A3 两轴自由但都要自己填。

所以结论要给成一个 **(轴 A, 轴 B) 的配对**，并且按八维（见 `.claude/rules/codex-review.md`，
复杂度双权重）逐维打分、显式处理维度冲突。

## 四、定硬边界：先写不变量，再写代码

候选的评分建立在前提上。前提不写死，实施中会被悄悄放弃，最后拿到的是高成本方案的成本
加低成本方案的承诺。所以裁决落地时要同时写出**违反即评分作废**的边界清单。

sparse 那七条的形状可以照抄，其中一条对任何新域都适用，**且必须排在动手之前**：

> 回归门先升级再动手。现有 check 只证明「新版自洽」，不证明「与旧行为一致」。

做法是改之前先钉住既有域两个代表算子的产物字节摘要（CSV、表头、块数、基线），再加三件：
覆盖每个既有原语的投影矩阵测试、新域一个最小包的逐字节复核样例、跨消费者的身份一致性验证。

新起一条线时另加一条边界，否则第 3.1 节那个评分立刻失效：

> 不复制既有线的完整 A1/A5，不写逐接口的采样分支，不借「独立」绕开既有机械门。

## 五、落地形态

**验收零上下文：一次验收的完整契约就是 `SKILL.md` 加 `references/` 加 `scripts/`。**
`CLAUDE.md` 与 `docs/` 是开发件，不进任何测试部署，验收时当它们不存在。

| 落点 | 放什么 | 判别 |
| --- | --- | --- |
| `SKILL.md` | 主流程阶段表、入口参数、每阶段的命令与退出码去向 | 读者要按它一步步做 |
| `references/*.md` | 运行态权威细节：字段、路径规则、协议、排障 | 主流程撑不下又必须精确 |
| `scripts/*.py` | 机械门：校验、生成、裁决 | **判据的确定性由它承担，不得绕过** |
| `assets/template/` | 随包渲染的量具与 README 模板 | 产物要逐字节可复现 |
| registry（模板内数据表） | 域惯例十二字段 | 换域只改值不改引擎 |

registry profile 的十二个字段是接新域的填空题清单：`seed_columns`、`description_column`、
`expect_column`、`expect_default_token`、`status_vocab_bound`、`threshold_columns`、
`first_param_ctype`、`entry_headers`、`footprint_policy`、`build_device_flag`、
`visible_devices_env`、`runtime_library_dirs`。

填不满或填不下，就是 L0 装不下的信号，回第三节重判，不要靠 overrides 硬塞——
`harness_overrides` 的可覆盖键恰四个且整键替换，这个上界本身就是防止适配悄悄变形的闸。

**profile 绑的是仓，不是域。** `entry_headers`、`build_device_flag`、
`runtime_library_dirs` 这些全是某个仓在某个 commit 上的事实，而**各仓由各自的维护者独立
演进**——`blas`、`sparse_frame` 这类 key 听着像算子域，编码的其实是仓的样子。所以每档
profile 必须记出处与基线 commit：**没有基线的 profile 是一句会过期而不自知的断言**。

接新域的三件机械事，顺序固定，做完才算接上：

1. **registry 加一档 profile**，十二字段按目标仓普查实例化，出处写进注释
   （sparse 那档注的是 `ops-sparse@5b2a5ba`）。
2. **既有域零漂移**：重跑既有算子的完整产物，逐字节比对旧版摘要。
3. **新域最小闭环**：一个算子从任务书到结论跑通全程，产物进样例或测试夹具。

## 六、常见错判

七条都踩过或被评审当场抓出来过。实例与证据在
[solver-0923-context.md](solver-0923-context.md)，这里只留判据。

- **把竞品自检当精度用例。** 竞品 bench 里的 `check` 是测速守门员，判「调用有没有写错」，
  残差超标就把该条耗时置 null。它比的是自洽，不是与高精度参考逐元素比。
- **把随包数据当标杆而不核口径。** 没有出处、采集口径与判据不符的数不是标杆。
  措辞也要卡住：只能说「逐结果来源无法建立」，不能反过来断言它一定来自某张卡。
- **用伪参数迁就旧模型。** 把造数控制伪装成 `params` 会打破「params 逐字对应 C 原型」
  的现有契约。宁可单独开一节。
- **半统一。** 只统一表头、留下另外几套各自维护的规则，等于付了重构成本却没拿到不变量。
- **把「入口没传参」误读成「表达不了」。** 构建脚本不传参是常见的，但二进制本身往往收
  完整入参。**判一件事「做不到」之前，先看它的入参面。**
- **把第三方工具的能力上限当成自己的。** 上游工具算不了某个统计量，不代表本仓自带的量具
  也算不了。缺的通常是被测对象的适配，不是统计公式。
- **漏掉输入恢复。** 原地写回的算子（getrf 一类）在预热与采样循环里会反复吃自己上一轮的
  输出，那不是同一输入的重复测量。**设计 runner 时，输入恢复与准备段归因比选 CSV 还是
  JSON 重要。**
