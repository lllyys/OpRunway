# blas 性能采集换 msprof op 行为规格（spec v2，2026-09-23）

本文是行为契约：定义换后端与撤 warmup 之后系统「是什么」，不含实施顺序与文件改动清单
（那是 plan 的事）。

下文用「**验收协议**」指 `repo-task-blas-accept/references/perf-protocol.md`，用
「**渲染契约**」指 `repo-task-blas-case-gen/references/perf-protocol.md` 收缩后的形态，
用「**复测协议**」指 `repo-task-blas-accept/references/retest-protocol.md`。不再用单字母
代称——两份同名文件用同一个字母会让后文的「某某的字段表」无法定位。

复测、豁免、折叠与证据保护的契约见前身 `blas-retest-warmup-spec.md`（spec v6），
其 §7 warmup 整节与 §11 附录 A 的落卡核对被本文推翻，其余不变。

v1 到 v2 按 Codex 八维评审（2026-09-23，gpt-6-astra，xhigh）与第三轮真机实测重写四处：
多 launch 改用 `--launch-count` 求和并撤销 v1 的每算子探测；承认 sparse 共用这条实现
路径；修正退出码表述与失败判定顺序；空间预算改为逐例检查。

## 1. 范围

只改性能采集后端与预热设计。精度量具、精度侧 `-rerun`、复测与豁免的折叠规则、
证据保护契约全部不动。

改动面横跨两个 skill，这是唯一能真正换后端的路径：

- `repo-task-blas-case-gen` —— 量具模板 `assets/template/verify_performance.py` 是采集的
  唯一实现，`scripts/package.py` 的 `render_runtime()` 把它渲染到真机。
- `repo-task-blas-accept` —— `scripts/accept.py` 在 A2 直接 import 上面那个 `package.py`，
  自己一行采集代码都没有；它消费量具产出的轮 JSON。

### 1.1 sparse 共用这条实现路径

**本轮不修改任何 sparse 专属代码，但 sparse 的运行时行为会跟着变。** 这两件事必须分开说。

`repo-task-blas-accept` 的适用范围本来就写着 ops-sparse 与 aclsparse，而
`render_runtime()` 对所有 `harness_profile`（`blas` 与 `sparse_frame`）渲染**同一份**
性能模板。换模板就是同时换掉 sparse 新渲染出的量具；撤 warmup 与撤落卡核对同样作用在
共享的消费路径上。

sparse 因此要进兼容性检查与回归范围。想让 sparse 行为完全不变就得另做实现隔离，
那等于长期维护双后端分支，按复杂度维不划算，本轮不做。

不碰 `repo-task-atk-accept` 与 `repo-task-case-gen`。

## 3. 实测事实基线

全部在 a3 的 `oprunway_prov` 容器实测，CANN 9.0.1，2026-09-22 至 23。完整记录见
scratchpad 的 `msopprof-facts.md`，本节只列进入契约的那些。

| 事实 | 值 |
| --- | --- |
| 二进制 | `msopprof` 独立可执行且在 PATH；`msprof op` 子命令同样可用 |
| 参数顺序 | `--output` 必须在被测程序之前，放后面会被当成程序参数 |
| `--application=` | 已废弃，改用位置参数 |
| `--ai-core` / `--task-time` | **被拒绝**，退 255 报 `unexpected argument` |
| 默认 `--launch-count` | 1，只采第一个 kernel launch |
| `--launch-count=N` | 可用；超额指定安全、零额外耗时与体积 |
| 产物布局 | 见 §4，取决于实际采到的 launch 数 |
| `Device Id` 语义 | **物理卡号**（`ASCEND_RT_VISIBLE_DEVICES=3` 时报 3 而非逻辑 0） |
| 退出码 | **不透传被测程序失败**；工具自身参数或初始化失败会退非零 |
| gtest 证据 | `--gtest_output=json:` 正常透传 |
| 单 launch 用例耗时 | `--aic-metrics=BasicInfo` 档 4.6s（默认档 6.2s） |
| 产物体积 | 约 2.2 MB 每 launch，随实际 launch 数线性增长 |
| 预热效果 | `--warm-up` 取 0 / 5 / 50 得 26.70 / 27.34 / 27.16 us，噪声级 |

### 3.1 耗时不再宣称提速

单 launch 用例上新后端 4.6s、旧后端约 10s。但多 launch 算子的采集耗时随 launch 数上升
（probe4 的 14 launch 耗 7.6s），而 cherk 每次调用至少 5 个 kernel。

**在拿到多 launch 真实算子的实测前，不对整体耗时下结论。** v1 写的「快 54%」只对
单 launch 用例成立，已撤回。

## 4. 采集命令与产物

### 4.1 命令

量具对每次采样发起的进程是：

```
msopprof --output=<采样目录> --aic-metrics=BasicInfo --launch-count=<N> \
         <被测二进制> --gtest_filter=<用例> --gtest_output=json:<证据路径>
```

四条约束进契约：

1. `--output` 与其余选项必须排在被测二进制之前，其后一律视为被测程序的参数。
   **选项一律用 `--key=value` 形式**：空格分隔会报 `argument --output miss value`
   （V1 实跑踩到）。错误信息不提示形式问题，容易误判成目录不可写。
2. 不再拼 `--application=`；被测程序及其参数作为 argv 尾原样透传，`shlex` 依赖随之去掉。
3. 不再传 `--ai-core` 与 `--task-time`，它们在新命令下是硬错误。
4. `--launch-count` 取一个宽裕的定值，默认 512（工具允许区间是 1 到 5000）。实测超额
   指定不报错、不增加耗时与体积，采到的就是进程实际发生的全部 launch。

选 `--aic-metrics=BasicInfo` 而不用默认档的理由是耗时与文件数都更低，读数不变。

二进制查找顺序沿用现行四级（`--msprof` 覆盖 → PATH → `$ASCEND_TOOLKIT_HOME` 下 →
`/usr/local/Ascend` 下），查找目标名改为 `msopprof`。**CLI 参数名 `--msprof` 保留不改**，
只更新帮助文本与查找目标——改参数名会扩大对外接口足迹，收益只是名字好看。

**可执行不等于可用。** 预检除判可执行位外，还要跑一次 `msopprof --help` 确认退 0；
不退 0 时报环境错误而不是采集失败，否则旧 CANN 上会表现成每一例都是算子问题。

### 4.2 产物布局有两种

布局取决于**实际采到的 launch 数**，不取决于 `--launch-count` 的取值：

| 实际采到 | 路径 |
| --- | --- |
| 1 个 | `OPPROF_*/OpBasicInfo.csv` |
| 多个 | `OPPROF_*/<kernel 符号名>/<序号>/OpBasicInfo_<时间戳>.csv` |

glob 必须递归覆盖两种：`OPPROF_*/**/OpBasicInfo*.csv`。只写扁平那条会在多 launch 算子上
扫空，表现为每例 NO_KERNEL，与「算子没跑起来」长得一模一样。

### 4.3 解析

一次采样的读数是**递归 glob 命中的全部文件、全部数据行的 `Task Duration(us)` 之和**。

行数等于该次进程实际发生的 kernel launch 数。多份多行是多 launch 算子的**正常形态**，
不是异常。

计分要求四条同时成立：至少一份文件、至少一个数据行、`Task Duration(us)` 列存在、
每个值都是有限正数。任一不成立按 §5 归类。

### 4.4 截断必须 fail-closed

**采到的行数等于 `--launch-count` 时，判环境不支持并停，不计分。**

理由是这种情况下无法区分「恰好这么多」与「被截断了」，而截断的后果是求和少算、
ratio 虚高、假 PASS——这是本次换后端唯一会把 FAIL 写成 PASS 的路径。

工具在计数达到上限后**静默停止**给后续 kernel 分配采集路径，只记一条 debug 日志，
不报采集失败（源码见 msopprof 的 `csrc/op_profiling/prof_injection/
device_process_manager.cpp:29-54`）。官方文档也把该参数定义为「最大采集数量」。
所以撞上限时一切看起来都正常：gtest 成功、CSV 合法、求和得出一个偏小的数。

这条不是假想防护，源码上已有两个确定的反例（`ops-blas@621aafdb`）：

| 算子与输入 | launch 数 | 构成 |
| --- | --- | --- |
| `ssymm/arch22` TC_L1_04 m=512 n=512 | **194**（实测） | 上三角 1 + pack/accum/dense 各 64 + 后处理 1 |
| `ssymm/arch22` TC_L0_02 | **50**（实测） | 下三角 1 + pack/accum/dense 各 16 + 后处理 1 |
| `sgemm_strided_batched/arch35` batchCount=128 | 128（源码推算） | 主机循环每批一次；`batchCount` 无上界 |

默认取 512 是基于这些反例留的余量，不是「必然够」的保证——保证来自本节的截断检查。
ssymm 的 194 已经用掉默认值的三分之一，而它只是 m=512 的中等规模。

sparse 侧本轮源码检索未找到超过 100 的反例：`SpSM` 的层级循环与
`gtsv2_strided_batch` 的 batch 消元循环都在 kernel 内部，host 侧只 launch 一到三次。
这不构成整仓上界证明，但 BLAS 的反例已经足以否定「100 够用」。

撞上限时的措辞是「当前采集口径不支持该用例的 launch 规模」，不能说成算子失败。
提高 `--launch-count` 能解决一部分，但产物体积随实际 launch 数线性增长
（约 2.2 MB/launch），几百个 launch 就是几百兆一次采样，所以上限不能无脑拉满。

`Task Type` 过滤整体作废：该列不存在，现行的 `KERNEL_TASK_TYPES` 常量与过滤分支一并删除。
`Op Name` 与 `Op Type` 两列**不进判据**——给它们定期望值等于给 case-gen 的 FACTS 加算子
相关字段，而本轮没有需要它们的判据。

九列依次是 `Op Name`、`Op Type`、`Task Duration(us)`、`Block Dim`、`Mix Block Dim`、
`Device Id`、`Pid`、`Current Freq`、`Rated Freq`。

## 5. 失败判定

判定按固定顺序走，先到先定，**环境问题必须排在算子证据之前**：

| 顺序 | 条件 | 终态 |
| --- | --- | --- |
| 1 | 采集进程超时 | TIMEOUT |
| 2 | 工具自身退出非零，或日志显示采集、写盘失败 | 环境错误 |
| 3 | gtest 证据不合格或缺失 | CRASH |
| 4 | 无文件、无数据行、缺列、值非有限正数 | NO_KERNEL |
| 5 | 以上都不成立 | 计分 |

第 2 条不恢复旧的「非零退出 → NO_KERNEL」。工具失败是环境问题，把它记成算子问题会让
排错方向完全相反。

不存在的 gtest 用例落在第 3 条：证据 JSON 里没有该用例的记录，判 CRASH 而非 NO_KERNEL。

### 5.1 磁盘不足必须与 NO_KERNEL 区分开

实测踩到：容器 `/dev/shm` 仅 64 M，被采集产物占满后 msopprof 仍退 0，只在日志里刷
`[WARN] Copy failed [...]`，且不产 CSV。按判定顺序这会落到第 4 条，也就是把环境问题
说成算子没起 kernel。

磁盘满还可能更早发作——gtest JSON 写不出来就先撞第 3 条判 CRASH，根本到不了第 4 条。
CSV 也可能存在但为空或截断。所以只查「文件不存在」不够。

三条防线进契约：

1. 日志检查覆盖写盘失败的多种表述，不只匹配 `Copy failed`；命中即判第 2 条环境错误。
   这条排在 gtest 证据之前，所以磁盘满不会伪装成 CRASH。
2. **每次采样前检查一次可用空间**，不是只在开跑前查一次。阈值按**本次采集上限**算，
   不按上一次的实际占用算：`--launch-count × 2.2 MB × 峰值系数`。

   不能用上一例的体积外推下一例：上一例可能只有一个 launch，下一例可能有一百个。
   用上限算是唯一在跑之前可知的量。峰值系数要大于 1，因为工具先复制目录再删原目录，
   有两份数据同时在盘的阶段——最终目录大小不是峰值。`2.2 MB/launch` 是经验值，
   也要留余量。

   按 512 的默认上限，单次采样的预算就是 1 GB 出头。这个数看着大，但它是**检查阈值**
   而不是实际占用：单 launch 用例的实际产物仍是 1.8 MB。空间不足时报环境错误并停，
   使用者可以调小 `--launch-count` 或换盘。
3. 采集目录不落 `/dev/shm`。这条是容量约束与风险提示，不是对 tmpfs 的一刀切禁令：
   大容量 tmpfs 未必失败，普通磁盘也未必安全，真正的保证来自第 2 条。

**本轮不自动清理已写入阶段目录的产物。** 现行证据保护契约把这些文件列为保留证据，
清理它们要先定义临时文件与保留证据的边界，那是另一件事。

## 6. 读数语义

**一次采样的读数是该次进程全部 kernel launch 的 duration 之和**（§4.3），
不再按 `calls_per_case` 做除法。

`calls_per_case` 字段本身保留并冻结为常量 1。保留的理由不是兼容包袱，而是它同时是复测
绑定锚、`evidence_id` 的哈希输入项与 `check.json` 的契约比对项——删字段会让已在盘的全部
`check.json` 自检失败。

冻结要在**生产入口**落实：新产生的采集一律只接受 1，accept 的 A2 参数入口与操作说明
同步收紧。读取历史记录时不追加这个限制。

`launches` 字段语义不变，仍是本次采样的 kernel launch 数；单 launch 算子下它等于 1。

### 6.1 这是口径变更，不是等价替换

同机同用例双后端实测（均为单 launch 用例，与 launch 计数无关）：

| 用例 | msprof | msopprof | 比值 | 绝对差 |
| --- | --- | --- | --- | --- |
| TC_PF_1001 | 23.78 us | 15.30 us | 0.64x | 8.48 us |
| TC_PF_1002 | 45.40 us | 35.72 us | 0.79x | 9.68 us |
| TC_PF_1003 | 68.50 us | 57.26 us | 0.84x | 11.24 us |

**新后端系统性读低。** 绝对差基本恒定在 8.5–11 us，是固定的单次调用开销被重放绕过的
特征；规模越小受影响越大。

两个读数量的是不同的东西：msprof 量真实的单次冷调用，含首次调用惩罚；msopprof 重放
kernel，量的是稳态。都不错，但**不可比**。NPU 侧读数变小会让 ratio 变好，卡在阈值 `0.8`
附近的用例可能从 FAIL 翻成 PASS。

哪一种更接近 GPU 基线的口径，**本轮无法判定**：基线的 `perf.meta` 六个键当前全是
`unspecified`，包括 `warmup`。不能宣称换后端「更准」，只能说它换了口径。
验收协议里「计时口径只使用 msprof 的 kernel task duration」这句要同步改写，
并把这次口径变更记进已实测边界。

跨后端折叠的洞**已被现有机制堵住**，不需要新增防护：`verifier_sha256` 是量具脚本自身的
哈希，也是复测绑定锚之一。换后端就是换脚本，哈希随之变化，拿新量具去复测旧首轮会被
绑定锚校验判成无效轮，不会混进折叠。代价写在 §9。

## 7. warmup 撤除

预热设计整体删除，不保留兼容分支。依据是 §3 的实测：重放模式本身绕开首次调用惩罚，
`--warm-up` 取 0 到 50 只有噪声级差异。

量具侧删除六段：顶层 `warmup` 序列化、`_case_record` 的 `warmup` 形参与 `warmup_exit`
字段、采样前的整段预热子进程分支、`--warmup` 参数定义、取值范围校验、复测模式下的归一。

accept 侧删除五处：测量轮的 `warmup` 必填校验、逐例 `warmup_exit` 类型校验、
复测史记录里的 `warmup` 键、复测明细表的 `warmup` 列、报告页脚相关措辞。

### 7.1 落地顺序是单向的，不是对称耦合

两侧的兼容关系不对称：

| 消费者 | 带 warmup 的旧记录 | 不带 warmup 的新记录 |
| --- | --- | --- |
| 旧 accept | 可读 | **测量复测轮判无效** |
| 撤除消费后的新 accept | 可读 | 可读 |

所以**先改 accept，再改量具**。第一步就是最终消费者行为，不需要临时的「字段存在才校验」
分支。反过来做（量具先撤）会让每个测量复测轮被判无效、静默跳过折叠，报告只剩首轮，
而 accept 不报错退出——症状看起来像量具坏了。

预热超时那条「记单例 TIMEOUT 后不再采样」的快捷路径随之消失。TIMEOUT 此后只可能来自
采集进程本身。

### 7.2 一个同名陷阱

`package.py` 的 `PERF_META_KEYS` 里有一个 `warmup`，那是 `gpu_baseline.csv` 顶部的基线
采集元数据，描述对照组（GPU）自己怎么测的，与量具的 `--warmup` 只是重名。

这个 `warmup` 一个字都不能动。按名字全仓搜删会顺手删掉它，连带 `facts-schema` 的
`perf.meta` 校验与基线表头一起坏。

## 8. 落卡核对撤除

`PROF_*/device_<卡>/` 这层目录在新后端下不存在，落卡核对失去现有数据源。按用户裁定
整条撤除，不改读 `Device Id` 列。

accept 侧删除 `PROF_DEVICE_GLOB`、`PROF_DEVICE_RE` 两个常量、`_prof_device_cards` 整函数、
以及 `_measure_round_problems` 里据此产生的 problem 与 warning。

**撤除要有替代告警，不是静默消失。** 换卡轮在报告的该轮摘要处输出一次
「实际落点未独立核对，设备号来自量具记录」。不扫描 CSV，也不恢复核对。

换卡轮的有效性从此只靠量具自报的 `device_resolved` 与绑定锚比对。复测协议里要明写这次
降级，并留下退路：`OpBasicInfo.csv` 的 `Device Id` 列是物理卡号，想恢复独立核对时让
accept 读这一列即可，不需要重新做实验。

## 9. 兼容性

`RETEST_SCHEMA_VERSION` **不升版本**。accept 对该版本做严格相等比较，直接升常量会让
既有的 measure 与 waive 复测轮全部变成无效轮。撤字段对新读者天然兼容：warmup 不参与
折叠核的状态计算，删掉消费点之后旧记录照样能读。

准确的表述是「历史复测轮被跳过」而不是「所有 JSON 失效」——首轮不经过复测版本检查。

要分清两件容易混的事：

- **旧首轮加已有的旧复测轮，继续正常折叠。** 绑定锚比较的是复测轮与**它自己的首轮**，
  不是与当前量具。换了 accept 不会让原本匹配的历史组合失效。
- **新量具给旧首轮追加测量复测，会被拒绝。** `verifier_sha256` 与首轮绑定，
  换后端改变该哈希（§6.1）。这是正确行为：两轮口径不同，折叠它们会让复测天然占便宜。
  要复测就得用新量具重跑首轮。

这条要在复测协议里写成显式的迁移说明，否则使用者会看到「复测跑了但报告没变」，
而那正是 §7.1 描述的最难排查的症状。

旧首轮 JSON 带 `warmup` 与 `warmup_exit` 字段，新 accept 读到时忽略即可，不报问题。
首轮性能 JSON 顶层的 `msprof` 字段记采集二进制路径，accept 从不读它，字段名保留、
内容改记 `msopprof` 的解析结果。

## 10. 预算账

SA-04 载入预算只统计 `SKILL.md` 与同一行链出的 `references/*.md`。`scripts/` 与 `assets/`
一个字节都不进账——所以量具与示例里省下的约 12 KB 对预算毫无帮助。这一点纠正了立项时
的预期。

按三条链分别算，不能算总数：

| 链 | 现余量 | 本轮动作 | 预计余量 |
| --- | --- | --- | --- |
| accept `SKILL.md` → `run-chain.md` | 8 B | 删 A4″ 性能复测整节 1051 B，删 warmup 相关 190 B | 约 1.2 KB |
| accept `SKILL.md` → 验收协议 | 2346 B | 撤 warmup 与除法相关约 4.4 KB，加新后端描述 | 约 5 KB |
| case-gen `SKILL.md` → 渲染契约 | 40 B | 按 §12 收缩 | 约 2.8 KB |

删 A4″ 节是删重复不是删信息：那 1051 B 与 `SKILL.md` 的 A4″ 段、复测协议逐字同源。

**三处锚点必须与小节同批处理。** 删验收协议的 `## warmup` 会让它目录里的 `#warmup` 锚点、
`run-chain.md` 与复测协议各一处的引用解析不到。SA-05 交叉引用检查是全仓拦截规则，
漏一处 lint 直接退 1。

## 11. 测试

现行 `parse_op_summary` **零测试覆盖**——全仓没有一份伪造的 profiling CSV，集成测试一律
在这个边界上打桩。而它恰好是唯一一处出错会把 FAIL 写成 PASS 的地方。

新解析器要补真单元测试，覆盖两种布局与全部异常形态：扁平单行、嵌套多行、零文件、
缺列、空文件、截断、非有限值、负值，以及「环境失败同时缺 gtest JSON」的组合。
`repo-task-blas-case-gen` 目前没有 `tests/` 目录，需新建（不放 `__init__.py`）。

accept 侧 `tests/test_retest_contract.py` 约 15 条用例依赖 `PROF_*/device_<卡>` 落点层级，
随 §8 撤除一并重写。这里有一个假绿风险：常量改了而 fixture 没改时，glob 扫空走的是
「缺目录不告警」的合法分支，测试会绿但设备核对已被静默关掉。重写时要有一条用例显式
断言该核对已撤除并输出了替代告警，而不是断言它没报问题。

两个 example 目录（cherk、sasum）是 `package.py` 的逐字节渲染产物，模板改完后各跑一次
render 即可，不手工改一个字。这条一致性门在本仓内无人自动校验。

**cherk 是多 launch 算子**（每次调用至少 5 个 kernel），正好是验证 §4.2 嵌套布局与
§4.3 求和的天然用例，应纳入真机回归。

## 12. 协议权威归属

**accept 侧的 `perf-protocol.md` 是正式性能协议的唯一权威；case-gen 侧收缩成渲染契约。**

Codex 按八维评审后推荐此方案（2026-09-23）。复杂度维（最高优先级）该方案得 5 分而
维持双份得 2 分，代价是本轮文档足迹比维持双份略大。

### 12.1 立项时的两个前提是错的

调查阶段说「case-gen 那份是 accept 那份的超集、把复测协议原样内联」，实测不成立：

- case-gen 的复测章节只有 6695 B，accept 的复测协议是 21879 B，后者另有完整的换卡、
  启动恢复与报告增量规则。两者不能互相替换。
- 两侧的阈值语义**真有区别**：case-gen 写「`perf.threshold` 默认 0.8 是项目策略，
  FACTS 可按任务书覆盖」，accept 写「阈值固定 0.8，由 accept 渲染进脚本并写入 manifest」。
  这是生成参数与正式验收政策的区别，去重时抹平就抹掉了一条真实契约。

维持双份的漂移风险也不是假设，已有实例：case-gen 同一份文档里，第 36 行说配不到基线的
`TC_PF_` 行不跑，第 197 行说记 `NO_REF`、只采集不评判。实现 `_comparable_rows()` 站第 36 行
那边，第 197 行是陈旧文本。

### 12.2 归属边界

- 验收协议：正式采集、解析、统计口径、失败判定、消费规则。复测仍留在复测协议，不动。
- 渲染契约：只留生成所需的输入、输出、模板替换与参数来源，并明写「FACTS 阈值可配置，
  正式验收由 accept 传入固定阈值」这条区别。
- 模板 README 里指向生成侧完整协议的含糊指针一并清理，只收缩 reference 不够。

**不要把 case-gen 特有的两节机械搬进 accept。** 「期望集与调用次数」与「逐例状态与
verdict」合计 2225 B，搬过去会把 accept 的性能协议链推到 32647 B，只剩 121 B；
而这两节的含义 accept 侧本来已有表述。

收缩是删除为主的改动，回滚成本低——这也是它能与换后端同轮做的原因。

### 12.3 顺带记一个机械门盲区

Codex 用内存探针证实 SA-05 的交叉引用检查有盲区：跨 skill 的普通链接不报错，
含 `..` 的路径不做规范化，目标不在标题表就直接跳过。

**「SA-05 放行」不能当作链接正确的证据。** 这条与本轮方案无关（方案 C 不新增跨 skill
链接），已记入待办。

## 13. 门控项

以下两条在实施中真机确认，未过门前按保守侧生效：

- **M1 多 launch 算子的端到端正确性（已过，2026-09-24）。** `ssymm/arch22` TC_L1_04
  实测 194 个 launch、5 种 kernel、194 份 CSV、总时长 92866.70 us；解析器返回的行数与
  总和逐一对上。同一份产物上**扁平 glob 命中 0 份、递归 glob 命中 194 份**——递归是
  必需项，只写扁平会让每个多 launch 用例静默变成 NO_KERNEL。
  cherk 在 a3 上建不出来（只有 arch35，本机是 ascend910_93 的 arch22 档），由 ssymm 顶替。
- **M1′ 截断路径（已过，2026-09-24）。** 在上面那份真实 194-launch 产物上，
  `--launch-count=194` 触发 fail-closed、`=512` 正常放行，措辞落在「采集口径不支持」。
- **M2 空间阈值。** §5.1 第 2 条的「上一次占用的整数倍」取几倍、32 MB 兜底够不够，
  用一次完整期望集的实跑核对，同时记下峰值与最终目录大小的差（工具会先复制再清理
  内部目录，最终大小不等于峰值）。
