## 实测结果

### 生成成功，退出码 0，生成物是数组类型

`csrc/oprunway_extension.cpp` 全文：

```cpp
// Generated by OpRunway. Do not hand-edit.
#include <tuple>
#include <vector>
#include <torch/library.h>
#include <torch/extension.h>
#include "npu_cpp_extension.h"

std::vector<at::Tensor> invoke_v0(const at::Tensor& x, at::IntArrayRef shifts, at::IntArrayRef dims, const at::Tensor& out)
{
    const c10::OptionalDeviceGuard device_guard(device_of(x));
    EXEC_NPU_CMD_EXT(aclnnRoll, x, shifts, dims, out);
    return {out};
}

TORCH_LIBRARY(oprunway_9c1e35e4a3f4b1df, m)
{
    m.def("invoke_v0(Tensor x, int[] shifts, int[] dims, Tensor out) -> Tensor[]");
}

TORCH_LIBRARY_IMPL(oprunway_9c1e35e4a3f4b1df, PrivateUse1, m)
{
    m.impl("invoke_v0", &invoke_v0);
}
```

**这就是 (b) 与 (c) 的分界判据本身**：`at::IntArrayRef shifts` 是**数组引用**，
Torch schema 写的是 `int[] shifts`（数组），**不是**第一版看到的 `int64_t shifts` / `int shifts`。

关键词扫描（B 节）：

```
'at::IntArrayRef'   in 生成物: True
'int[]'             in 生成物: True
'int64_t shifts'    in 生成物: False
'int shifts'        in 生成物: False
'aclCreateIntArray' in 生成物: False    ← 见下面这条注释，不是缺陷
'EXEC_NPU_CMD_EXT'  in 生成物: True
```

⚠ **`aclCreateIntArray` 不出现在生成物里是对的，不要拿它当反证。**
standard 派发下句柄由官方宏 `EXEC_NPU_CMD_EXT` 内部的 `ConvertTypes(...)` 建；
extended 派发下 codegen 显式写出 `ConvertType(shifts)`（E 节实测可见）。
两者都是 op-plugin 的官方转换器，`aclnn_py` 那条通路才需要自己 `aclCreateIntArray`
（因为它是 ctypes 直调，没有 op-plugin 这一层）。
🟡 **推断**：`ConvertType(at::IntArrayRef)` 返回 `aclIntArray*` 属 op-plugin 的官方重载——
本轮**没有**读到 op-plugin 源码来逐字核对该重载，判据是**下面那条真机证据**，不是读源码。

### 这条通路有真机证据（不是只在本地生成过）

GaussianBlur 走的正是 `cpp_extension` + 数组属性：`plugin/samples/specs/gaussian_blur.spec.json`
的 `ksize` 是 `default: [5, 5]`，走同一条 `int_array` 分支；
`dev-doc/oprunway-changes-brief.md` 记的那次真机复跑是「不 source 任何东西，164/164 执行成功、0 失败」，
并首次跑出全套验收产物。**所以「生成的类型能编译、能在真机上派发」有实测背书**，
不是只在本地跑了个 codegen。
⚠ 但那是 **GaussianBlur** 的证据，**不是 Roll 的**——Roll 本轮没上真机，本文不替它背书。

### C · 标量 / 数组怎么分流：只看 `default` 的值结构

`cpp_extension_codegen._attr_type`（`:148`）实测：

```
default=[1]      -> ('at::IntArrayRef', 'int[]', 'int_array')
default=[1, 2]   -> ('at::IntArrayRef', 'int[]', 'int_array')
default=1        -> ('int64_t', 'int', 'int64')
default=None     -> ('int64_t', 'int', 'int64')
default=[]       -> 拒: 是 list 但不是非空 list[int]，既非标量也非受支持的 int_array——fail-closed
default=[1.5]    -> 拒: 同上
default=[True]   -> 拒: 同上
default=[1,'a']  -> 拒: 同上
default=[[1]]    -> 拒: 同上
```

🔴 **这条最值得记**：畸形 list **不会**顺着掉进标量分支。第一版报告里那个
「生成 `int64_t` 去接一个 Python list」的静默错型，现在被显式 fail-closed 堵住了
（`_attr_type` 里那段 `if isinstance(default, list): raise`）。

分流**只看值结构、不看算子身份**，符合仓规 §5.1：任何声明了 `list[int]` 属性的算子零改即用。

### D · dtype 受控词表仍然拒绝数组写法（这是设计，不是遗漏）

```
dtype=['int_array']   -> 拒: attr 'shifts' dtype 须为单值 ['bool','float32','float64','int32','int64']
dtype=['int64_array'] -> 拒: 同上
dtype=['aclIntArray'] -> 拒: 同上
dtype=['list[int]']   -> 拒: 同上
dtype=['int64[]']     -> 拒: 同上
```

第一版把这条当成「作者没有第二个选项」的证据——**那个推论错了**。
正确的写法是 `dtype: ["int64"] + default: [k, ...]`；报错信息本身也把这条写进去了
（`（数组属性请给非空 list[int] 的 default → int_array）`）。刻意不新增 `int64[]` 这类 dtype，
是为了让 `gen_cases._attr_ctype`（按 per-case 取值判）与 codegen（按 spec `default` 判）
用**同一套判据**得出同一个答案。

### E · extended stage2 + ND 张量格式下，数组槽照样对

同一份 spec 加 `"aclnn_tensor_format": "nd"` + `stage2_form: "extended"` 再生成：

```
std::vector<at::Tensor> invoke_v0(const at::Tensor& x, at::IntArrayRef shifts, at::IntArrayRef dims, const at::Tensor& out)
auto converted_params = std::make_tuple(
    OprunwayConvertNdTensor(x),
    ConvertType(shifts),          ← 数组槽走官方 ConvertType
    ConvertType(dims),
    OprunwayConvertNdTensor(out),
    workspace_size_addr, executor_addr);
m.def("invoke_v0(Tensor x, int[] shifts, int[] dims, Tensor out) -> Tensor[]");
manifest.variants[0].dispatch = generated_extended_two_stage
manifest.variants[0].stage2_call_arity = 8
```

两种派发形态下数组槽的 C++ 类型与 schema 类型完全一致。

## `aclnn_py` 那半句：**现在也不属实了**

第一版记的 `"*" in tok` fail-closed 仍在（`aclnn_runner.py:321`），但它**前面**多了一道
`aclIntArray` 的放行分支（`:301-306`，正则 `_INT_ARRAY_PARAM_RE`，`:265`）：

```
'const aclTensor* x'        -> {'name':'x','role':'in','ctype':'tensor','const':True}
'const aclIntArray* shifts' -> {'name':'shifts','role':'attr','ctype':'int_array'}
'const aclIntArray* dims'   -> {'name':'dims','role':'attr','ctype':'int_array'}
'aclTensor* out'            -> {'name':'out','role':'out','ctype':'tensor','const':False}
```

整份 `aclnnRollGetWorkspaceSize` 过 `parse_aclnn_signature`（`:446`）也成功：
`op_name='Roll'`、四个 params 如上、`stage2_form='standard'`。

放开的范围**很窄，且仍据 C 类型而非算子名**——旁证：

```
'const aclFloatArray* w'  -> AclnnRunnerError: 是指针/数组形态（非 aclTensor/aclScalar）——域外接口能力，fail-closed
'const aclIntArray** bad' -> AclnnRunnerError: 含 aclIntArray 但不是 `(const) aclIntArray *<name>` 形态——fail-closed
'aclTensorList* t'        -> AclnnRunnerError: aclTensorList 属域外接口形态，fail-closed
```

marshal 侧：`_ATTR_CTYPES`（`:590`）仍只有 `['bool','float32','float64','int64']`——
**这是对的**，`int_array` 不是值传递标量，它走另一条分支：`(c_int64 * n)` 缓冲 →
`aclCreateIntArray` → 按 `c_void_p` 传，并与 tensor / scalar 在**同一个 finally** 里
`aclDestroyIntArray`（`:1581-1614`、`:1401-1403`）。

## 仍然存在的一条缝（如实记账，本步不改）

**codegen 按 spec `default` 判数组性，`gen_cases` 按 per-case 取值判**，两者在
`default` 与实际取值的值结构不同时会分岔。举例：`default: 1`（标量）但
`attr_matrix` 给 `shifts: [1, 2]` ——

- codegen → `int64_t shifts` / schema `int`（C 节实测）；
- `gen_cases._attr_ctype(p, [1,2])` → `'int_array'`（I 节实测）；
- `cpp_extension_adapter.build_invocation_plan:88` **只校 role/name 与变体匹配，不校 ctype**，
  manifest 里也没有逐 attr 的 ctype 可供对照（实测 manifest 的 `variants[]` 只有
  `active_attrs` 名单）。

这条缝在 `aclIntArray` 场景下会先被 CP-C0 撞掉（签名说 `int_array`、slot 按 `default` 算成
`int64` → 对账拒）。真正没人拦的是「签名本身就是标量 `int64_t`、而 spec 给了 list 取值」——
🟡 **推断**：那种情况会在真机上被 torch schema 拒成 `TypeError`（**fail-loud，不是假 PASS**），
但**本轮没有实测**，因为需要真机 build（仓规 §5.3，本地不跑 compute）。
建议做步骤 6（spec 变更门）或步骤 7 时顺手把 attr ctype 也纳入 invocation-plan 的对账。
