## 4. 三个可行方案，按两个维度切

收缩后真正的分歧只有两处：**判据与裁决代码住哪儿**，**harness 交付到哪儿**。

| | 甲 · 扩 BLAS + overlay 交付 | 乙 · 新起 solver + 现场交付 | 丙 · 新起 solver + overlay 交付 |
| --- | --- | --- | --- |
| 我们写 | frame + per-op harness + **扩 CSV 列模型** + golden | 执行器 + golden + 族级裁决 + 采集 | 同乙，产物装进检出 |
| 复用 | blas 的 A1–A5 全链、六件包契约、msprof | A1、A5 证据布局、`perf_harness` | 同乙，另借 `build.sh` 编译 |
| 主要代价 | **动既有线的用例模型**，回归门要先升级 | 第三套运行与裁决代码 | 多一层装/preflight/回滚 |
| 主要风险 | 族级不可拆 vs「一包一 CSV」定义冲突；L1 缺口仍在 | 长成复制既有线 | 跟 ops-solver 结构变化走 |

**丁 · 接 ATK 线**：要新写 handle C API 后端、改输入表示与比较器，还要背上不适用的阶段。
v1 评审给 19/45，v2 不再把它当主候选，但若有翻案理由请指出。

**无 frame 时，甲的 overlay 与丙的 overlay 都要自带驱动/golden/比较**，也就是说三个方案
我们都写全套；差别在代码住哪个 skill、产物落哪里。

## 5. 当前倾向：乙

三条理由，都不依赖已被订正掉的那五条：

1. **甲要动既有线的用例模型**，而 BLAS 与 sparse 两个域正在用它。爆炸半径最大的不是新写
   代码，是改别人正在跑的东西。
2. **丙比乙只省编译链配置**，却换来 overlay 的装/回滚/preflight 一整套，还要跟 ops-solver
   的结构变化；而 `build.sh --run` 三步不传参只跑默认 shape，要传参就得绕过它，借到的有限。
3. **乙的边界最稳**：只依赖公开头 `cann_ops_solver.h` 与可链接的 `libops_solver.so`。

**请把这三条也当作待反驳的假设。** 尤其第 2 条——若 CANN 编译链自配的成本被低估，丙会反超。
