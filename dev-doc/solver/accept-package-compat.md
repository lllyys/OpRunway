# accept 与任务包的兼容设计记要

背景（Mr.0 2026-09-23）：任务包今日交付开发者后**不可再更改**，而阈值裁定（T3/T4/
T7/T8）、期望集、accept 实现都会继续演进。本记要回答：accept 如何在包冻结的前提下
高效兼容。

## 五条机制

1. **判定参数不在包的裁决面上**。包内 verify 双件只是自测辅助件；判定标准、执行、
   结论出具全在 accept 的 `criteria/`（裁决主权，设计 v2 3.3）。**阈值语义此后任何
   裁定，改 accept 一处即可，包零改动。**
2. **manifest 版本三元组 + 支持区间**。包记 `package_ver / criteria_ver /
   renderer_ver`；accept 声明支持区间并写进报告。旧包遇新 criteria 只触发「副本
   漂移」告警（数据错配才阻断），验收照常以权威实现计算。
3. **期望集独立于包**。accept 从任务书生成七类期望集，先于结果存在。batched 留空
   （Mr.0 裁定）不改变期望项——它恒在、状态为证据不足；标准补章后**另发 batched
   新包**即追加证据，旧包不动，族级在聚合层合流。
4. **accept 依赖的契约面收窄为三样**：`cases/index.json` 条目字段、npz 数组名与
   dtype 映射（实/复共用字段名）、被测输出三键（`out32/info/status`）。包内其余
   内容（README、gen_data、sim、canonical 切片）对 accept 透明，怎么演进都不破坏
   兼容。
5. **逐包判定与族级聚合分离**。每包出独立 report，可单独复算；族级结论只在聚合层
   由期望集驱动。后补包、重测包都是聚合层的增量输入。

## 交付不可改的残留风险与缓解

唯一实质风险：包内 verify 副本嵌的是**当前**阈值参数，若最终裁定不同，开发者自测
视角与验收会出现差异。缓解已内置：README 与报告都写明 `formal` 恒为
`PENDING_RULING`、验收以 accept 侧为准；裁定落地时向开发者发**阈值裁定通知**
（一页说明），不改包。

## 演进钩子

数据形态转流式（不落盘裁定）只动包的生成与自测通路，不动上述三样契约面；复数、
后续算子族按同一 manifest/期望集机制并入，accept 不需要针对某个包做特判。
