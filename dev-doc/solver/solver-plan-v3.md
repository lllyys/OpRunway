# 0923 验收实施计划 v3

v1（`solver-route-decision-packet.md`）与 v2（`solver-route-plan-v2.md`）是选型文档，都已评审。
**选型已收敛，本文不再比选，写的是怎么开工。** 两轮评审见 Codex thread `01a0c318`。

## 1. 结论，以及它有多强

**方案：乙——新起 `repo-task-solver-accept`，调用器自产并留在验收现场。**

第二轮八维重评：乙 34 / 丙 33 / 甲 30 / 戊 27 / 己 26 / 丁 19（满分 45，复杂度双权重）。

**这是窄幅领先，不是定论。** 评审原话：「34 对 33 是当前证据下的窄幅推荐，不是已经实测
成立的成本优势。」第一轮支持乙的三条理由——L2 物理量不一致、无参考耗时、入口不能传采样
次数——**全部已被订正掉**，第一轮那个 34 分不能当本轮结论的证据。

现在撑住乙的只有两条：

1. 0923 需要新的采样归因、内存观测与族级完整性裁决，这些能力不能直接从 BLAS 全链取得。
2. 独立调用器隔离了测试构建图对被测库的影响——这不是假想：`test/cheevj/CMakeLists.txt`
   会改被测库源码的编译选项并给库加 `omp` 链接，所以「只新增文件」不等于「被测物构建
   语义不变」。

**两条翻案条件（评审给定，逐字保留）：**

- **改判丙**：目标环境证明仓外 caller 必须复制大量、持续变化的私有构建配置，而 overlay
  能通过稳定入口构建并证明不改变被测库的编译链接语义。
- **改判甲**：一个最小 S-LU 实现证明现有 schema 不需变更，新增采样能力与族级门可通过小
  范围通用扩展完成，BLAS/sparse 旧行为保持，且明显少于乙的新编排代码。

所以**第一步不是建 skill，是把这场三分之差变成实测**（见第 4 节 P0）。

## 2. 术语

用语定义与三档命名以
[accept-line-adoption-method.md](../accept-line-adoption-method.md) 第 3.2 节为准，本文只取结论：

- **harness 含 golden**，所以「自产 harness」意味着 golden 也自产；要单指不含 golden 的
  那半才说「调用器」。
- **overlay 是交付形态不是东西**，它装的是 harness 加用例数据加安装语义。
- 三档是 **① 消费开发者的 / ② 自产·overlay 交付 / ③ 自产·现场交付**，本计划选 **③**。

②③ 的 harness 内容是同一回事，差别只在交付形态。**harness-gen 的生成层设计在 ③ 下仍可借，
但它现成的实现用不上**——支持矩阵限 FACTS schema v1、`golden.kind=cblas`、不支持复数与
nullable，且要绑一份目标工程兼容配置，solver 四条全不满足。

## 4. 分期（按评审修正）

**P0 · 判据澄清与实测立据**（部分与选型无关，可立即开）

1. 提取任务要求、建接口与必测项清单；澄清 `1e-2 or 32·ULP` 的选择与 ULP 参照值。
   **不冻结任何一条线的 CSV、结果 JSON 或打包协议。**
2. 三类数学判据（与 golden 逐元素比 / 自洽重构 / 恒等式）各做一个原型，先固定输入输出
   语义。golden 实数 float64、复数 complex128。
3. **`n=32` 按待定处理，不自行裁定。** 任务书明确要求它合法并列入 P-12；旧头文件与 bench
   只到 31 不能推翻任务书。要核的是任务方是否打算修订，以及开发者如何提供对应 A100 结果。
4. **构建与采样验证（这一步定乙还是丙）**：在授权目标环境，用目标版本头文件与库证明仓外
   调用器能编译、加载、调用；再证明 trace 能区分准备、恢复、预热与正式调用。
5. 并行发起 A100 性能与 workspace 证据请求——不阻塞建工具，但阻塞正式性能与部分内存结论。

**P1 · 完整 S-LU 族，族级门从第一期就在**

- `Sgetrs` 是**第一个技术切片**，不是「一族闭环」：它验依赖链、`trans/nrhs`、`info`，
  **没验**批量指针数组、求逆、全部内存门，也没覆盖复数。
- 第一期的结束条件是**完整 S-LU 族**。族级门必须此期就存在：先让缺项正确返回「证据不足」，
  再逐项填满。**不能第二期才补聚合**——现有性能期望集依赖基线匹配、无基线行会被排除，
  沿用那种构造会把「必测项缺证据」变成「未进入本次比较」。

**P2 · 铺开其余五族**，含复数全族与 `Xgeev`（无任务书，不出正式结论）。

## 5. 硬边界：违反即重新评估方案

评审给定的十二条，每条都要落进 skill 的 `scripts/` 与 `tests/`，不是人工清单。

| 硬边界 | 怎么机械发现被违反 |
| --- | --- |
| 裁决实现只在发布 skill 内，仓外只放运行产物 | 在仅含发布切片的环境跑完整命令；缺 `dev-doc/`、`repos/` 即无法运行则不合格 |
| 调用器不改被测源码、公开头与测试树；被测库在任务自有现场构建 | 执行前后对既有文件做内容清单差分；**不能只查 tracked 文件而漏掉被覆盖的未跟踪文件** |
| 被测身份明确，不能「链接成功就算目标正确」 | 记录目标 revision、头文件、实际加载库、CANN 与设备信息；用错版本库的负例必须被拒 |
| 所有接口走同一生命周期与采样引擎 | adapter 只暴露准备/恢复/调用/取结果；契约测试验证统一的调用次数与顺序；时间戳、median 与 verdict 只能由公共入口产生 |
| 每次预热与采样都从规定输入开始；准备失败不得归罪后续接口 | 用会原地改写输入的假被测实现逐次检查恢复；注入 getrf 准备失败须停止对应 getrs 测量 |
| 每个样本只含目标调用的 kernel，不得以总和除次数代替 | 保存样本到原始 trace 的关联；加入准备、恢复、预热 kernel 的测试 trace，结果必须不变 |
| 预热、采样与内存复用符合任务书 | 记录 ≥10 次成功预热、30 次正式样本与 workspace/指针数组生命周期；跨进程重建、预热失败、样本不足、采样中重新分配均不得正式通过 |
| 数值判据来自任务书，既有残差 token 不得隐式替代 | 固定判据测试：匹配率达标但最大误差超限、仅虚部错、合法不同 pivot/相位、错三角、错 `info`；未澄清阈值不得临时选 |
| 族级期望集先于结果与基线存在 | 从固定任务清单生成必测集合；分别删一个接口、一条 P case、一项 bufferSize/内存证据，结果均不得为通过 |
| 参考耗时与门禁基线分开 | 正式比较要求每条 P case 的完整参数、A100 来源、采样协议与版本；仅有 min/max/avg 的输入只能停在摸底态，**不得改变必测集合** |
| 内存门有实际观测，不只查 runner 自己申请的 workspace | 观测须覆盖库内分配；用隐藏分配与泄漏的假库验证检测能力；100 次生命周期在同一进程内检查 |
| 复用有明确接口；改公共件须证明旧行为仍成立 | 列出复用模块与发布依赖；改公共代码前固定受影响 BLAS/sparse 的回归样本；出现完整 A1/A5 副本或旧结果漂移即触发重评 |

这些门防的是**无意测错、漏测与错判**。不做签名、不可篡改日志、层层确认，也不做「全仓
revision 一变就拒绝运行」。

## 6. 请复核什么

选型不再重问。本轮要的是**可开工性**：

1. 第 3 节那九条回调，有没有回调错或回调不足的。
2. 第 4 节的分期：P0 五项是否都真的不依赖选型；P1 以「完整 S-LU 族 + 族级门」为终止条件
   是否可达，还是仍然过大。
3. 第 5 节十二条边界：**有没有彼此冲突的、有没有实际不可机械判定的、有没有缺的。**
   特别是「每个样本只含目标调用的 kernel」在 msprof 的实际输出下能否做到。
4. 按这份计划，**P0 做完是否足以把乙/丙之间那三分之差判定下来**；如果不够，缺哪一项证据。
5. 本文有没有把「窄幅推荐」当成「已定论」来写——这是我们最担心的失真方向。
