## 0. 术语

| 词 | 含义 |
| --- | --- |
| 判据卡 | 一类算子角色的判定参数集：直审目标、比对公式、阈值、预处理标记 |
| 接口卡 | 调用器引擎的每接口差异面：API 名、依赖链准备段、契约限制 |
| 还原目标 | 解不唯一算子第一层比对的对象（如 P·L·U vs A），由任务书定 |
| 族级期望集 | 从任务书生成、先于结果存在的一族必测清单（接口、P 项、bufferSize、内存证据） |
| 环境门 | accept 开始前对 CANN 版本、设备、被测身份、包完整性的检查 |
| 包指纹 | manifest 里记录的包内容摘要，用于发现数据错配与旧包混入 |
| P-xx | 任务书性能必测项编号（0923 共 12 条，P-12 即 n=32 那条） |
| S-LU | 单精度实数 LU 族（sgetrf/sgetrs/sgetriBatched/smatinvBatched） |
| 冻结三档 | 精度参考工程的数据落盘分类（golden 依赖什么就冻什么），与交付档②③无关 |
| 三层判定 | solver 精度标准结构：还原/真值直审（混合容差双门）→ 不满足 → LAPACK ε 归一化残差兜底终审 |

## 1. 环节全景

| # | 环节 | 执行者 | 输入 | 产物 | 流向 |
| --- | --- | --- | --- | --- | --- |
| E1 | 发布素材 | 任务发布者 | — | 任务书、cases.json、竞品 cu、bench_result.json（可缺） | → E2 |
| E2 | 生成任务包 | 发布者运行 case-gen | E1 | 任务包（第 2 节） | → E3、E4 |
| E3 | 开发与自测 | 开发者 | 任务包 | 算子代码 + 自测记录 | → E4 |
| E4 | 验收 | 验收者运行 accept | 任务包 + 开发者代码 + 目标机 | 验收报告 | → 发布者 |

任务包是两 skill 唯一的**运行数据**交界；此外存在一条**发布依赖**：case-gen 渲染自测
副本时消费 accept 的 `criteria/`（见 3.3）。开发者自测与验收共享同一份输入与同源判据
副本，**作用是收窄排查范围**——自测过而验收挂时，差异来源限于环境、版本、副本漂移、
采样波动或覆盖缺项，不承诺「必是环境问题」。

## 2. 任务包契约（case-gen 产物，一算子一包）

包内容按类列举（类数不要求对应顶层文件数）：

| 类 | 内容 | 形态 |
| --- | --- | --- |
| `gen_data.py` | 数据构造脚本：转写竞品 cu 的合法输入构造逻辑，显式 seed，落盘 | python，零参可跑 |
| `cases/` | 预生成数据集：case 标识、参数、dtype、内存布局、有效比较区域、输入与 golden 的对应关系逐 case 记录 | npz/bin + 清单 |
| `golden/` | CPU 高精度参考输出（scipy/numpy，实 float64 复 complex128），由发布者运行 `gen_data.py` 一并产出随包 | 随包落盘 |
| `ratio_cpu 基线` | 逐 case 的 CPU FP32 同精度链路残差比（兜底判据的阈值参数），与数据同源实测随包冻结 | 数据 |
| `harness` | 调用器：一份引擎 + 接口卡；区分「构建被测库」（任务自有 checkout）与「编译调用器」两步，记录目标 revision、公开头、实际加载库 | C 源 + 构建脚本 |
| `verify_accuracy.py` | 精度自测辅助件（accept criteria 的渲染副本，见 3.3）：三层判定——直审（混合容差双门）→ 兜底（LAPACK 残差）；输出不构成验收证据 | python |
| `verify_perf.py` | 性能自测辅助件（同为渲染副本）：**判据数据逐 case 从 `perf_baseline` 取 bench_result 对应条目**（按 n/batch/lda/uplo 等参数精确匹配），输出逐项比值与参考性提示；受 T1 运行语义约束，正式性能裁决仍在 accept | python |
| `perf_baseline` | bench_result.json 的逐 case 摘录 + P-xx 表；case-gen 生成时完成参数匹配与去重（cases.json 实测有重复行），**无对应条目的 case 标记性能证据不足**；bench_result 整体缺失时精度包照常生成 | 数据 |
| `README` | 面向开发者：自测命令、输出位置、辅助结论含义。不含正式报告模板 | 文档 |
| `manifest` | 算子、接口清单、seed、criteria 版本、渲染格式版本、包指纹 | JSON |

要点（**2026-09-23 数据形态修订**，Mr.0 裁定「不落盘」）：cases/golden 等大数据
不随包落盘——包内只有生成脚本（显式 seed）、canonical 清单与 KB 级小表（perf_baseline、
ratio_cpu 参考）；测试流式进行：逐 case 现场生成→喂被测→判定→丢弃，只留判定记录。
确定性由「seed + manifest 环境版本记录 + 生成与判定同进程闭环」保证，字节冻结仅保留
给小表与抽验样本（原「golden 随包冻结」条款对大数据段作废）。精度与性能同输入
（默认集合关系见 T2）；调用器不做竞品那种 27 份骨架复制。

## 3. 两个 skill 的契约

### 3.1 `repo-task-solver-case-gen`

输入 = 任务书 + cases.json + 竞品 cu + bench_result（可缺）。输出 = 任务包。
步骤：解析 cu 构造逻辑 → 转写 `gen_data.py` → 生成数据与 golden → 装配调用器与
自测副本 → 渲染 README/manifest → 自检（同一渲染入口复渲相等 + golden 抽验：抽验对象
是随机抽取 case 的 golden 与独立重算值的一致性）。

### 3.2 `repo-task-solver-accept`

输入 = 任务包 + 开发者代码 + 目标机。输出 = 验收报告。

- **族级期望集先于结果存在**：accept 从任务书生成一族的必测清单（接口、P 项、
  bufferSize、内存证据），聚合以期望集为准——包或接口漏交表现为期望集上的
  「证据不足」，不是「不在范围」。
- 流程：环境门 → 构建装载被测（任务自有 checkout；隔离测试构建图**且**做构建前后
  内容清单差分，两者互补不互替）→ 逐接口精度 → 性能采样比对 → 内存门（库内分配
  观测与同进程生命周期证据，承载硬边界 11，落地在 S4）→ 族级聚合 → 报告。
- **复测语义**：每次复测是独立运行记录，正式结论取自单次完整运行；不同代码、输入或
  判据版本的结果不隐式拼接；无效轮跳过并告警（沿 2026-09-17 先例，不做防篡改链）。
- **报告归 accept**：正式报告模板与聚合规则在 accept 内，包内 README 不承载。

### 3.3 裁决主权与版本参照（Mr.0 裁定，2026-09-23）

**判定标准、判定执行、裁决三件全部在 accept skill 侧。** 三条规则：

1. accept 用自带判据独立计算正式结论；包内脚本可参与造数、构建、采集，
   **不提供被直接采信的通过结论**。
2. 自测副本（`verify_accuracy.py` 与 `verify_perf.py` 两个，精度性能各一）漂移只告警
   入报告，不升级为任务硬失败。
3. 数据错配、被测身份错误、必要证据缺失仍阻断**相应**正式结论——这三类伤害善意
   使用者，不属于可退级防护。

机制：判据内核（精度：阈值表 + 判据卡 + 比对实现；性能：采样协议 + 基线比较规则）
住 accept `criteria/`。精度判据结构即 **`repos/solver_tasks-main` 的三层判定——它就是
solver 标准**（Mr.0 2026-09-23；其文中「开源生态标准/现行标准」的指涉一律代换为
最新 `mixed_tolerance_standard.md`，原引 experimental 版已 404）：还原/真值直审（逐元素按混合容差双门）→ 不满足 →
LAPACK ε 归一化残差兜底终审，兜底默认启用。实现件同源移植：还原目标构造（P·L·U、
Q·R、F·Fᴴ vs A）、ipiv 正序回放、复数 golden z 前缀、半三角范数口径、冻结三档、
各族 verdict 脚本。**兜底阈值依赖逐 case 的 ratio_cpu 基线**（CPU 同精度 FP32 参考
链路、同 case 同输入实测；标准工程原文：NPU 验收时由 CPU 参考预先算出），由
case-gen 随包产出。case-gen 经
**同一个确定性渲染入口**产出包内副本（两侧不各自实现）；manifest 记录生成时的
criteria 版本与渲染格式版本；accept 对版本支持范围显式判断，报告记录实际裁决版本，
v1 不建历史版本兼容框架。副本核对的意义是**发现漂移**，不是证明判据正确——判据
正确性靠 `criteria/` 的固定正反例测试（含「匹配率达标但最大误差超限」这类双门用例）。

## 4. 已定与未定

已定（七点 + 2026-09-23 裁定）：

- 任务包由我们提供，case-gen 先行；调用点（测试脚本）归 case-gen。
- **精度标准 = solver_tasks-main 的三层判定（solver 专用标准；Mr.0 2026-09-23 裁定：
  原混合容差标准不完全适用 solver）**：第一层还原/真值直审，逐元素判按最新混合容差
  标准（matched_ratio 与 max_abs 双门）；不满足走 LAPACK ε 归一化残差兜底终审，
  兜底默认启用。golden = numpy/scipy CPU；还原目标由任务书与标准工程定。

- 裁决主权三件在 accept 侧（3.3）。
- **T6 已裁（Mr.0，2026-09-23）：v1 不统一仓测试**；复议条件：开发者普遍照抄包件改
  仓测试，或仓判据与验收判据差异实际引发争议。

## 5. 打通计划：薄垂直切片

一个算子走全环节，模拟开发者用仓上既有 `cmatinv_batched` 充当「开发者返回的代码」。
既有 E2E 实测的证据范围限定：**证明了仓外调用器在 950PR 可编译加载调用、精度双判据
可行**；用的是自选规格（batch 远小于任务 cases），未证明可直接消费完整任务包。

| 期 | 内容 | 完成条件（可机械判定） |
| --- | --- | --- |
| S0 | 设计评审与处置 | 第 8 节处置表每项有落点；未裁定项运行语义成文（第 4 节） |
| S1 | **最小判据内核（criteria）+ 共享渲染入口** + case-gen 骨架 + 首包 | 包自检过；`gen_data.py` 重跑数组内容逐位一致（复现界定为数组内容，非容器文件字节）；criteria 正反例全过 |
| S2 | 模拟开发者自测 | 无口头指导，仅凭包内 README 走通；记录前置、命令、退出码；**注入一个错误输出，自测必须不通过** |
| S3 | accept 骨架 + 对首包验收 | 仅含发布切片的环境独立跑通；错误版本库被拒；期望集删一项→不得通过；无合规基线→无正式性能通过；副本漂移→仅告警 |
| S4 | 复盘 → 铺完整 S-LU 族 + 内存门 | 工具对全族每项输出裁决或证据不足；**工具覆盖完整 ≠ 算子族正式通过**，接口未交付或基线未补时如实报证据不足 |

S2 检验的是包对**开发者**的冷读可用性；验收零上下文（accept 侧）由 S3 的
「发布切片独立跑通」单独检验，两者不互相替代。

## 6. 开发者仓内测试与任务包的关系

现状（`repos/ops-solver` 本地 clone）：六算子测试，一算子一目录五件套——CMakeLists
（链 `${OPS_SOLVER}`）、`<op>_test.cpp`（读 bin 调算子写 bin，无判据无计时）、
`data/gen_data.py`（getrf 族 seed=149、其余 42，产输入与 golden）、
`data/verify_result.py`（逐元素 allclose + error_ratio，无 matched_ratio 与 max_abs
双门，阈值与比较对象均与混合容差标准不同）、README（`bash build.sh --ops=<op> --run`）。

三条定位：

1. 验收判据的标准、执行与裁决都在 accept 侧（3.3）；包内两个 verify 是自测辅助件，
   开发者仓内 `verify_result.py` 更不作为验收证据（隐式替代即违硬边界 8）。
2. 自测用包、仓测试归仓：开发者提交进 ops-solver 的 test/ 服务代码仓自身回归，
   属维护者域，与验收解耦（Mr.0：仓里的自测代码可以是另外的）。
3. accept 防线：隔离测试构建图**且**内容清单差分（互补，见 3.2；机器侧 cheevj 的
   test CMake 改被测库编译选项是实证先例）。

是否额外渲染仓测试骨架（原 T6）已裁定 v1 不做，理由与复议条件见第 4 节。
