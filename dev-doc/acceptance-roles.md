# 社区算子任务的五个角色

一次社区算子任务从发布到验收，有五个角色。本文只定义角色、各自的产物与信任级别，
以及同一件 skill 落在不同角色手里时的用法差异。具体的接线方法见
[accept-line-adoption-method.md](accept-line-adoption-method.md)。

**为什么要先分角色：** 同一件 skill 在不同角色手里，输入、输出和可信级别都不同。
不分角色谈「用 case-gen」会漏掉最要紧的一点——它的产物在 BLAS 线上是**一件供两边消费的
契约交换格式**：发布者产它、开发者照它开发、验收者直接验它，根本不存在「验收者再产一次」
这一步。只有发布者没用它时，验收者才退而自己补一份。两种模型的差别见第四节。

## 一、五个角色

| 角色 | 是谁 | 拿到什么 | 交出什么 | 可能用的 skill |
| --- | --- | --- | --- | --- |
| **任务发布者** | 社区任务的出题方 | —— | 任务书、性能 case，可能有精度 case 与脚本 | doc-write、case-gen |
| **代码仓维护者** | 目标算子仓的 owner | 各方的 PR | 合入裁决，仓的形态与约定 | —— |
| **开发者** | 接任务的社区贡献者 | 发布者的全部材料 | PR、自测报告、自测用例与测试代码 | 不用本仓 skill |
| **验收者** | 判这个算子能不能收的人 | 前两者的全部产物 | 验收证据与结论 | case-gen、harness-gen、accept |
| **skill 构建者** | 建 skill 与 agent 的人 | —— | skill、agent、机械门 | —— |

五个角色的边界说明：

- **任务发布者**在任务书里记明目标代码仓（0923 是 `gitcode.com/cann/ops-solver`），
  性能 case 一般随包发；精度 case 与配套脚本给不给不一定——BLAS 线的六件套是给全的形态，
  0923 是只给性能、精度为零的形态。
- **代码仓维护者**是唯一能改仓的角色，详见下一节。
- **开发者**拿到的就是发布者公开的那一份，不多不少。交付物按任务书列：PR、设计文档、
  自测报告、自测用例及测试代码、待验收代码地址。**他也改不了仓**，只能提 PR。
- **验收者**拿得到前两者的全部产物，但**拿得到不等于可用**——这是后面两节的主题。
- **skill 构建者**就是本仓（OpRunway）承担的角色。它**不做真实验收**，而是模拟验收者去跑
  这些 skill，再按模拟结果改造它们——这层关系见第八节。

## 二、改仓的权限：只有维护者有

**除代码仓维护者外，没有任何角色能改目标仓。** 要改就得提申请走合入，成本高、周期不由
我们控制。

**非必要不推动。** 这不是礼貌问题，是成本问题：一次上游改动要排队、要评审、要等合入，
而验收有它自己的节奏，两者对不上。

由此，「要动仓里的东西」这句话必须拆成三种，它们的权限完全不同：

| 做法 | 动了什么 | 谁能做 | 成本 |
| --- | --- | --- | --- |
| **改上游仓** | 仓的既有文件或基础设施 | 只有维护者（他人提 PR 等合入） | 高，且不由我们控制 |
| **往检出里追加**（overlay） | 只加文件，不碰既有文件，可整体回滚 | 验收者自己 | 低 |
| **完全在自己现场** | 什么都不碰 | 验收者自己 | 低，但环境自理 |

第一行与后两行的区别是**改的是仓还是工作副本**。overlay 装进开发者的工程检出，装完可回滚，
不经过维护者——把它说成「改目标仓」是混了这条线。

**方案里凡是依赖第一行的，都不是我们能单方面执行的选项**，只能作为「建议上游做」提出来，
不能写进验收通路的前置条件。0923 上一个现成例子：「给 ops-solver 补一套 test frame」听起来
是条路，实际要维护者合入，所以它不是候选方案，是一条上游建议。

判 overlay 可不可行，看的是**仓的测试注册机不机械**：ops-solver 的 `test/CMakeLists.txt`
是 `foreach(TEST_NAME ${TEST_NAMES})` 加 `add_subdirectory`，目录存在就收，`TEST_NAMES`
由 `build.sh` 从 `--ops` 传入（`build.sh:179-180`）——**追加目录不需要改任何既有文件**，
所以 overlay 在这个仓机械可行。

### 维护者是按仓分的，不是一个

ops-blas、ops-sparse、ops-solver 各有各的维护者，约定各自演进。三条推论：

- **「BLAS 线能行」不构成「solver 也能行」的理由。** 两个仓的测试形态差那么远，不是同一批
  人前后不一致，是本来就由不同的人在管。拿一个仓的现状去推断另一个仓，会推错。
- **推动上游是逐仓谈的。** 一个仓接受了某个约定，不给另一个仓任何承诺；成本要按仓分别估，
  不能合并成一句「推动上游」。
- **registry 的 profile 实际绑的是仓，不是域。** `entry_headers`、`build_device_flag`、
  `runtime_library_dirs` 这些全是仓的事实，而仓会被它的维护者改——ops-blas 的 frame 面
  两个月内动过六次。所以 profile 必须记出处与基线 commit（sparse 那档注的是
  `ops-sparse@5b2a5ba`），**没有基线的 profile 是一句会过期而不自知的断言**。

## 三、产物的三种身份

角色决定产物的身份，身份决定它能不能当证据用。**这是整篇最要紧的一条。**

| 产物来源 | 身份 | 能不能当验收证据 |
| --- | --- | --- |
| 任务发布者 | **判据权威 + 待核数据** | 判据必须遵守；数据必须先核出处与口径 |
| 开发者 | **被测物** | **不能**——PR、harness、自测报告全是被测的东西 |
| 验收者 | **证据与裁决** | 是，且只有它是 |

一句话：**判据来自发布者，被测物来自开发者，证据只能来自验收者。**

由此推出两条平时容易含糊的：

**开发者的自测报告不是验收证据。** 任务书把「自测用例及测试代码」列为交付件，意思是
它要被验收，不是它来验收。

但**「是被测物」不等于「不能用」**。身份决定它需要被核，不决定核完之后能不能拿来跑。
这两件事要分开，否则会得出「开发者交的一律不用」这种与 BLAS 实况相反的结论。

### 开发者的 harness 能不能用，是目标仓的属性

BLAS 线的实况是：开发者交的 harness **直接可用，验收者不必再生成**。原因不在开发者自觉，
在 ops-blas 的仓强制：

- `test/frame/` 有九个共享头（`csv_loader.h`、`verify.h`、`fill.h`、`device.h`、
  `blas_test.h`、`test_main.cpp` 等），驱动、读 CSV、比对全在仓里，不由算子作者重写。
- 形态被钉死：70 个算子目录下有 69 个 `<op>_param.h`、74 张 `<op>_test.csv`、
  99 个 `<op>_test.cpp`（按 `arch22`/`arch35` 分档）。
- 开发者只填 per-op 的三件加一个 `<op>_golden.h`，而 golden 的实质常常就一行——
  `asum/sasum/sasum_golden.h` 共 36 行，核心是 `cblas_sasum(n, x, incx)`。

**规律的来源是仓的 frame，不是开发者。** 仓有 frame，每个开发者交出来的形状就一样；
仓没有 frame（ops-solver 无 GTest、无 `csv_loader.h`、全仓无 `.csv`），各人就各写各的。

由此「开发者的 harness 能用到哪一步」拆成两条互不相干的轴：

| 轴 | 决定什么 | 判据 | ops-blas | ops-solver |
| --- | --- | --- | --- | --- |
| **仓的 frame 强度** | 调用器能不能直接用 | 仓里有没有强制形态的共享件 | 强 | 无 |
| **golden 的可审性** | 判据器能不能直接用 | 那份 golden 人能不能一眼审完 | 一行 `cblas_*` | 判法可任选，难审 |

两轴都强就是消费自带（BLAS 的现状），两轴都弱就得自产（solver 的处境）。三档的定义见
[accept-line-adoption-method.md](accept-line-adoption-method.md) 第 3.2 节。

**所以「被测物不能当量具」是按域成立的判断，不是无条件的禁令。** BLAS 能消费开发者的
golden，是因为它一行就能审完，不是因为原则让了步。

**发布者的数据是权威但不可靠的。** 判据章节说了算，但随包的基线数据该核还得核。
0923 的性能门禁写 A100，而 27 份 `bench_result.json` 无一记录 GPU 型号、驱动或 CUDA 版本，
只有两份改动报告提到 H100——**结论只能是「逐结果来源无法建立」**。权威的是那句
「`T_NPU ≤ T_A100 / 0.8`」，不是那批数。

## 四、同一件 skill，两个角色，两种用法

| skill | 在任务发布者手里 | 在验收者手里 |
| --- | --- | --- |
| **doc-write** | 写任务书，定判据与交付契约 | **不用**——只能读，有问题走上游反馈 |
| **case-gen** | 产六件任务包，交给开发者 | **直接验它**；上游没产时才自己补 |
| **harness-gen** | 一般不用 | 开发者的 harness 不可用时补一套调用器 |
| **accept** | 不用 | 唯一使用者 |

**doc-write 在验收者手里是空的**：不改任务书，发现缺陷只能提 issue 或 PR 回上游，
改得动下一批，改不动当期。case-gen 那一格则要分两种模型说。

### 同源模型：case-gen 的产物同时是交付件和验收输入

BLAS 线里**不存在「验收者再产一次用例」这回事**——不是省了这一步，是设计上就不需要。
六件任务包是生成侧与验收侧之间的**唯一交界**，契约写死在
`plugin/docs/development/blas-case-package-contract.md`：

| 文件 | 验收侧怎么用 |
| --- | --- |
| `<op>_test.csv` | 部署，构造精度集与性能集 |
| `gpu_baseline.csv` | 性能脚本匹配基线并标 scope caveat |
| `gen_csv.py` | 读 FACTS，核生成器版本与通用区哈希 |
| `README.md` | A2′ 人工审阅 C++ 消费侧 |
| 两个 verify 脚本 | 开发者自测用；accept 另用同插件模板重渲一份进 `runtime/` |

**关键一句在契约原文里：「验收侧接受任何满足本契约的六件目录……不要求本次任务包由同一
会话生成。」** 六件是契约定义的交换格式，不是会话产物——所以发布者按需求产出的包，
验收者直接能用，开发者照着开发的也是同一份。

两个 verify 脚本那一行值得单看：accept **不信任包里那两份拷贝**，而是用同插件的 case-gen
模板重渲一遍进 `runtime/`。同一套模板所以逐字节同构，但信任来自重渲，不来自拷贝。

### 补缺模型：发布者没用 case-gen 时的降级

这时验收者自己跑 case-gen 补出可验的用例，产物只进验收现场，开发者事前看不到。

**这是降级，不是设计。** 同源模型里开发者与验收者看的是同一份用例，零歧义；补缺模型多
背一个问题——开发者没见过这批用例，判负的正当性要靠第六节那条边界兜。

0923 就在补缺模型里。当期只能这么走，但**下一批可以争取回同源模型**：把 solver 的 case-gen
做成同样「既能发也能验」的产物形态，再推动发布者用它，比每批都补缺便宜。

## 五、三个「未必」，与它们逼出的一条结论

验收侧的设计前提，必须按最坏情形写：

1. **发布者未必用我们的 skill。** 0923 的六份任务书来自上游 `ops-solver` 的 `origin/task`
   分支，不是 doc-write 写的，格式与字段都不受我们约束。
2. **发布者未必把用例交给开发者。** 交了性能规格不等于交了精度用例；0923 点名的六个
   `*_family_950_testCase/` 目录一个都不存在。
3. **开发者交的 harness 未必可用——而这取决于目标仓，不取决于开发者。** 仓有强 frame 时
   （ops-blas）直接可用、不必重产；仓没有时（ops-solver）各人各写。**判它之前先看仓，
   不要先看人。**

还要再加一条，它比上面三条更硬：**第四个「未必」是我们改不了仓**（第二节）。凡是需要
维护者合入才成立的前置条件，验收通路都不能依赖。

**结论：验收侧必须自足。** case-gen 与 harness-gen 在验收者手里的定位是「补缺口」，
不是「消费上游产物」——把它们设计成依赖上游用了我们的工具，遇到 0923 这种批次就整条线失效；
设计成依赖上游先改仓，则连启动条件都不在我们手上。

这里有一条现存约束要记明白：**harness-gen 要求手上先有一个符合六件契约的任务包**。
它直接消费包内的 `_column_specs(facts)`，并有 fail-closed 的包 ABI 门
（`UNSUPPORTED_PACKAGE_VERSION`）——认的是契约与可识别的生成器版本，不是「谁产的」，
所以发布者按契约产的包同样能喂给它。但上游连六件都没给时，顺序就变成**先补 case-gen
产出任务包，再 harness-gen 消费它**：验收者得把发布者本该做的那一步先自己补上。

## 六、验收者自产用例的合法性边界

验收者自己造用例来判开发者，合法性来自一处：**判据是任务书给的，用例只是任务书声明的
场景的实例化。**

所以边界很清楚：

**自产用例必须可追溯到任务书的声明；任务书没声明的规格，不能作为判负的依据。**

0923 的任务书 §3.5 列了九类必测场景（基础功能、矩形与 padding、trans、选主元、info、
批量边界、空问题、确定性、非默认 stream）并给了入参生成规则，这就是自产用例的合法来源。
超出这张表去造规格、再拿它判不通过，是把验收变成出题。

**这一节只在补缺模型里需要。** 同源模型下开发者拿到的就是验收要跑的那份，不存在
「他没见过」的问题——这也是同源模型更值得争取的原因之一。

## 七、0923 的角色实况

| 角色 | 是谁 | 实际交了什么 |
| --- | --- | --- |
| 任务发布者 | 源头 ops-solver `origin/task`，经 `community_task` 转发 | 6 份任务书 + 27 套竞品 bench |
| 代码仓维护者 | `gitcode.com/cann/ops-solver` 的 owner | 仓的现状：7 个算子、无测试 frame |
| 开发者 | 社区贡献者 | 尚未交 |
| 验收者 | 用这些 skill 判算子的人，**不是我们** | 待定 |
| skill 构建者 | 我们（本仓） | 现有三条线与 harness-gen |

发布者这一栏**没用我们的工具**：任务书不是 doc-write 写的，用例不是 case-gen 产的，
所以第五节那三个「未必」在这批上是三个「确实」。

## 八、构建者与验收者的关系：模拟，然后改造

**skill 构建者不做真实验收。** 它做的是模拟验收者去跑这些 skill，看哪里卡住，再按模拟
结果改造 skill——这个闭环就是 skill 的开发方式，改造本身是目的，不是风险。

要防的是另外两件：

**一、模拟失真。** 构建者手里有真验收者没有的东西——`plugin/CLAUDE.md`、`plugin/docs/`、
仓规、上一轮 session 的记忆。带着这些跑通，不等于零上下文的验收者也能跑通。仓规为此定了
两道：验收的完整契约只有 `SKILL.md` 加 `references/` 加 `scripts/`，开发件不分发、
模拟时当它们不存在；正式验收一律走 `isolated-acceptance` 的无头通路，不在本仓 session 里跑。

**模拟要像，就得把自己降到验收者的信息水位。** 冷读可理解性也只有全新 session 才测得准，
resume 的评审带着上一轮上下文，不是冷读者。

**二、改造方向长成特判。** 模拟里卡住，最省事的改法是对着手头这个算子加一条特判；单次看
都成立，累积起来 skill 就成了一堆 if。八维评审里通用性、泛化性、复杂度三条就是拦这个的，
所以核心裁决逻辑与对外契约的改动无条件走 checkpoint 评审。

**判断一次改造对不对，问一句：这条改动是只对手头这个算子成立，还是对这一类都成立。**
