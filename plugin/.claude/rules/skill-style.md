# skill 开发规范

约束本仓 `skill/<name>/` 下自己写的文件：`SKILL.md` 与 `references/*.md`。
写这些文件时本规则常驻上下文，不需要主动去读。

规范取自 `cannAgent/cannbot-skills` 的 skill 部分。它的 Agent、Team、plugin
依赖图、治理流程与领域目录分类不适用本仓，未纳入。

## 三条原则

**信息来源可信。** 技术事实只能来自 ATK 源码、CANN 官方文档、任务书、工程公开
接口面、用户明确提供这五处。不确定就标注不确定，不要写成事实。

**渐进式披露。** `SKILL.md` 只写路由与契约，知识放 `references/`，需要时再展开。

**简洁精炼。** 三条落地做法：

- 先给结论，再说原因
- 能成表就不写散文
- 一个段落只讲一个要点

## SKILL.md 是路由器，不是知识库

样例仓 59 个 skill 的 `SKILL.md` 中位 108 行，最短的 22 行——一棵决策树加两个链接，
知识全在 `references/` 的 7 份文件里。

骨架如下，没有的章节就不写，不要留空壳：

````markdown
---
name: <与目录同名的 kebab-case>
description: <做什么 + 何时触发>
---

# <Skill 名>

## 入口参数      表格：参数名 | 含义 | 取值约束 | 初值推断
## 前置检查      有强制步骤才写，标明不可跳过
## 主流程        决策树或阶段表；长流程拆进 references/
## 参考资料      链接清单
````

## frontmatter 契约

| 字段 | 要求 |
| --- | --- |
| `name` | kebab-case，与目录名逐字相同 |
| `description` | 说清**做什么**与**何时用**；只写做什么，agent 选不准 |

与别的 skill 有真实混淆风险时，才在 `description` 里写"……时改用 X"。
没有混淆风险不写——那是反向说明，不是默认格式。

## 目录用途

| 目录 | 放什么 |
| --- | --- |
| `references/` | 按需加载的知识：规范、判据、约束、排错 |
| `scripts/` | 可执行量具 |
| `assets/` | 模板与样例，供照抄 |

引用深度不超过两级：`references/a/b.md` 可以，再深一层不行。

## 指令必须具体

这是样例仓文风好的真正原因，也是本仓文档散文化的病根。

**禁止"适当处理"、"根据情况"、"必要时"这类执行者要猜的表达。**

命令、路径、参数、退出码、输出模板一律写死：

| 写法 | 判定 |
| --- | --- |
| 环境不满足时适当处理 | ✗ 执行者要猜 |
| `probe_env.py` 报告非 Phase A 时停在 S1，输出 `阻塞·未生成 @S1` | ✓ |
| 精度不达标就走失败流程 | ✗ 哪个流程、什么输出都没说 |
| 精度未通过时性能状态填 `未执行(精度未通过)`，不跑性能轮 | ✓ |

## 写完自检

取样例仓复核维度里与本仓相关的六条：

- [ ] `description` 说清了做什么与何时用
- [ ] 步骤有输入、处理、输出，执行者不用猜流程
- [ ] 失败、缺输入、环境不可用时的去向写明了
- [ ] 命令、路径、参数、输出格式具体
- [ ] 大段知识在 `references/`，`SKILL.md` 只留路由
- [ ] 技术事实有来源，未验证项已标注
