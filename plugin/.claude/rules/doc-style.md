# 行文规范

约束 `skill/<name>/SKILL.md`、`skill/<name>/references/*.md` 与 `docs/guide/*.md`。
形式规范（骨架、载体法则、渐进式披露）在 [skill-style.md](skill-style.md)，
这份只管**怎么把句子写出来**。

判据不靠人记：

```bash
python3 .claude/hooks/doc_style_lint.py            # 全仓
python3 .claude/hooks/doc_style_lint.py --fix      # 只自动修半角标点
```

改 `SKILL.md` 或 `references/` 时钩子会自动跑它并把结果注回上下文。

## 判据

每条都能机检，且**禁一个必须给一个替代**——只禁不给替换，下一个人只会换一个同样差的词。
词表在 `doc_style_lint.py` 的 `BANNED`。

| 规则 | 禁什么 | 为什么 |
| --- | --- | --- |
| `heading_question` | 标题用疑问句式：`怎么`、`什么时候`、`要不要`、`？` | 同一批文档的章节名要能横向对齐；疑问句每份问法都不同，对不齐也扫不动 |
| `heading_anthro` | 标题里出现`它` | 读者常从目录直接跳进某节，代词在那里没有先行词 |
| `anthropomorphism` | `它想`、`它认为`、`它知道`、`它的灵魂` 等认知动词 | 把工具写成有意图的主体，读者要先解析角色才读得到机制 |
| `first_person` | `我们的`、`我们会` | reference 是被查阅的，「我们」的指代在查阅现场不成立 |
| `filler` | `简单地`、`轻松`、`显然`、`众所周知` | 不携带信息，且「简单」对卡住的读者是反效果 |
| `vague` | `适当`、`必要时`、`视情况`、`酌情`、`尽可能` | 执行者要猜。skill-style.md 早就写明禁止，此前没有检查器 |
| `future_tense` | `将会`、`即将` | 文档描述当前行为，将来时会过期 |
| `halfwidth_punct` | 中文语境里的 `,` `:` `;` `(` `)` | 一致性。`--fix` 可自动改 |
| `xref_broken` | `xx.md「章节名」` 指向不存在的节 | 让 agent 去查一节不存在的内容，它要跑到那一步才发现 |
| `anchor_broken` | `](#锚点)` 解析不到 | 同上 |

代码块、行内代码、链接目标、引用块（`>`）一律不判——引用块常常是贴出来的上游原文
或社区回复，按本仓行文改它就是篡改证据。

## 章节名词表

同一类文档的章节名必须能横向对齐。**先从这张表里挑，挑不到再新造**：

| 内容 | 章节名 |
| --- | --- |
| 跑之前必须具备的东西 | `前置条件` |
| 怎么调起来 | `用法` |
| 必须由人决定的项 | `需人工指定` |
| 落盘的东西 | `产物` |
| 明确不做的事 | `范围之外` |
| 出错了去哪 | `常见问题` |
| 判据与阈值 | `判据` |
| 机制解释 | `工作原理` |

`docs/guide/` 四份已全部按这张表对齐，可照抄。

## 主语怎么选

分界线取自 Google 开发者文档风格指南：**第二人称写读者要做的事，第三人称写软件做的事。**
本仓的岔子在于三类文档的读者不是同一个人：

| 文档 | 读者 | 主语 |
| --- | --- | --- |
| `docs/guide/` | 用 skill 的人 | 祈使句为主。要区分动作方时用「助手」，不用「它」 |
| `SKILL.md` | 执行的 agent | 祈使句。「你」= agent，可以用但没必要 |
| `references/` | 查阅中的 agent | 只描述机制与判据，不出现人称 |

**别把对话过程当成文档结构。** `你说什么 / 它问你什么 / 你拿到什么` 这种写法是把一次
对话的转录当骨架，读者得先在脑子里演一遍角色才拿得到信息。写契约，不写剧本。

## 没有收进来的规则

Diátaxis 要求 reference「只描述，不解释」（austere and uncompromising，不放 opinion
与 explanation）。**本仓不收这一条**，因为读者不同：Diátaxis 假设读者是人，看不懂会
自己去翻 explanation；本仓 `references/` 的读者是 agent，不写清楚「为什么这么定」，
它会自行推翻这个决定重来一遍。所以本仓的 references **保留「为什么」**，
只把它约束在结论与取舍上，不铺叙述——这一条写在 skill-style.md 的载体法则里。

同理砍掉的候选判据（都在存量上标定过，误报太高）：

| 砍掉的 | 为什么 |
| --- | --- |
| 禁 `请` | 命中 9 处，多数在 `golden-task-doc.md` 与 `solution-kinds.md`，是贴出来的上游原文与社区回复样例，改它等于篡改样例 |
| 禁 `它会` / `它自己` | 描述软件行为用第三人称本来就是对的，命中 10 处大半是正常用法 |
| 禁 `其实` / `当然` | 4 处全是正常的转折语气 |
| 禁 `只需` | 「只需生成任务包时改用 X」这类是正常限定，不是填充 |

## 新增判据的门槛

1. 先在全仓存量上跑一遍，看命中量与**误报**
2. 误报率高就别加——判据一旦被忽略，整个门禁就失效了
3. 给替代写法，写进 `BANNED` 的 value
4. 在 `test_doc_style_lint.py` 里补一条命中样例和一条误报样例
