# 开源仓算子样例跑测

从一台空机器到一张逐算子的通过/失败台账。

## 概览

| skill | 输入 | 产物 | 前置 |
| --- | --- | --- | --- |
| `cann-env-setup` | 工作区路径 + 目标仓 | 可编译可运行的机器 + 环境报告 | 无 |
| `cann-950-feature-scan` | 仓路径 | 命中 950 新特性的算子清单 | 无 |
| `cann-ops-run` | 仓路径 + 算子清单 + 芯片型号 | 逐算子台账与日志 | NPU |

三者不必连续执行：机器已就绪可直接跑测，已确定测试范围可跳过扫描。
产物统一落在项目根目录的 `cann-ops-report/`，彼此通过文件衔接。

> ⚠️ **在项目根目录下开工，不要 `cd` 进 skill 的安装目录。**
> 否则跑测产物会写入 `~/.claude/skills/`，下次更新 skill 时被一并覆盖。

---

## `cann-env-setup`

把裸机或新服务器搭成可编译算子的状态。**不负责安装 CANN 本身**，CANN 需事先装好。

### 用法

```text
用 cann-env-setup 搭环境。
工作区：<找算子仓、以及新 clone 落地的根目录>
目标仓：<要搭哪几个，例如 ops-math,ops-nn>
```

追加「先干跑，只出计划不执行」可仅查看将要变更的内容。

### 需人工指定

**每一类有副作用的动作都先出计划，确认后执行**：建 conda 环境、`pip install`、
`git clone`、把仓切到配套 tag。

两项明确不代做：

| 不代做 | 实际行为 |
| --- | --- |
| `sudo` 安装系统包 | 列出缺失项并给出命令，是否安装由人决定 |
| 静默停在 master 上编译 | 找不到配套 tag 时询问，不自行选定 |

### 产物

环境报告一份，中文写明「已就绪 / 还差什么」，附一次单算子冒烟编译的结果——
能编出算子包，才算这台机器真正可用。

## `cann-950-feature-scan`

静态扫描源码，列出用到 Ascend 950 硬件特性的算子。

### 前置条件

无。纯静态分析，不需要真机。

### 用法

```text
扫一下 <仓名或路径> 里用到 Ascend 950 特性的算子。
```

### 需人工指定

**扫哪个仓。** 候选仓从当前目录检出后交付确认，检不出才询问路径。
**每轮都会确认，不沿用上次的选择。**

### 产物

markdown 清单一份，列出命中 simt / hif8 / RegBase 的算子。

用途是**缩小跑测范围**：整仓无差别全跑需要数小时机时，按清单挑重点更划算。

---

## `cann-ops-run`

编译、安装、运行各算子样例，产出台账。

### 前置条件

带 NPU 的机器。这是最耗时的一步，可能跑数小时。

### 用法

```text
用 cann-ops-run 跑测。
仓：<本地源码路径，目录里要有 build.sh>
算子：<具体清单，例如 add,matmul,softmax>
芯片：<ascend910b / ascend950 / ascend310p，或者让它自动探测>
```

### 需人工指定

**开跑前声明范围与拓扑并等待确认**——哪几个仓、哪些算子、如何并发。
确认发生在花掉数小时机时之前。

两项硬约束：

| 约束 | 原因 |
| --- | --- |
| 不接受「整仓无差别全跑」，必须给具体算子清单 | 防止一句话烧掉一整天机时 |
| 不臆测芯片型号 | 未指定且探测不到时询问 |

启动后转入后台，中途无需干预，也不会持续刷日志。

### 产物

按仓分目录，落在项目根的 `cann-ops-report/<仓名>/test/`：

| 产物 | 内容 |
| --- | --- |
| 跑测台账 | **权威结论**。逐算子通过或失败，续跑时据此跳过已通过的 |
| 逐算子日志 | 编译、安装、运行三段分开存 |
| 失败诊断 | 失败算子各一篇，写明卡在哪、日志出处 |
| 跨仓摘要 | 每轮自动生成，供快速浏览 |

**最终报告默认不生成**，需显式要求——跑测中途出报告只会给出半份结论。

## 台账到手之后

**失败不等于算子有缺陷。** 先看诊断篇给出的层次，以下三类都不是算子本身的问题：

- 环境没配好
- 仓没切到配套 tag
- 编译期就挂了

确认是算子自身问题并要反馈上游的，接[社区 issue 处理](issue-workflow.md)——
它读的就是这张台账。

## 常见问题

| 现象 | 原因 |
| --- | --- |
| 直接去敲 `build.sh` | 不应如此。同一个仓多进程并发编译会撞 `CMakeCache.txt`，跑测入口本就管着这件事 |
| 声称「跑测完成」但台账里有未消费的失败 | 不成立。要求把失败逐条落到诊断篇 |
| 要求改算子源码把测试跑过 | 不允许。跑测只观测不修改，改了台账即失去意义 |
