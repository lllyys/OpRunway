# 任务书撰写：调用与示例

`repo-task-doc-write` 的调用方式。它是[社区算子任务](community-task.md)链路的第一步，
整条链路的概览在那份文档。

## 用法

调用命令，跟上算子名：

```text
/repo-task-doc-write <算子名>
```

助手随即发出 intake 表。把材料、前提与已知项填进表里对应的答题块，留空的项跳过：

| 段 | 填什么 |
| --- | --- |
| 必填·事实 | 只有你知道的：背景、代码仓、硬件型号、CANN 版本、性能标杆与判据、提交目录 |
| 必填·决定 | 方向性判断：工程模式、对标基线、是否随机算子 |
| 可选·已有结论 | 助手本会给候选的项。已想好的（如接口签名、支持的数据类型）直接写下，省一轮确认 |

信息给全走两次输入的快速路径：填表一次，总审拍板一次。留空的必填项转成批次追问，
多几轮对话，结论不受影响。

## 示例

以真实任务 aclblasCgeru（复数单精度无共轭秩 1 更新）为例，调用：

```text
/repo-task-doc-write aclblasCgeru
```

助手发来 intake 表后，这样填：

- 工程模式：kernel直调
- 对标基线：cuBLAS cublasCgeru（语义参考 Netlib cgeru）
- 硬件与版本：Ascend 950PR，CANN 9.1.0
- 提交仓库：https://gitcode.com/cann/ops-blas 的 blas/ger/arch35 目录
- 已有材料：golden 由 cblas 生成，不依赖 torch
- 输出到：reports/cgeru/

填完交回，助手把推断的候选（签名、数据类型面、值域、异常行为、精度阈值等）一轮呈上，
你逐项拍板——准了、缺了、还是多了。拍板过后助手落稿并跑质量门，贴出门的完整输出与封条。
封条是交付的唯一凭据，**过完门禁再手改任务书封条就对不上**，改完要重跑一次门禁。

## 备选：提前填好整表传入

不想等助手递表，可以先填好整表一次传入。空白母版随 skill 发在
`assets/intake-template.md`，拷一份填好，调用时把它交给命令，两种传法：

- 贴路径：`/repo-task-doc-write aclblasCgeru`，同一条消息里注明「用这份填好的 intake：
  <文件路径>」。
- 内联贴表：命令之后直接把填好的表粘进来。

这么走，intake 只占一次输入，加总审拍板一次，是最紧的两次输入。

**只往 ` ```answer ` 块里写，别动 `### <骨架key>` 标题与围栏结构**——解析器靠它们切块。
用带自动格式化的编辑器填会把下划线转义、破坏围栏，映射就对不上了。
