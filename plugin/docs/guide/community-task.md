# 社区算子任务

从需求材料到验收结论的完整链路。

## 概览

| skill | 输入 | 产物 | 前置 |
| --- | --- | --- | --- |
| `repo-task-doc-write` | 算子名 + 需求材料 | 可验收的任务书 | 无 |
| `repo-task-case-gen` | 任务书 | 测试用例 + CPU 标准答案 | 无 |
| `repo-task-atk-accept` | 上两者的产物 + 算子工程 | 验收结论报告 | NPU |

BLAS 类算子把后两个换成 `repo-task-blas-case-gen` 与 `repo-task-blas-accept`，形态一致；
该分支的细则（输入产物、验收后复测与豁免）见 [blas-usage.md](blas-usage.md)。

**任务书自带跑测件时跳过中间那步。** 部分社区任务（sparse 系列如此）随任务书交付
一整套用例与执行器脚本，验收直接拿它跑，`repo-task-case-gen` 不参与。

**三者不必连续执行。** 每一步的产物都是文件，隔几天、换台机器都能接着用：
已有任务书可直接从出用例开始，拿到现成用例包可直接跑验收。

## `repo-task-doc-write`

把需求材料整理成一份约束明确、可据以验收的任务书。

### 用法

```text
/repo-task-doc-write <算子名>
```

助手随即发一张 intake 表收齐信息（材料、前提、已知项），随后把推断整理成一轮总审
请你拍板。信息给全走两次输入的快速路径；缺的项转批次追问，代价是多几轮对话。

**调用与示例**见 [doc-write-usage.md](doc-write-usage.md)。

### 需人工指定

**拍板**：助手把推断的候选一轮呈上，你逐项判断——准了、缺了、还是多了。信息在 intake
表里给全时，这一轮之外不再追问；随机算子、签名与对标基线对不齐等条件项按需各加一轮。

| 事项 | 说明 |
| --- | --- |
| 拍板是唯一不可代做的事 | 模型的推断不算事实。答复原话逐字记档，因此不要只回「可以」，要写出理由与边界 |
| 无人拍板则流程终止 | 会一直停在该轮等待。这是设计如此，不是卡住 |
| 随机数生成类算子多问一项 | CPU 与 NPU 的随机数流通常不一致，精度不能默认用相等比 |

### 产物

| 产物 | 面向 |
| --- | --- |
| 任务书 `.md` | 外部开发者照它开发，验收方照它判定 |
| `decisions.json` | 存档。每条约束由谁拍板、原话是什么 |
| 门禁封条 | 证明交付版本通过了质量门 |

**过完门禁再手改任务书会导致封条对不上**，需重跑一次门禁再交付。

### 不适用的场景

- **算子已开发完，只想补份文档。** 这套流程的价值在开发前把约束定死
- **无人对约束负责。** 见上面「无人拍板则流程终止」

## `repo-task-case-gen`

依据任务书生成测试用例，并在 CPU 上算出标准答案。

### 前置条件

装有 Python 与 CPU 版 torch 的任意机器，不需要 NPU。

### 用法

```text
用 repo-task-case-gen 为 <算子名> 生成用例包。
任务书：<任务书路径>
算子工程：<有的话给上，会去读工程自带的接口文档>
输出到：<产物落在哪>
```

### 需人工指定

**精度比对的真值取自哪个基线。** 任务书写明了就不问；未写明时会列出候选、
参数是否逐位对应、以及选取依据，交付确认。

这一项不可代做：**基线选错整个用例包要重做**，且要到 NPU 上跑出一片无法解释的
精度失败才会暴露。

### 产物

一个目录，含用例、冻结的输入、CPU 算出的标准答案，以及一张记录接口事实的表。

**整目录交给验收步骤，不要拆开挑文件。** 三者配套，缺一样会被拒收，或者测错对象。

## `repo-task-atk-accept`

在 NPU 上编译部署算子工程，跑精度与性能，产出验收结论。

### 前置条件

带健康 NPU 卡的机器。

### 用法

```text
用 repo-task-atk-accept 验收 <算子名>。
用例包：<上一步的产物目录>
算子工程：<待验收的算子目录>
母仓：<这个算子所属的开源仓根目录>
输出到：<验收现场建在哪，不要放进仓里>
```

### 两条用例来源

| 手上有什么 | 用例从哪来 | 精度标杆 |
| --- | --- | --- |
| 任务书 + 算子工程 | `repo-task-case-gen` 生成的用例包 | 用例包里冻好的标准答案 |
| 任务书 + 自带跑测件 + 算子工程 | 自带件里那份 | 自带件的 CPU 节点当场算 |

走哪条按手上有什么定，不用指定。自带件那条上有两件事照既定口径自动做：

- **精度用例扩到 1000 条**，并补齐任务书要求的全部数据类型。自带件的生成脚本
  通常只覆盖其中两种，且把类型写死在代码里，单纯加条数补不上这个缺口
- **性能跑两批**：自带件的泛化集，加任务书性能判据表里的场景。前者证明泛化面，
  后者才是达标线，两批对应任务书两条不同的要求，少跑一批就有一条没测到

扩出来的那批在报告里单独成节，不与自带件原有用例合并算通过率——前者是验收方
按任务书补的，后者是任务方自测的口径。

### 需人工指定

**算子工程目录**与**结果落点**，两项均需确认。

**即使只检出一个候选也会要求确认。** 算子名与目录名常常不同，唯一候选完全可能是
实现同一套接口的另一个算子——装错时前面各阶段都不报错，要到最后才表现为
「整类数据类型精度不达标」，届时会被误读成算子有缺陷。

确认之后转入无人值守，中途不需要干预。

### 执行模型

精度轮由两个执行器跑，报告中并列呈现。

```text
先查：CANN 里有没有同名内置算子抢走 tiling
                    │
      ┌─────────────┴──────────────┐
    没有                          有
      │                            │
 ATK 跑全量                   ATK 跑全量（测的是内置实现，只作对照）
      └失败→ 单条复跑               │
            剔除批内污染      C++ 跑全量（用算子包自带的 tiling）
      │                            └失败→ 换卡单条复跑，剔除批内污染
 C++ 复跑失败集                     │
 ＝交给算子作者的复现器              │
      │                            │
  ▼ 以 ATK 为准               ▼ 以 C++ 为准
```

**失败用例为什么要单条复跑。** 批量执行时前序用例损坏 device 或显存，后续用例会连带
失败或连带算错，而真凶自身往往显示通过。单起进程提供干净环境，才分得开真凶与受害者。
复跑结果三分：仍失败、跑起来但算错，两者都是真实缺陷；单跑通过的属批内污染，**不计缺陷**。

**C++ 通过为什么不能推翻 ATK 的失败判定。** C++ 执行器用 DMA 搬输入，ATK 走真实
PyTorch 用户的路径，某类缺陷只在后者的时序下触发，C++ 结构上碰不到。此类情形仍判缺陷，
报告注明未复现。

**同名内置算子为什么会让判定依据反转。** ATK 必须拉起 torch_npu，torch_npu 拉起 GE，
GE 按算子类型先到先得注册 tiling，内置那份先到、算子包自带的被拒。此时 ATK 测的是仓库
里的旧实现；C++ 执行器不碰 torch_npu，用的是算子包自带的 tiling。这是结构性限制，
没有环境变量可以改变。

| | ATK 执行器 | 裸 C++ 执行器 |
| --- | --- | --- |
| tiling 来源 | GE 注册的那份，**有同名内置就抢不过** | 算子包自带 |
| 算子把卡跑崩之后 | 进程不复位，同批后续全连带 | 重启进程续跑，无连带 |
| 搬输入的方式 | 与真实 PyTorch 用户一致 | DMA，**某类缺陷碰不到，会漏报** |
| 覆盖 | 精度 + 性能 | 只有精度 |

**算子只注册 torch 算子、不暴露 aclnn 接口时**（sparse 系列如此），上面这套双执行器
对照不适用，报告里那一节标「不适用」，精度判定只有 ATK 一路。代价是少一路交叉验证，
失败判定全靠单条复跑，报告里会写明。

### 产物

| 产物 | 面向 |
| --- | --- |
| `report/index.html` | 人。一屏看完总结论、精度按数据类型、性能按规模档 |
| `report/report.md` | 人。详版，多了部署过程、失败复验、覆盖边界、证据链 |
| `report/verdict.json` | 机器可读的唯一结论，下游工具认这份 |
| `repro/` | **算子作者**。整包拷走即可复现失败用例，无需安装任何 skill |

**结论由脚本从数据算出，不要手改报告**——下次重跑即被覆盖。要改措辞或版式，
让助手重出报告，一个数都不会重算。

## 结论可信度

报告会主动标出自身边界。以下三项需要识别：

| 报告上出现 | 含义 |
| --- | --- |
| 某一格标着**未覆盖** | 该部分**一条都没测过**。既非通过也非失败，是本轮没有答案 |
| 精度表上方一条**黄底提醒** | CANN 内置的同名实现抢了 tiling，**该表测的不是待验收代码**。真正的结论在「tiling 归属与双执行器对照」那节的独立执行器一轮，见上文[执行模型](#执行模型) |
| 性能写着**未评级（精度未通过）** | 精度未过不评性能。已跑出的耗时留作参考，不构成结论 |

出现「未覆盖」而总体结论写着通过时，**以未覆盖为准**——说明本轮验收不完整，
要么补跑，要么在结论里如实写明缺口。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| 门禁一直判红 | 先读报错，其中带着「不写会怎样」与替代写法。**不要改判据来通过**，那等于拆掉防线 |
| 整批用例一起失败 | 多半是卡被占用或算子工程没装对，不是算子本身的问题。先做失败复验再下结论 |
| 助手想跳过某个环节 | 验收中有几道闸标着「不可跳过」，跳过则结论不成立。各自拦什么见 [`repo-task-atk-accept/SKILL.md`](../../skill/repo-task-atk-accept/SKILL.md) |
