# 社区 issue 处理

把问题反馈给上游开源社区，并跟踪到有结论。支持 GitHub、Gitee、GitCode。

## 概览

| skill | 用途 | 输入 |
| --- | --- | --- |
| `cann-issue-report` | 起草 issue，一个问题一篇 | 失败项来源 + 仓的本地路径 |
| `cann-issue-track` | 跟踪回复、复测、闭环 | 已提的 issue |

两者可独立使用。已经提过 issue、只想跟进回复的，直接用 `cann-issue-track`。

> 📌 **范围限定为「提问题并跟到结论」，不绑定算子。**
> 起草侧目前读的是算子跑测台账（见[开源仓算子样例跑测](ops-sample-run.md)）,
> 泛化到任意开源仓的输入仍在开发中；跟踪侧已可用于任意仓。

## 提交前确认

发评论、关 issue、新建 issue 发出后不可撤回，维护者会立即收到通知。两个 skill 遵循同一流程：

1. 先空跑，**将待发送内容原样打印**，标题与正文均不截断
2. 三选一：**确认执行** / **我先改改** / **暂不执行**
3. 仅「确认执行」会调用上游接口
4. 另外两项将草稿存为文件并给出路径，**不调用任何接口**

建 git 分支、执行清理命令等仅影响本机的动作，同样先行确认。

**未经确认即声称「已提交」属于异常**，要求贴出实际发送的内容核对。

## `cann-issue-report`

将跑测失败项整理为社区可读的 issue 草稿。

### 用法

```text
用 cann-issue-report 给失败项起草 issue。
仓：<本地源码路径，上游平台由 git remote 推断>
芯片：<ascend910b / ascend950 / …>
```

### 需人工指定

| 项 | 原因 |
| --- | --- |
| 芯片型号 | 写入 issue 正文的环境表。推断错误等于向社区报告了错误的环境 |
| 提报范围 | 先列出候选清单供删减，再起草 |
| 是否提交 | 提交不可撤回，见「提交前确认」 |

### 产物

| 产物 | 内容 |
| --- | --- |
| issue 草稿 | 一个问题一篇。含错误日志摘录、已执行的诊断、命中的 950 特性（若已扫描） |
| 提交状态记录 | 跨轮去重的依据，同一问题不重复提报 |

### 范围之外

- 不重跑测试、不读源码做新诊断，仅将已有结论整理成社区可读的形式
- 不修改跑测台账与日志
- 访问令牌只从环境变量读取，不写入任何文件

## `cann-issue-track`

读取社区回复，按方案复测，并关闭已解决的 issue。

### 前置条件

| 项 | 说明 |
| --- | --- |
| 令牌 | `GITEE_TOKEN` / `GITCODE_TOKEN`。缺失时会提示配置方式，不静默跳过 |
| issue 来源 | 非 `cann-issue-report` 提交的 issue 无法自动接续，需提供链接手动登记 |

### 用法

```text
用 cann-issue-track 看看提的 issue 有回复没有。
```

### 需人工指定

| 项 | 说明 |
| --- | --- |
| 社区方案是否采纳 | 方案由模型阅读评论后理解，改动计划与复测方式会先行提交确认 |
| 复测通过后是否关闭 issue | 属于对外发送，见「提交前确认」 |
| 复测未通过是否追问 | 同上 |

**方案理解基于语义而非关键词匹配，存在偏差可能。** 计划不符预期时选「我先改改」。

### 产物

复测结果、已关闭的 issue，以及归档进常见问题库的有效解法。

### 范围之外

- 不修改原仓工作区，源码改动一律新开分支
- 不代替 `cann-issue-report` 提交新 issue，仅处理已提报的
- 不覆盖跑测台账，只追加复测记录
- 清理类操作不允许作用于 `/`、`/home`、`/usr`、`/etc`

## 常见问题

| 现象 | 原因 |
| --- | --- |
| 声称已提交，但未经确认 | 属于异常。要求贴出发送内容与 issue 链接核对 |
| 找不到已提的 issue | 状态记录只覆盖自身提报的 issue，其他来源需手动登记 |
| 同一问题被提报两次 | 状态记录被删除或更换了目录，去重依赖该文件 |
