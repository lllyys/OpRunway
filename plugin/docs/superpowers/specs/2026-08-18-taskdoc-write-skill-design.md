# 社区算子任务书撰写 Skill 设计

**日期：** 2026-08-18
**状态：** 已评审，待实施
**产物：** `skill/repo-task-doc-write/`（与现有验收 skill 同仓并列）

## 0. 一句话

基于模板和规则的结构化追问流程，辅助需求方快速产出一份合规、无歧义、可验收的社区算子开发任务书，出口有一道不可绕过的质量门。

---

**记号约定：** 形如 `§2.5`、`§3.2` 的编号指**任务书模板的章节**，
指本设计文档自身的章节时写「本文 §x」。

## 1. 问题与目标

### 1.1 任务书的两个受众

任务书不是给一个人看的，它同时是两份契约：

| 受众 | 要从任务书得到什么 |
| --- | --- |
| **外部开发者** | 开发范围、实现约束、交付件清单、自验方法、提交位置 |
| **验收 agent** | 能零歧义机械导出的验收约束（覆盖面、精度判据、性能判据、错误语义） |

只按其中一个受众设计会漏。验收侧的 `skill/repo-task-atk-test/references/intake.md`
定义了一张 13 字段的验收约束表，但它完全不覆盖交付件、PR 目录、参考资料这些
纯开发者信息；反过来社区模板 v3.0 对错误语义和性能判据的可执行性要求过软。

### 1.2 现状缺陷（来自实物核对）

核对对象：

- `task-docs/community_task_docs/task_doc_templete_v3.0.md`（85 行章节骨架）
- `task-docs/community_task_docs/task_doc_example_v3.0(SlidingTileAttention_task_doc).md`（185 行）
- `task-docs/任务书人工checklist.xlsx`（Sheet1 共 14 条检查项）

样例暴露的缺陷分三类，每一类都对应一道可脚本化的门：

**A. 跨章节不一致**

| 缺陷 | 说明 |
| --- | --- |
| §2.3 接口定义有 `windowSizeLen`，§2.4 参数表没有这一行 | 漏参 |
| §2.3 用 camelCase，§2.4 用 snake_case | 违反 checklist 第 7 条 |
| §2.4 说 q/k/v 值域 `(-∞,∞)`，§3.5 说 `(0,1)正态分布` | 同一参数两个答案 |
| §2.4 说 `text_length ∈ (0,∞)`，§2.1 说 `has_text=false 时按 0 处理` | 0 不在声明值域内 |
| §2.4 描述说 `window_size` 是奇数窗口，值域写 `(0,∞)`，§3.5 写「[1,100] 平均分布」 | 奇数约束三处都没落进可执行表达 |

**B. 无边界表达**

- §3.3「与 0.8 倍【FastVideo + GPU(A100)】持平」——「持平」是 `≥` 还是 `±容差`，没定义；
  GPU 侧口径是 `Calls / Total time / Avg time`，NPU 侧怎么对齐没写。
- §2.4 异常行为列 8 行全是「触发参数校验报错」——给不出任何一个具体非法输入。
- §3.1 只写「A2系列产品」，性能表只给 910B3；模板 §3.3 自己要求「A2 要明确 910B3、910B4」，
  checklist 第 10 条同样要求。样例违反了自己的模板。
- §3.1 只有 CANN 版本，没有 torch/torch_npu 版本；GPU 标杆没有驱动/CUDA 版本，
  性能对标不可复现。违反 checklist 第 9 条。

**C. 形式缺陷**

- §3.5 的 `[自测用例和测试指导](测试用例文件夹路径)` 是未替换的占位符，
  同时是隐藏跳转链接，违反 checklist 顶部「所有链接需要显式贴出来」。
- `community_task_docs/README.md` 声称模板是 v2.3，目录里实际是 v3.0。

**D. 模板缺位**

模板 v3.0 里没有位置承载两类信息：

1. **非连续 Tensor 支持**。验收侧 `intake.md` 明写「任务书参数表『非连续Tensor』列；
   无此列记为未声明」，每份任务书到验收阶段都会挂一个待确认项。
2. **随机类算子的精度对比判定策略**。验收侧 `random-operator-signals.json` 有 18 个信号词，
   命中即强制要求四选一策略，否则 `derive_interface.py` 退出码 2。
   样例 §3.5 写了「(0,1)正态分布」，恰好命中——这份任务书拿去验收会被拦住。

### 1.3 两个来源互有长处

不以验收 skill 为唯一权威。逐维核对结果：

| 维度 | 社区模板 v3.0 | 验收 skill |
| --- | --- | --- |
| 内存要求 | 有（§3.4） | 无此维度 |
| 数据排布格式 | 有（§2.4 独立列） | 约束表只有 dtype/rank/shape/attr |
| 入参生成规则 | 有（§3.5 表格，需求方语言） | 有，但用「语义轴」这类验收侧语言 |
| 交付件 / PR / 参考资料 / 注意事项 | 有（§4-§7） | 不覆盖 |
| 错误语义的可执行性 | 弱（一列同值即可） | 强（要求「必须拒绝的输入和报错要求」） |
| 性能判据的可执行性 | 弱（「持平」可过） | 强（要求绝对门槛或对比规则） |
| 非连续 Tensor / 随机策略 | 无 | 有 |

正确做法是把两个来源合并成一份「关键信息要素」清单，逐条标注服务谁、判据是什么。
这份清单就是本 skill 的骨架。

### 1.4 环境约束

任务书撰写发生在算子开发之前，**不能依赖真机或 torch 探测**。
本机实测：`python3 -c "import torch"` → `ModuleNotFoundError`，numpy 2.4.4 在。

因此 agent 给出的「对标接口支持哪些 dtype、attr 该长什么样」只能来自模型知识或联网文档，
没有一条能在本机实证。这不是削弱「人拍板」要求，而是把它变成硬性要求：
**每个推断项的证据强度天然弱，必须人确认。**

有 torch 的机器上可以顺带抓签名当辅助证据，但门禁不得依赖它。

## 2. 架构决策

### 2.1 Markdown 是唯一真相

交付物就是模板格式的 md，人拿到后一定会手改。质量门写 parser 按固定章节号和表格列反解后校验。

副产物 `evidence/decisions.json` 只记「谁拍的板」，不参与渲染。

**放弃的替代方案：** 结构化 JSON 当真相再渲染出 md。判据最硬，但人改了 md 就与 JSON 脱钩，
且 §2.1 的数学公式、算法说明这类散文塞进 JSON 很别扭，模板改版等于改渲染层。

### 2.2 要素清单驱动

`references/taskdoc-elements.json` 是唯一骨架。追问流程、渲染脚手架、质量门、
待确认清单全部从它派生。

骨架条目形态：

```json
"2.4.value_range": {
  "section": "2.4",
  "name": "值域范围",
  "form": "table_column",
  "audience": ["developer", "acceptance"],
  "required": "always",
  "decision_owner": "human",
  "agent_may_propose": true,
  "checks": ["nonempty", "no_unbounded_for_generated_tensor",
             "consistent_with:3.5.tensor_distribution"],
  "vague_forbidden": true,
  "failure": "开发者不知道要处理到什么范围；验收侧生成不出数据，(-∞,∞) 没有对应的采样规则"
}
```

比现有 `artifact-contracts.json` 多两个字段：`audience`（服务哪个受众）、
`decision_owner`（谁拍板）。

**为什么不用「检查项驱动」：** 直接把 checklist 14 条加已知缺陷写成一组 check 函数，
完备性不可判定——这正是现有仓 CLAUDE.md §3.1 记的教训「按事故索引」。
骨架让「漏没漏」变成可枚举的。

**为什么不用「判据写进模板注释」：** 判据与模板耦合，不可测试，模板改版全废。

### 2.3 人拍板：答复原话入库

agent 把推断项挑出来逐批问人，人的答复原文写进 `decisions.json`。
门禁校「每个 human 要素都有一段人的原话」，而不是校一个布尔标志。

```json
{
  "2.4.dtype": {
    "agent_proposal": "fp16, bf16, fp32",
    "provenance": "model_knowledge",
    "rationale": "torch.roll 支持全部浮点类型",
    "human_reply": "去掉 fp32，本期只要 fp16/bf16",
    "state": "human_modified"
  }
}
```

`state` 取 `human_confirmed` / `human_modified` / `human_supplied`。
门禁不做语义判断——空字符串判红，「对」也算确认。

**放弃的替代方案：** 生成一份待确认清单让人一次性批注。轮次少，但人容易整列填「✓」走过场，
门禁区分不了认真看过还是批量放行。

### 2.4 同仓并列

```
repo-task-atk-test/
├── skill/
│   ├── repo-task-atk-test/     验收（现有）
│   └── repo-task-doc-write/    撰写（新增）
├── docs/
└── third_party/ATK/
```

共享事实（`experimental_standard.md`、`random-operator-signals.json`）各自保留一份副本，
`tests/test_shared_facts_sync.py` 用 sha256 比对，漂了就红。

不做软链或抽第三目录：skill 部署到别的机器上就是一个普通目录，必须自包含。

### 2.5 四条红线

验收 skill 的红线不能整体照搬。**红线 1「不拿算子实现当验收依据」在撰写阶段不成立**——
写任务书时算子还不存在，而对标实现（`FastVideo.sliding_tile_attention`、`torch.roll`）
恰恰是必须读的合法依据。照抄会把 skill 写死。

可直接复用的只有红线 2（上游素材只读）和红线 4（agent 声明不可信）。
撰写侧重新推导的四条：

| 红线 | 内容 | 破了会怎样 |
| --- | --- | --- |
| **A. agent 推断不是事实** | 全部推断项必须人拍板并留答复原话 | 任务书写着一堆没人负责的约束，开发者照做、验收照测，错到最后才发现 |
| **B. 章节号只做加法** | 社区模板章节号不重编号，只在末尾追加 | 存量任务书与交叉引用全断 |
| **C. 门禁不可绕过** | `gate_pass.json` 用 sha256 封住当前 md | agent 声称跑过门禁，或跑完又改稿 |
| **D. 黄金任务书必须真的返回 0** | 反向 fixture 是门禁有效性的前提 | 门禁靠「什么都判红」通过全部正向测试 |

红线 2 在本 skill 的形态：`docs/development/taskdoc-source/origin/` 是上游素材的只读归档，
不修改、不就地修复。修复产物另存到 `references/`。

## 3. 章节骨架（v3.0+）

改动只有加法，三处，v3.0 现有章节号一个不动
（样例里有 `[2.4章节](#24-参数说明)` 这类交叉引用，重编号会全断）。

| 改动 | 内容 | 服务谁 |
| --- | --- | --- |
| **新增 §2.5 算子实现约束** | 非连续 Tensor 支持、broadcast 规则、dynamic shape 要求、原地/视图语义、确定性计算要求、空 Tensor / 0 维处理 | 开发者（主）+ 验收 |
| **§3.2 增条件子项** | 随机类算子的精度对比判定策略；非随机算子写「不涉及」 | 验收（主）+ 开发者 |
| **§2.4 列不变（9 列）** | 只是每列有了明确填写判据 | — |

### 3.1 为什么 §2.5 加在末尾而不是插在 §2.2

逻辑上「实现约束」紧跟「功能实现要求」更顺，但插入会把 §2.2-§2.4 全部后移，
存量任务书和交叉引用作废。收益是行文顺序，代价是兼容性，不划算。

### 3.2 §2.5 解决的真实问题

SlidingTileAttention 样例的实现约束现在是这样散落的：

- 「不支持 broadcast」「q/k/v 必须同 shape 同 dtype」→ 挤在 §2.4 表格里 `q` 那一格的描述列
- 「确定性计算要求」→ 在 §2.1 正文末尾
- 「S 必须不小于 image_seq_len + text_length」→ 也在 `q` 那一格
- 非连续 Tensor → 哪儿都没有

开发者要拼出「我到底要满足哪些实现层约束」，得把一个表格单元格读完再回头翻 §2.1。

「空 Tensor / 0 维处理」是新增的第 6 条，社区任务书最高频的漏项，
开发者不知道要不要处理、验收侧不知道该不该构造，双方都吃亏。样例里也没有。

### 3.3 §2.5 与 §3.4 的边界

§2.5 管「实现要满足什么」（约束），§3.4 管「跑起来占多少」（指标）。
内存布局约束进 §2.5，内存占用比值进 §3.4。

### 3.4 向后兼容

门禁遇到没有 §2.5 的老任务书，不是解析崩溃，而是给一条可定位的红：
`§2.5 缺失 · 非连续Tensor/确定性计算等实现约束无处声明`。

### 4.1 两处取值域决策

**「数据类型」列用独立词表，不绑 ATK 类型系统。**

取值域为 `tensor / scalar / attr / string / list_int / list_list_int / ...`，
自己维护，不直接引用 ATK 的 `flat_types` + `group_types`。

理由：任务书是发给开发者的，不该被验收工具的内部类型系统绑架。
代价是可能出现「任务书合法但 ATK 表达不了」的类型，那种情况门禁给**警告**不阻塞，
留给验收阶段处理。

**`(-∞,∞)` 判红，但报错给替代写法。**

对一个 fp16 输入 tensor 写 `(-∞,∞)` 是错的（表示不了，且 NaN/Inf 要不要测没交代），
更关键是生成不出数据。但需求方确实经常想表达「不限定」。

门禁判红并在报错里给出可接受写法：`全值域（含 Inf/NaN：不测）` 或 `[-1e4, 1e4]`，
逼出一个明确表态而不是简单拒绝。

## 5. 判据

### 5.1 一致性（纯机械，判别力最强）

| 判据 | 抓到的样例真实缺陷 |
| --- | --- |
| §2.3 签名参数名集合 == §2.4 表格参数名集合 | `windowSizeLen` 漏参、命名风格不一致 |
| §2.4 参数名 ⊆ §3.5 生成规则表 | — |
| §2.4 值域 ⟷ §3.5 分布 不矛盾 | q/k/v 声明 `(-∞,∞)` 但 §3.5 说 `(0,1)正态` |
| §2.4 值域 ⟷ §2.1 算法说明 不矛盾 | `text_length ∈ (0,∞)` 但算法说「按 0 处理」 |
| §3.1 声明的每个具体型号 ⊆ §3.3 性能表的型号 | 只写 910B3 |
| §2.4 出现的每个 tensor dtype ⊆ §3.2 阈值表的列 | — |
| §3.2 阈值数值 ⟷ `experimental_standard.md` 白名单 | 抄错阈值 |

### 5.2 明确性（词表 + 形态）

**模糊词黑名单按要素作用域生效，不做全文扫描。**

`「建议参考 https://...」` 出现在 §6 参考资料完全合法；出现在 §3.2 精度要求里
就是把硬标准写软了。骨架里 `vague_forbidden` 逐要素声明，避免误伤。

黑名单从样例真实缺陷提取：
`持平`、`基本一致`、`合理的`、`尽可能`、`视情况`、`酌情`、`较高`、`较低`、
`若干`、`原则上`、`适当`、`必要时`、`TBD`、`待定`、`TODO`、`xxx`。

形态类判据：

- §3.3 判据必须含比较符加数字（`≥0.8×` 合法，`持平` 不合法）
- §2.4 异常行为列不得全表同一句话
- §3.2 必须逐 dtype 给阈值，不能只写一句「满足生态标准」
- 非图片的 markdown 内联链接一律违规
  （一条规则同时抓住 checklist 顶部「链接必须裸露」和样例的未替换占位符）

### 5.3 xlsx 14 条人工检查项的归属

`任务书人工checklist.xlsx` Sheet1 的 14 条，逐条映射到骨架要素后分成两类：

- **已被机械判据覆盖**（第 1、3、5、6、7、9、10、11、14 条）：章节完整性、任务概述三要素、
  工程模式、接口定义、参数一致性、环境版本、性能逐型号、内存要求、PR 目录。
  这些不再需要人读，由 `check_taskdoc.py` 裁决。
- **仍需人读**（第 2、4、8、12、13 条的语义部分）：标题与任务发放纪要是否一致、
  算法逻辑是否正确、精度阈值是否覆盖所有输入场景、自验策略是否可行、交付件要求是否恰当。
  这些渲染进 `references/manual-checklist.md`，作为交付前的人工核对清单。

映射关系写进骨架（每条要素声明它满足 checklist 的第几条），
`render_views.py` 从骨架渲染 `manual-checklist.md`，两者不会脱钩。

### 5.4 完备性

`required: always` 的要素为空即红。`conditional` 先判条件：

- 随机算子信号词命中 → §3.2 随机策略变必填
- §2.3 参数序列与标杆接口不一致 → §3.5 对应关系变必填

## 6. 流程

```
T1 受理        算子名 + 已有材料 → 判定工程模式、对标基线、是否随机算子
T2 推断        agent 出候选（数学定义/签名/dtype 面/值域/错误场景/实现约束）
T3 拍板        按风险分批追问 → 答复原话入 decisions.json
T4 落稿        渲染骨架 md → agent 按 decisions 填内容
T5 质量门      check_taskdoc.py 跑到退出码 0 → 交付
```

### 6.1 T3 的批次划分

40 条要素里约 30 条需要人拍板，逐条问 30 轮不现实。按决策簇分 8 批，
每批 3-5 个相关项一次呈现：

| 批 | 内容 | 为什么同批 |
| --- | --- | --- |
| 1 | 工程模式 · 对标基线 · 代码仓 | 决定后面全部推断的前提 |

## 7. 量具

| 脚本 | 职责 | 退出码 |
| --- | --- | --- |
| `next_questions.py` | 算出还缺哪些拍板项、按风险排序、分批输出 | 0 |
| `probe_baseline.py` | 可选辅助证据：有 torch 时抓 `inspect.signature`，无 torch 优雅降级并标注 `provenance: model_knowledge` | 0（永不阻塞） |
| `make_taskdoc.py` | 从骨架渲染 md 脚手架（章节 + 表头 + §8 固定内容），一次性，此后 md 是唯一真相 | 0/2 |
| `check_taskdoc.py` | 唯一不可绕过的门 | 0/2/3 |
| `render_views.py` | 骨架派生 `manual-checklist.md` 等视图，维护者用 | 0 |

退出码对齐现有仓：`0` 全过，`2` 判据不满足（内容问题），
`3` 结构解析失败（md 不符合模板骨架，无法定位章节）。

### 7.1 门禁分层

```
L0 结构    章节齐全 · 表头列数 · 占位符残留 · 内联链接违规        → 3 或 2
L1 一致性  2.3↔2.4 · 2.4↔3.5 · 2.4↔2.1 · 3.1↔3.3 · 阈值↔标准     → 2
L2 明确性  作用域内模糊词 · 判据须含比较符+数字 · 异常行为不得同值 → 2
L3 拍板留痕 每个 human 要素在 decisions.json 有非空答复原话       → 2
L4 双受众  开发者族：交付件/PR/自验可执行                          → 2
           验收族：反填约束表 → acceptance_map.json，有待确认项即红
```

L4 验收族的产物 `acceptance_map.json` 是交给验收 agent 的接力棒——
它就是验收侧 S1 要填的那张约束表，提前填好了。

### 7.2 「不可绕过」怎么落地

光靠 SKILL.md 写「必须跑门禁」不够，agent 可能不跑还声称跑了。

**门禁通过时写 `evidence/gate_pass.json`，内含当前 md 的 sha256、时间戳、各层结果。**

交付物里没有 sha256 匹配当前 md 的 `gate_pass.json`，就是没过门。
这同时堵住第二个漏洞——跑完门禁又改了 md，sha256 对不上，当场露馅。

SKILL.md 的硬要求：交付前必须贴出 `check_taskdoc.py` 的完整输出含退出码，
且 `gate_pass.json` 的 sha256 与交付的 md 一致。

## 8. 测试策略

### 8.1 三组 fixture

**正向：每类缺陷一个最小 md**（`tests/fixtures/defects/`）

一个缺陷一个文件，断言门禁精确抓到那一条、不多抓。
整份 185 行样例当 fixture 会让定位困难，最小片段才有诊断力。

**回归：真实样例副本**（`tests/fixtures/real_sample.md`）

SlidingTileAttention 样例原样拷入（注明来源与拷贝日期，源不在本仓不做同步校验）。
断言门禁能解析不崩溃、抓出的缺陷清单与 golden 列表一致。

**反向：一份必须返回 0 的黄金任务书**（`references/golden-task-doc.md`）

这一组最重要。没有它，门禁可以靠「什么都判红」通过全部正向测试——
那是最容易写出来的假门禁。

黄金样例造法：拿 SlidingTileAttention 样例，把 §1.2 列出的全部缺陷逐条修好
（补 `windowSizeLen`、统一命名、`(-∞,∞)` 改成明确值域、「持平」改成 `≥0.8×`、
补 910B4、补 §2.5、修占位符和内联链接）。

它一石二鸟：既是防假红的测试锚，又是 `references/` 里给 agent 看的写作参考。
做这件事的过程本身会检验骨架——某条缺陷「修不了」，说明骨架缺了对应要素。

## 9. 落地顺序

```
0  素材归档 + defect-map.md（逐条缺陷 → 对应判据）
1  taskdoc-elements.json（40 条）+ test_elements_spine.py
2  task-doc-template.md（修复版模板）+ golden-task-doc.md（黄金样例）
                                              ← 反过来验证骨架完备性
3  check_taskdoc.py L0 结构 + L1 一致性 + 缺陷 fixtures
4  check_taskdoc.py L2 明确性 + L3 拍板留痕 + L4 双受众
5  next_questions.py + make_taskdoc.py
6  SKILL.md + references/（含从骨架派生的视图）+ skill 侧 CLAUDE.md
7  probe_baseline.py（可选，最后做，无 torch 也不影响交付）
```

第 2 步产出**两份**，不只是黄金样例：

- `task-doc-template.md`——修复后的**模板**。原始 v3.0 模板自身也有缺陷：
  填写要求写得含糊（§3.2「建议参考生态标准」把硬标准写成软建议）、缺 §2.5、
  §2.4 表头对每列该填什么只给了疑问句而非判据。
- `golden-task-doc.md`——修复后的**样例**，即黄金任务书。

第 2 步放在第 3 步之前是刻意的：先造出「什么叫合格」的实物，再写判据。
反过来做，判据会长成「刚好能通过实施者脑子里那份想象」的样子。

第 0 步的 `defect-map.md` 是第 3、4 步的输入：每条判据都要能指回它源自哪一条真实缺陷。
指不回去的判据是凭空设计的，要么删掉，要么补上它防的是什么。

## 11. 开发态

### 11.1 skill 侧 CLAUDE.md

`skill/repo-task-doc-write/CLAUDE.md` 是本 skill 的开发规则文件，
仓根 `CLAUDE.md` 加一行索引指向它。

内容分两类：

| 类别 | 来源 |
| --- | --- |
| **复用** | 行文与开发实现规则：文档行文风格、脚本命名与退出码约定、TDD 流程、遇到问题的查找顺序 |
| **重写** | 四条红线（见本文 §2.5，红线 1 不适用，A/B/C/D 是新的） |

复用的是**怎么写**（行文与实现规范），不是**写什么**（内容约束）。
后者每个 skill 自己推导，照搬会把 skill 写死。

复用的部分写成引用而不是复制：`详见 ../../CLAUDE.md §3.2`。
仓根 CLAUDE.md 每次会话都进上下文，复制一遍等于同一条规则在上下文里出现两次。

仓根 CLAUDE.md 需要同步改动的地方：

- §0 一句话：本仓从「一个验收 skill」变成「两个 skill」
- §4 文件结构：加 `skill/repo-task-doc-write/` 与 `docs/development/taskdoc-source/`
- 新增一行指向 skill 侧 CLAUDE.md
- 新增行文结构化规则的摘要与指针（见本文 §11.3）

### 11.2 素材归档的只读纪律

`docs/development/taskdoc-source/origin/` 下的文件是上游素材的拷贝，只读。

发现缺陷时**不就地修**，而是：在 `defect-map.md` 记一条（缺陷、位置、对应判据），
修复产物另存到 `references/`。这样「上游原样是什么」和「我们认为该是什么」
永远分得开，上游改版时能逐条重放。

归档时注明来源路径与拷贝日期。源不在本仓，不做自动同步。

### 11.3 行文结构化规则

两个 skill 共同遵循。规则正文写进 `docs/development/skill-development-principles.md`，
仓根 CLAUDE.md 放摘要与指针。

**问题**：现有文档遵循了短句、一行一句，但并列观点被堆成连续句子，
读的时候得自己在脑子里编号。实测验收 skill 有 14 处
（SKILL.md 13 处、`experimental_standard.md` 1 处）。典型形态：

```
只读取当前阶段的 reference。
reference 只提供该决策域的规范。
不通过链接追读其他 reference。
```

三条并列规则，没有任何视觉层级。

**规则正文**（给 agent 读，语义判断）：

1. 并列观点 ≥2 条就结构化，不要堆成连续句子
2. 无先后关系用 `-`，有先后或步骤用 `1. 2. 3.`
3. 一条一行，前面补一句领起句说明这是在列什么

**机械判据**（脚本，只抓高置信子集）：

- 连续 ≥3 行、每行以「。」结句、且不是列表/表格/标题/引用 → 红

判据为什么用「行末是不是句号」：朴素做法「连续 3 行短句就该加项目符号」
误报率约一半，因为软换行的一句话也是连续三行。两者唯一可机械区分的地方在行末——
软换行的行末是逗号、顿号、破折号或半个词，独立并列句每行自己收「。」。
实测 14 处命中全部为真并列，无误报。

**脚本抓的是子集，不是全部。** 它抓不到只有 2 条的情况，
也抓不到软换行写成的并列。语义判断的责任在 agent，
规则正文必须写明这一点，否则下一个人会以为「脚本没红就是合规」。

**存量豁免白名单**：验收 skill 已有的 14 处进白名单，不阻塞本次实施；
新写的一律红。白名单就是待办清单的机器可读版本，改一处删一条，删空即还清。
同一份待办以文件加行号的形式记进 `skill/repo-task-atk-test/CLAUDE.md`。

## 12. 未决与风险

| 项 | 风险 | 缓解 |
| --- | --- | --- |
| parser 依赖模板稳定 | 社区模板改版 → parser 失效 | 章节号和表头列写进骨架，改版只改骨架；`test_real_sample_regression.py` 会先红 |
