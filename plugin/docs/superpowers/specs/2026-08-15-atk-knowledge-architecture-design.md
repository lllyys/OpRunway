# ATK 验收 skill 知识架构设计（终版）

日期：2026-08-15
范围：S1–S5 全链路的知识组织方式，重心在 S2–S4 的「配套产物生成」
证据：远端会话 `9e20e8c7`（roll 验收，15:16–16:05，398 次工具调用）+ 仓库现状审计

---

## 0. 一句话

把 skill 从「按事故索引的文档集合」改成「按产物契约索引的单一骨架 + 派生视图」，
让完备性可枚举、一致性由结构保证、关键要领在阶段入口自动送达。

---

## 1. 诊断：一种病，四层表现

前几轮反复「补完了，下轮还是漏」，不是补得不够，是**四层都按事故索引**。

### 1.1 文档层

11 份 reference 按主题分，每次跑测发现一条事实就塞进最近的文件。

没有任何一处回答「这个阶段要产出几样东西、每样几个字段、每个字段的规范写了没有」。

完备性因此不可判定——只能等下一次真机跑测来告诉你还缺什么。

证据：`tuple_numbers` 是 `scripts/make_yaml.py:181` 亲手写进 YAML 的字段，
在 SKILL.md、11 份 reference、7 份模板里出现 0 次。

### 1.2 测试层（本次审计新发现，也是最关键的一条）

`tests/test_document_style.py` 27 条测试，形态是这样的：

```
test_case_output_path_is_documented
test_soc_declaration_gate_is_terminal
test_atk_hardcoded_upper_border_trap_is_documented
test_removed_reference_names_do_not_return
```

**一次事故一条字符串断言。**

这套测试能防止已知条目被删（有价值，本项目确实两次在精简中删掉过验证过的修复），
但它**结构上无法发现缺失**——它只知道「原来写的还在」。

这解释了「每次都声称做好了」：测试全绿是真的，测试覆盖的是历史事故的并集，不是应有知识的全集。

**v2 方案正要再造第四个这样的产物。** 终版据此重构。

### 1.3 事实层与模板层：各自正确，合起来失效

最贵的两次失败，所需事实都早已在 skill 里，只是不在做决定的那一刻。

**S2 的空组**：L0 有 `group_min_length: 1`，`plugin-authoring.md` 有
「不要把缺省参数表示为空的复合输入组」。但后者是写插件时才读的文件，
而空组是在 decl 设计期定死的——代价是推翻 decl、拆双分面、重写三个文件。

**S3/S4 的基线绑定**：L0 有 `binding: name=null → args；non-null → kwargs`，
模板注释有「形参名必须和基线函数签名一致」。
但没有任何一处在 S2 命名输入时说：**YAML 输入名必须等于基线函数形参名**。
agent 命名成 `x`（基线是 `input`），kwargs 绑定必然 TypeError，
它改用 `input_data.args`——而 args 恒为空。
代价：读 ATK 源码 11 次，改插件 3 次，一次全量跑测 42/81 失败。

四层各自正确，合起来仍让 agent 走进死路。**没有绑定，就没有一致性。**

### 1.4 补偿静默：缺陷永不冒头

本轮读 ATK 框架源码 34 次、读 skill 自身量具源码 64 次、手工拼环境前缀 29 次。

每一次都当场解决了问题，任务继续往前走，skill 从不知道自己缺过这一条。

## 3. 设计目标

- **可判定**：知识是否完备，改完当场知道，不靠下一次真机跑测
- **可同步**：改任一层（事实/规范/模板/量具），其余层不同步就红
- **准时送达**：关键要领在阶段入口出现，不靠 agent 记得去翻
- **可观测**：每一次「靠自己补上」都留下结构化痕迹

## 4. 架构

### 4.1 单一骨架：产物契约登记表

v2 曾打算并列做三张表（作战卡、决策点清单、字段矩阵）。三张表描述的是同一件事的三个切面，
并列维护必然漂移，且会变成第四个按事故索引的产物。

终版改为**一个骨架 + 三个派生视图**。

骨架是 `references/artifact-contracts.json`：全链路产物的封闭清单，每样产物逐字段登记。

```
artifacts:
  <op>_decl.json:
    stage: S2
    owner: agent                    # agent 手写 / 脚本产出 / ATK 产出
    template: assets/example/decl.json
    spec: references/case-design.md#必测集契约
    consumed_by: [make_must_cover.py]
    fields:
      operator_class:
        owner: agent
        source: 任务书算子类别
        consumer: _coverage_strategy 选默认轴与交互组
        failure: 未知类别 → make_must_cover 退出码 2
```

四个字段级属性对应四个必须回答的问题：**谁写、依据什么写、谁消费、写错了什么时候怎么炸。**

第四个属性把 late binding 显式化——报错文本可以反查条目，这正是本轮最缺的东西。

封闭清单（先钉死，再展开）：

- S1：约束表、`env.json`、`env.sh`
- S2：decl、物化脚本、`must_cover.json`、materialized、YAML、生成器、基线插件、
  aclnn 执行器（条件性）、冻结输入
- S3：manifest、SoC/op_api 绑定报告、冒烟日志
- S4：accuracy / performance results、`verdict.json`
- S5：报告、复现包

**清单封闭是完备性可判定的前提。** 清单不封闭，一切退回「等下轮跑测」。

### 4.2 视图一：阶段作战卡（S1–S5）

SKILL.md 内联五张，槽位固定不随算子变：

| 槽位 | 内容 |
| --- | --- |
| 核心 | 一句话：本阶段把什么变成什么 |
| 产出物 | 每行一样：文件名 / 关键点 / 规范去哪读 / 模板或量具 / 炸点 |
| 先查后写 | 本阶段该用 `atk_lookup.py` 查的主题名（只列主题，不列答案） |
| 出口门禁 | 门禁名，与脚本退出码语义一一对应 |
| 不做的事 | 本阶段越界动作 |

卡不承载规范正文，只承载地图与雷区。它消灭三种摸索：
不知道要产出什么、不知道规范在哪、不知道哪一步会炸。

### 4.3 准时送达：`mark_step.py` 渲染当阶段卡

卡写在 SKILL.md 是「开场一次性给全」，不等于「在合适的时机知道」。

`mark_step.py <n>` 已经是阶段打点的必经动作，让它**从骨架渲染并打印第 n 阶段的卡**。

于是关键要领在阶段入口再次出现，只花当前一张卡的上下文，且由骨架渲染，不可能与规范脱节。

这是「一把手流程」的落点：流程推进动作本身携带该阶段的作战指令。

### 4.4 视图二：决策点清单

骨架里 `owner: agent` 的字段全集，就是 agent 必须自己判断的决策全集。

由脚本渲染成 `references/decision-points.md`，四列：决策、判据来源、查询方式、判错的表现。

**一个决策没有判据来源，就是一个洞。** 可枚举、可审、可增量补，不必等真机跑测发现。

初始条目来自三轮真机跑测（median / huber_loss / roll）的全部失败点。

### 4.5 视图三：一致性锁 —— 用结构不变量替代事故断言

这是回应「实施、模板、量具必须强一致地改」的机制，也是对 §1.2 那 27 条事故断言的修正。

区别是根本性的：

- 事故断言：「关于 SoC 门禁的那句话还在吗」——只对已发生的事有效
- 结构不变量：「骨架里每样产物都有 template 或标注无需模板」——对未来的新产物同样有效

四条不变量：

| 锁 | 断言 | 谁不同步就红 |
| --- | --- | --- |
| L1 骨架↔量具 | 量具导出的字段常量 == 骨架登记的字段 | 量具加字段没登记；登记了量具不认 |
| L2 骨架↔卡 | 每阶段骨架产物 ⊆ 卡产出物 ⊆ 骨架产物（双向） | 加了产物没进卡；卡里写了不存在的产物 |
| L3 模板↔事实 | 模板中 `# [L0:key]` 引用的键存在，且值未变 | L0 值变了模板没跟着改 |
| L4 骨架↔规范 | 每个 `owner: agent` 字段的 `spec` 锚点可解析 | agent 要自己判断却没有规范 |

关键设计：**L1 的字段常量必须是"活的"**——脚本自身用它做未知键检测或输出组装，
不是纯给文档看的常量。否则常量本身会变成第二份需要同步的东西。

副产品：`make_must_cover.py` 因此获得 decl 未知键检测，写错键名当场报，不再静默忽略。

现有 27 条事故断言的处置：能被四条不变量覆盖的删除，
编码了一次性事实（如某个阈值表必须保留）的保留并标注为「不变量无法覆盖」。

### 4.6 规范按可执行性分层

SKILL.md 的「工作边界」现在是 40 行单句祈使。CLAUDE.md §3.3 已指出：
反复用 MUST/NEVER 强调同一条，说明 why 没讲清。

架构上的修法是按**可否被量具检查**切分：

- 量具能查的（冻结后不得重生成、分母口径、常量张量、所有 ATK 任务经 `run_atk_task.py`）
  → 移进量具，正文只留一行「由 X 门禁保证」
- 量具查不了的（不读被测源码、不用实现补充验收知识、推断项先标记）
  → 留在正文，篇幅缩短后注意力反而集中

正文只写不可机检的纪律，是让剩下那几条真正被读进去的唯一办法。

### 4.7 环境前缀：`evidence/env.sh`

手工拼环境 29 次、同一错误重复 2 次，成因是每个 Bash 都是新 shell 而 skill 没给载体。

`probe_env.py` 增产 `evidence/env.sh`：CANN `set_env.sh`、vendor `set_env.bash`（S3 安装后追加）、
`ATK_CUSTOM_OPP_PATH`、`TORCH_DEVICE_BACKEND_AUTOLOAD=0` 等本机实测必需项。

所有命令模板统一改成 `source evidence/env.sh && cd <绝对路径> && ...`，顺带解决 cwd 泄漏。

`env.sh` 同时固化 skill base dir——本轮压缩后 agent 用 `find` 现找，跑到了 08-14 的陈旧副本上。

### 4.8 无知上报：`evidence/knowledge_gaps.json`

- `atk_lookup.py` 查不到的主题即 skill 缺陷，先登记，再读 ATK 源码
- 读完必须回填：主题、问题、结论、源码位置、阶段
- S5 报告列出全文，作为下一轮回流清单

强度**只记录不拦**：读源码是正当兜底，硬门禁会把正常验收变成阻塞，
且与「验收执行期间不改 skill」的现行纪律冲突。

回填条目下一轮优先进决策点清单，而不是直接塞进某份 reference——
这是防止 §1.1 那个病复发的关键动作。

## 5. 适配器专章

三类适配器本轮全部出过问题，而 skill 对它们的支持强度极不均衡。

| 类 | 文件 | 接线字段 | 本轮问题 |
| --- | --- | --- | --- |
| 生成器 | `<op>_constraint.py` | YAML `generate` | 复合组长度、组是 list，崩 3 次 |
| CPU 基线 | `function_<op>.py` | YAML `api_type` | args/kwargs 绑定、容器形态，崩 3 次 |
| aclnn 执行器 | 同文件或独立 | YAML `aclnn_api_type` | typed null 指针，S3 冒烟才发现 |

共同特征：**接线字段都在 YAML 里，而 YAML 在 S2 末冻结。**

### 5.1 核心规则：适配器判定必须在 S2 完成

`align_signatures.py` 已经产出判定所需的全部输入：
`baseline_adapter.required`、`aclnn_adapter.required`、`semantic_review`。

本轮 `semantic_review` 明确预言了「dims 置空需 typed 空指针适配器」，
agent 判断「S3 冒烟再说」，于是 S3 才发现、才改 YAML、才与冻结纪律撞车。

规则：**`semantic_review` 每条条件性预警，必须在 S2 对照用例集实际取值判定**——
触发条件存在就当场写适配器并接线；不存在就记录「已判定不触发」及依据。

判定表进 `plugin-authoring.md`：预警类型 × 怎么在用例集里验证触发。

### 5.2 例外出口：`rewire_adapter.py`

运行期类型校验这类问题确实可能只在 S3 暴露，给一条受控通道，不让 agent 自己发明。

脚本职责：patch YAML 接线字段 → 重跑 `atk case` → 逐字段 diff 新旧 case JSON →
断言只有接线字段变化 → 核对冻结输入 sha 未变 → 写留痕。

不满足即退出码非 0，视为需回 S2 重做。

这把本轮 10 次手工自证变成一条命令，同时保住冻结纪律的实质：用例语义未变，只换执行器接线。

### 5.3 冻结门禁补基线核验

冻结那次跑测基线已经全线失败，门禁只核输入落盘就放行，错误推迟到 S3 才炸。

修复：冻结时解析同一次跑测日志，基线节点失败数非零即退出码非 0。

纯量具修复，不涉算子专属逻辑。

### B. 缺陷（按证据定级）

| # | 级 | 事项 |
| --- | --- | --- |
| B1 | P0 | `evidence/env.sh` + 命令模板绝对路径 + skill base dir 固化 |
| B2 | P0 | 基线绑定规则：YAML 输入名 == 基线形参名（决策点 + 模板 + `make_yaml` 校验） |
| B3 | P0 | `freeze_inputs.py` 补基线执行核验 |
| B4 | P0 | 适配器 S2 判定规则 + `rewire_adapter.py` |
| B5 | P0 | 「可变长复合组」知识域（L0 + 决策点 + 模板） |
| B6 | P1 | 可表达性判定前移到 `make_must_cover.py` |
| B7 | P1 | 补事实：执行期报告路径、能力报告 sha 依赖、构建入口可能在上级仓 |
| B8 | P1 | 物化脚本通用化（CLAUDE.md §10.6 未落地，本轮又赔 2 次） |
| B9 | P2 | `probe_env.py` 补 chip / op_commit |

新增知识域「可变长复合组」的三条事实，全部 B 级（源码 + 实跑双确认）：

- 组长度来自 YAML `tuple_numbers`，ATK 每条用例随机抽取，与 combo 顺序无关
- `case.inputs[i]` 对复合组是 `list[InputCaseConfig]`，不是单个对象
- 组长度下限为 1，空组不可表达

设计期规则：**per-combo 长度变化的复合组，必须在生成器里重建组**。

### 不做

- 不改 `atk/` 源码
- 不为 roll 写任何算子专属逻辑（CLAUDE.md §3.1 泛化红线）
- 不做骨架的全自动生成——`owner: agent` 的字段本就无法从代码反射，硬做会退化成假登记

## 8. 验证方式

四条可执行判据，前三条防漂移，第四条是唯一的真实检验：
