# repo-task-doc-write 方案设计

把需求方的口头要求整理成一份合规、无歧义、可验收的社区算子开发任务书。

任务书是两份契约合成的一份文档：对**外部开发者**划定开发范围、实现约束、交付件与
提交位置，对**验收 agent** 是全部验收约束的唯一来源。两个受众都不满足的内容不该出现。

设计目标是**让每一条推断都有人拍板**。撰写发生在算子开发之前，不依赖真机或 torch，
agent 给的候选没有一条能在本机实证，所以人的判断是唯一可靠的把关点。

## 五个阶段

| 阶段 | 做什么 | 出口 |
| --- | --- | --- |
| T1 受理 | 收算子名与已有材料，定工程模式、对标基线、是否随机算子 | 前提三项已拍板 |
| T2 推断 | 给候选：签名、dtype 面、值域、错误场景、实现约束 | 候选成文，标注 provenance |
| T3 拍板 | 按八个批次追问，答复原话入 `decisions.json` | `next_questions.py` 报 done |
| T4 落稿 | 渲染脚手架，按 decisions 填内容 | md 全部章节非空 |
| T5 质量门 | `check_taskdoc.py` 跑到退出码 0 | 封条 sha256 匹配交付的 md |

T3 的八个批次按依赖排序：前提 → 接口 → 类型与排布 → 形状与值域 → 异常行为 →
实现约束 → 精度 → 性能。前一批没定完不问后一批，避免拍板结果互相推翻。

## 四条红线

验收 skill 的「不拿算子实现当验收依据」在撰写阶段不成立——写任务书时算子还不存在，
对标实现恰恰是必须读的合法依据。撰写侧重新推导的四条：

| 红线 | 内容 | 破了会怎样 |
| --- | --- | --- |
| A | agent 推断不是事实，全部推断项必须人拍板并留答复原话 | 任务书写着一堆没人负责的约束，错到最后才发现 |
| B | 社区模板章节号只做加法，不重编号 | 存量任务书与交叉引用全断 |
| C | 门禁不可绕过，`gate_pass.json` 用 sha256 封住当前 md | agent 声称跑过门禁，或跑完又改稿 |
| D | 黄金任务书必须真的返回 0 | 门禁靠「什么都判红」通过全部正向测试 |

## 产物与边界

交付三样：**任务书 md**、**`decisions.json`**（每条约束的拍板原话与出处）、
**`evidence/gate_pass.json`**（封住交付版本的 sha256）。

下面两种情况不适用：

- 算子已经开发完，只想补一份文档 —— 本流程的价值在开发前定约束
- 没有人能拍板 —— 红线 A 决定了流程会卡在 T3 不动
