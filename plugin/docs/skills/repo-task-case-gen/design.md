# repo-task-case-gen 方案设计

按任务书生成、校验、冻结并封印 ATK 用例，不需要 NPU。

设计目标与验收侧一致：**驱动零上下文的 AI 助手独立完成自己负责的阶段。**
生成侧只读任务书，不读待验收工程，也不绑定某个 PR。

## 阶段

生成侧负责 S1–S2，出口是可复用的封印交接包。

| 阶段 | 做什么 | 出口 |
| --- | --- | --- |
| S1 任务书解读 | 推导约束、接口与 CPU 环境事实 | 待确认项清零，证据齐全 |
| S2 用例生成 | 生成必测集、YAML、适配与输入 | 门禁全过，输入冻结 |
| 封印 | 核对产物并计算 SHA256 | `evidence/bundle.json` |

可表达性在 S1 检查，基线绑定在 S2 冻结前检查。问题越早暴露，返工越少。

## 边界

生成侧遵守以下边界：

- 签名只来自任务书 §2.3，dtype 只来自 §2.4
- 任务书写不清就形成待确认项，不去工程里补答案
- 每个接口分面只运行一次 `atk case`
- S2 封印后不再修改用例、YAML、约束器或冻结输入
- 判据由量具从数据推导，不接受“我检查过了”

四条架构红线、骨架与共用件纪律见
[开发规则](../../../skill/repo-task-case-gen/CLAUDE.md)。

## 与验收侧的交接

交接包是两侧唯一接口。它包含任务书摘要、ATK 版本、接口事实、冻结输入与全部文件摘要；
同一任务书生成一次后，可以为不同 PR 各复制一份进入验收。

验收侧先复制原包，再用 `check_bundle.py` 重算摘要并核工程接口。封印失败留在生成侧；
封印成功后的构建、NPU 环境与精度性能问题交给
[repo-task-atk-accept](../repo-task-atk-accept/design.md)。

上手步骤见 [quickstart.md](quickstart.md)。
