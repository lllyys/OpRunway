# repo-task-atk-test 方案设计

用 ATK 测社区算子，判定精度与性能是否满足任务书要求。

设计目标只有一个：**驱动零上下文的 AI 助手独立跑完端到端验收。**

助手不预设背景知识，所有判据从数据推导，不靠它自称检查过。

## 流程为什么分五段

每段有固定出口，出口产物不齐不进下一段。分段依据是「失败在哪一段暴露最便宜」。

| 阶段 | 做什么 | 出口 |
| --- | --- | --- |
| S1 任务书解读 | 把任务书变成可核验的约束，记录本机环境 | 约束表 + 环境与接口证据 |
| S2 用例生成 | 产出测试配置、用例与跑测适配 | 冻结输入的 SHA256 |
| S3 编译安装部署 | 构建并安装待验收算子 | 一条冒烟测试真的跑通 |
| S4 精度性能测试 | 跑全量，裁决精度，记录性能 | accuracy / performance 结论 |
| S5 输出测试结果 | 给报告、结论与可复现包 | 换台机器能重跑 |

三处检查被刻意前移：可表达性从 S4 提到 S1，基线绑定从 S3 提到 S2，环境检查从
S1 提到 S0。平均省掉两个阶段的返工。

## 两种入口

父 skill 按已有输入选择下面一侧，两侧共用量具与知识，只通过交接包传递产物。

| 入口 | 输入 | 环境 | 阶段 | 出口 |
| --- | --- | --- | --- | --- |
| `repo-task-case-gen` | 任务书、形态、基线 | CPU：Python、ATK、torch | S1–S2 | 封印交接包 |
| `repo-task-atk-accept` | 交接包、工程、任务书、device、CANN | NPU + CANN | S0、S3–S5 | 裁决与报告 |

生成侧只读任务书，因此交接包不绑定某个 PR。原始交接包保持只读，每个 PR 各复制一份进入
验收侧，同一份任务书据此只需生成一次用例。

## 四条红线

这四条决定了流程的形状，修改流程时不可违背。

| 红线 | 为什么不可退让 |
| --- | --- |
| 不拿算子实现当验收依据 | 算子是被检验的对象，用它推导测试配置是循环论证 |
| ATK 只读 | 它是指向上游的子模块，改一行就把本仓与上游的偏离带进提交 |
| S2 之后输入不可变 | 冻结防的是拿测试配置去迁就算子的实际表现 |
| 助手的声明不作数 | 判据一律从数据推导，「我检查过了」不构成放行依据 |

两侧如何落实四条红线见[拆分设计 §2.6](../../superpowers/specs/2026-08-20-atk-skill-split-design.md#26-四条红线在两侧的形态)，
此处不复制对照表。

第一条禁的是**实现**，不是工程。待验收工程的头文件声明、README、构建入口照读——
公开接口面是签名对齐的唯一合法来源，去 CANN 装机目录找同名接口会拿到另一份代码。
禁的是 kernel 计算逻辑、tiling 分支、内部断言这些实现细节。

## 产物与边界

验收结束后工作目录里有三样：**结论**（精度与性能是否达标）、**证据**（环境指纹、
接口事实、冻结输入的校验和）、**复现包**（换台机器可重跑本轮验收）。

下面三种情况不适用：

- 没有任务书 —— 精度与性能的判据全部来自它，没有它无法验收
- 算子还没开发完 —— 先用 `repo-task-doc-write` 把任务书写出来
- 只想跑一次功能测试 —— 五阶段的开销不划算
