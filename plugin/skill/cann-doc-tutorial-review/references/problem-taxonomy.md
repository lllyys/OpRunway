# 问题分类（3 大类 × 7 错误类型 · finder 检查清单）

每条问题 = 一个 `sub`（错误类型细类，S1–S7，必填）+ 两根正交轴（`impact` 严重度 / `verdict` 确定度）。
**大类由细类自动决定，finder 不用单独填。**
**本轮舍弃 `minor`（瑕疵不查不报），只产 blocker / misleading。**

> 旧版 S6 是「讲不清/缺必要信息」二合一，现拆成 **S6 内容描述不清晰** 与 **S7 关键信息要素缺失**——
> finder 必须二选一：读者「读不懂/看不懂」→ S6；读者「信息不齐、做不下去」→ S7。

## 分类的第一原则：按「靠什么坐实」分大类

不按「错在哪种文档元素」分，按**这条缺陷拿什么来判定**分。好处：大类一确定，**结论能到多硬（确认 / 疑似）就自动确定了**，读者一眼知道该不该信、要不要人工复核。

| 大类 | 判据 | 含错误类型（细类） | 结论能到多硬 |
|---|---|---|---|
| **对不上代码** | 照做与代码/脚本不一致 | S1 文档接口声明与代码不符 · S2 文档示例代码不符合预期行为 | **可确认对错** |
| **文档内部缺陷** | 不用翻代码，读文档即可判定 | S3 引用或路径失效 · S4 同源文档内容冲突 | **可确认对错** |
| **讲得不到位** | 概念或讲法存疑，需领域判断 | S5 概念/术语讲错 · S6 文档内容描述不清晰 · S7 关键信息要素缺失 | **最多「疑似」，需人复核** |

## A. 对不上代码（客观 · 对照代码可下「确认对不上」）

- **S1 文档接口声明与代码不符** — 文档写的文件名 / 命令 / 参数名 / 函数签名 / 数据类型表 / schema / **产品支持表的 √×** / 版本·SOC·分支适配声明，与代码真实定义或注册不一致。
  **多列代码不支持的类型、用错名、假 √（标支持但代码没注册）= 阻断；漏列代码已支持的 = 瑕疵（本轮不报）。**
  *（合并自旧 C2 命名/接口 + C5 支持范围——两者本质都是「文档声明的契约 ≠ 代码实际契约」，旧分法在 dtype 表上必然撞车。）*

- **S2 文档示例代码不符合预期行为** — 贴出的代码片段语法/拼写错、段内「声明」与「使用」对不上；或文档说「运行后生成什么 / 在哪 / 应看到什么输出」、具体数值 / 公式 / 行为，与脚本·代码实际不符。
  **只有标称「粘贴 / 替换进某文件」的【规定式】片段、照做真编不过才升 blocker；【示意式】片段（教写法 / 给例子，读者会自然适配）变量名 / 签名对不上 → 至多 misleading、通常不报**（灵魂③，先 steelman「真会照贴被卡住吗」）。
  *（合并自旧 C3 片段自身错 + C6 运行结果/数值/行为——两者都是「照着这段执行，结果对不上」。）*

## B. 文档内部缺陷（客观 · 光读文档即可判定，不必翻代码）

- **S3 引用或路径失效** — 超链接 / 章节锚点失效或点过去是无关内容；文档点名要参考 / 进入的文件 / 目录在仓内不存在。*（旧 C1）*
  > **本地克隆护栏**：目标越出仓根（跨仓/上级文档集引用）、落在未 `init` 的 **git submodule**、或命中 **git-lfs**（`filter=lfs`）而本地没拉取——这三种都是「本地没拉全」，不是文档错，**不报 / 只降级**（详见 `static-checks.md`）。
- **S4 同源文档内容冲突** — 同一篇 / 同算子多篇文档对同一事物说法不一致。*（旧 C4）*

> S3 与 S4 归一类的理由：**都不需要读代码逻辑就能修**（只需查文件树 / 比对文本），对维护者是同一种活。

## C. 讲得不到位（教学判断 · 先 steelman，最多「疑似」）

- **S5 概念/术语讲错** — 把原理讲反，或用了和框架同名、容易混淆的说法。**需外部反证（仓内实现 / 官方文档 / API 语义）才升「确认讲错」，否则只能「疑似概念风险」。** *（旧 J1）*
- **S6 文档内容描述不清晰** — 文字在、读者却看不懂：措辞含糊、前件不对、规则表述有歧义、逻辑跳步（读者「理解不到」）。*（拆分自旧 J2 的「讲不清」）*
- **S7 关键信息要素缺失** — 少了必要步骤、没交代前置条件 / 工作目录 / 前提、指代「这个 / 那个文件」却没说哪一个（读者「信息不够、做不下去」）。*（拆分自旧 J2 的「缺必要信息」）*

## 两根正交轴 + 判定纪律

- **impact**（严重度，按「后果 + 方向」定，**不机械按细类映射**）：
  `blocker` 照做会失败（编不过 / 步骤扑空 / 选到用不了的芯片·类型）> `misleading` 困惑但能恢复（死链 / 同篇矛盾 / 示例输出贴错）> `minor` 几乎无后果（**本轮舍弃不报**）。
- **conf**（确定度，bool）：`true` 确认（有强证据坐实）/ `false` 疑似（线索级，需人工复核）。
  **大类 C（讲得不到位）永远 conf=false**，除非有外部反证。
- **三态（对照代码时的结论）**：`确认对不上`（强证据反证）/ `疑似`（静态没找到但可能生成/外部/分支）/ `未找到静态证据`（存疑不指控）。

## 落类判据（互斥）

- 文档说的东西 **≠ 代码里的** → 看是「静态契约」还是「可执行的」：契约类（名字/签名/dtype/支持表）= **S1**；可执行类（片段/命令/产物/数值/行为）= **S2**
- **不用开代码库就能发现** → 找不到 = **S3**；前后打架 = **S4**
- **需要领域判断才知道对不对** → 讲错了 = **S5**；看不明白 = **S6**；信息不够做不下去 = **S7**
- 同一原文有多个问题 → 按**最小可修复事实**拆条

## 报前自问（减少「瑕疵级误报」，比机械对照优先）

报任何一条（尤其 misleading）前过这道闸，**只有读者会被实际卡住才算缺陷**；「字面对不上但读者自然能对上」不是缺陷：

1. **读者会不会照做？** 只是示意 / 演示、读者自然会适配 → 不报（灵魂③）。
2. **读者会不会按错 / 找不到 / 误解而做错？** 会 → 报；纯字面不一致、读者扫一眼就懂（如文件名少个空格、示例变量名换了个）→ **瑕疵，不报**。
3. **是不是只是风格 / 排版 / 术语不统一？** 是 → 不报（本轮连 minor 都舍弃，只产 blocker / misleading）。
4. **教学条（S5/S6/S7）先 steelman**：有没有一种读法这里没问题 / 上文已给依据？有 → 不报。

反例（看着像错、实际是瑕疵，别报）：同篇文件名 `trace.json` vs `trace_core0.json` 这种读者能自然对上的微差、术语中英混用但上下文无歧义、代码块缩进、锚文本少个词——**默认不报**；只有该不一致真的会让读者选错文件 / 跳过一步才升 misleading。

## 已实测的判定陷阱（照做会造成规模化伪问题，别踩）

下面每条都在真仓上量过，不是推测。**看着像"对不上代码"、实际不是**：

| 别这么判 | 为什么错 | 实测代价 |
|---|---|---|
| `op_list.md` 的 **op_kernel/op_host/op_api/op_graph 四个 ✓✗ 列** ↔ 同名目录是否存在 | 算子的 aclnn/kernel 实现**可以由别的算子承接**（`dir_structure.md` 明说"若缺少 op_host 目录，可能是调用了其他算子 op_host 实现"）;`op_graph/` 里只有一个 `proto.h` 也不等于支持图模式调用 | 单仓实测 **316 条全伪** |
| 「产品支持表标 √ 但 `_def.cpp` 没 `AddConfig(该 arch)`」→ 判假 √ | **`AddConfig` 是本仓构建面，不是产品支持面**——老芯片常由 CANN 发布包里的 binary 承接。实例：`activation/fast_gelu` 文档标 950/A3/A2 全 √，代码只有 `AddConfig("ascend950")`，全目录搜不到 `ascend910b` | 每个此类算子稳定产 2 条 blocker 级伪问题 |
| dtype 表 `BFLOAT16` ↔ 代码 `ge::DT_BF16` 视作不一致 | 文档名与 `ge::DT_*` 枚举名本就不同形 | 逐算子误报 |
| 文档里任何 ``` 目录树都拿仓根去解析 | `docs/README.md` 的树以 `docs/` 为根、开发指南的树以**算子目录**为根——先判树根再比对 | 4 仓 213 条 → 加"仓根锚定"闸后剩 4 条（全真） |
| 判「死锚」只认 markdown 标题 slug 为靶 | 显式 HTML 锚点也是合法跳转靶：`<a name="…">`（topic 转出）与任意元素的 `id="…"`（如 `<div id="op_host/{op}_def.cpp">`） | 每仓 2–8 条伪 |

## 本地克隆造成的「假死链/假缺失」（linkcheck 已设护栏，finder 手查也别踩）

| 看着像死链/缺文件 | 实际是 | 该怎么做 |
|---|---|---|
| 链接 `../..` 爬出**仓根**、指向上级/兄弟仓的文档 | 发布态是完整文档集，本地只克隆了单仓快照 | 越出仓根 → 降 `SUSPECTED/minor`（linkcheck 默认如此），不写「确认死链」 |
| 目标在 **submodule** 目录里但本地是空的 | 忘了 `git submodule update --init` | 命中 `.gitmodules` 前缀 → 跳过 |
| `.png/.bin` 等文件缺失 | 该仓用 **git-lfs**，克隆没拉 LFS 内容 | 命中 `.gitattributes` 的 `filter=lfs` → 跳过 |
| 目标在 build / 生成目录 | 产物 build 后才有 | 不按字面判，标「疑似产物路径」 |

> 共同教训：**先证伪自己的检查，再相信结果**。一个"22% 的文档都错了"的结论，几乎总是检查口径错了，不是文档错了。看到某仓大量死链/对不上时，先怀疑是不是本地克隆不全，再怀疑文档。

## 三条灵魂

① **不打玄学分** —— 主观判断（大类 C）先 steelman 再 flag，报则必带判例。
② **grep 不到 ≠ 编造** —— 走三态，只有强证据才写「确认」。
③ **按实际开发者影响判，不按机械字面对照判** —— 示意 ≠ 规定（见 S2）。
