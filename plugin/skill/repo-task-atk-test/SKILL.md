# ATK 社区算子验收入口

## 按输入选子流程

这个 skill 有用例生成与测试验收两个子流程。只根据手上已有的输入选一侧，
进入后按子页完整执行。

| 手上的输入 | 进入哪个子流程 |
| --- | --- |
| 只有任务书 | 读 [case-gen/SKILL.md](case-gen/SKILL.md) |
| `atk-case-<op>/` 交接包、工程目录和任务书 | 读 [acceptance/SKILL.md](acceptance/SKILL.md) |
| 两者都没有 | 停下来，询问用户要生成交接包还是执行验收 |

## 两侧通用规则

分面、物化、接线字段、能力域这些词在各 reference 里反复出现，动手前先读
[references/glossary.md](references/glossary.md)，一页读完。

不要修改待验收算子源码、构建脚本或编译产物。
验收 YAML、插件、证据和报告不属于待验收对象。

其他算子的验收目录（如 `atk-verify-<op>/`）不是证据：它们的接线、取值和
结论没有经过本次门禁，"先例通过了"不能替代读懂一条判据或规则。确有共性
经验要复用，先把它写成 reference 或量具规则，再照规则走，不要直接抄产物。

`scripts/` 是量具。发现脚本缺陷时停止当前轮次：改量具要经得起回归测试——
补一条复现缺陷的用例，并在至少两个不触发该缺陷的既有基线/算子上验证
没有引入新的误判，全部过了才算修复，然后重跑受影响阶段，把改动和验证记入证据。
说不清「为什么没引入新误判」就不要动 `scripts/`：记录为已知问题，
剔除受影响用例并留痕，不要为了让当前用例通过而悄悄改判据。

覆盖、精度和性能判据必须能追溯到任务书、已确认基线或生态标准。推断项先标记并请求确认。

所有数字由脚本产生。模型只组织证据和文字，不人工重算通过率、覆盖率或性能选样。

## reference 和脚本规则

读 reference 时遵守以下边界：

- 只读取当前阶段的 reference。
- reference 只提供该决策域的规范。
- 不通过链接追读其他 reference。

`references/artifact-contracts.json` 是量具读的骨架，卡和检查点清单都从它渲染。
不必打开它：卡和 `gate_lookup.py` 已经把里面的话按需送到眼前。唯一没有
别处可查的是产物依赖链（`consumed_by`，谁消费这件产物），确实要查那个再打开。

脚本参数以脚本自身 `--help` 为准。版本不兼容时只核对实际子命令。
不要使用裸 `atk`。始终使用环境指纹中的绝对 CLI 和同一 Python。

常用入口见各阶段 reference。不要在主技能中复制脚本参数。

## 上下文被压缩后

不要凭摘要往下写，也不要把读过的 reference 重读一遍。跑
`scripts/probe_progress.py -C <工作目录>`：它会判定当前在哪一侧，并指出下一步。
