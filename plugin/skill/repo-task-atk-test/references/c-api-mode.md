# c_api 模式适用范围

本文件只负责 S1 的适用性判断。调用序列表和执行器写法属于 S2，构建与绑定属于 S3。

## 目录

- 接受什么接口
- 四层准入门
- 半裸接口的四种情形
- 全裸 kernel
- v1 封闭层级
- 内存布局是 S1 必确认项

## 接受什么接口

`c_api` 接受公开的宿主 C 入口：调用者在 CPU 上传入设备指针，函数体完成参数校验、
tiling、kernel 拉起与必要同步。入口必须能由任意调用者用合法实参直接调用，不能依赖
工程测试程序里的私有准备步骤。

先运行适用性门禁，确认声明、v1 参数类别和真机架构目录中的入口都存在：

```bash
<python> scripts/check_c_api_applicability.py \
  --env evidence/env.json --candidate <公开 C 函数名> \
  --header <公开头文件> --op-dir <算子目录> \
  --layout arch_dirs --arch-dir <archXX> --arch-dir-basis '<工程写明映射的位置>' \
  -o evidence/c_api_applicability.json
```

experimental 布局改用 `--layout experimental`，并传入算子目录下的
`--build-cmake <算子目录>/test/CMakeLists.txt`，门禁会自行读取 `--npu-arch`。
这项 S1 检查只是存在性启发式；权威判断是构建后对 `.so` 执行的 S3 导出函数名门禁。

## 四层准入门

| 层 | 必须确认 | 不满足时 |
| --- | --- | --- |
| 宿主入口 | 有可直接调用的 host C 函数 | 拒绝，要求项目补入口 |
| 公开契约 | 参数、返回状态和上下文协议可从公开材料确认 | 阻塞，不能从实现猜 |
| 交付形态 | 能构建出含目标导出函数名的动态库 | 静态库或无导出时阻塞 |
| 约定体系 | 参数能落入 c_api v1 的封闭类别 | 超出层级时阻塞 |

四层都通过才进入 S2。某层“应该没问题”不算通过，必须把依据写进约束表或门禁报告。

## 半裸接口的四种情形

半裸接口有宿主函数，但公开性或交付形态不完整。处理方式固定如下：

| 情形 | 处理 |
| --- | --- |
| V1 C++ mangled 导出名 | 支持；`nm -D` 必须唯一匹配，报告记录 ABI 风险 |
| V2 声明不在公开头文件 | 默认阻塞；仅当项目公开文档给出完整声明且用户书面确认时受控放行 |
| V3 函数未从现有库导出 | experimental 可构建验收侧 wrapper；只有静态交付时阻塞 |
| V4 上下文协议未公开 | 阻塞，不设例外；不能复刻实现里的私有结构 |

V2 的受控例外仍要把完整声明固化到项目认可的公开头文件，再交给签名量具读取。
聊天里的手抄声明不能跨阶段充当调用契约。

## 全裸 kernel

只有 device kernel、没有宿主入口的实现不属于 `c_api`。停止并请项目增加公开 host C
入口；验收侧不自行补 tiling、launch 或同步逻辑。

## v1 封闭层级

v1 只开放 `context` 与 `execute` 两步，以及 enum、整数维度、布局量、主机标量、
设备指针和设备指针数组。以下能力不在 v1：

- descriptor 构造与销毁；
- workspace 查询、分配与回收步骤；
- aclsparse 一类描述符驱动接口；
- blasLt 一类启发式算法选择接口。

遇到这些参数时按能力边界报告，不临时扩写执行器。

## 内存布局是 S1 必确认项

接口名和 BLAS 家族惯例不能决定内存布局。真机案例的待验收函数使用行主序，而
cuBLAS 同类约定常见列主序；若按惯例猜，合法 shape、leading dimension 与基线都会错。

必须阅读项目公开文档，把 `order` 和依据（谁要求的、写在哪）写进
`evidence/constraints.md`，再把同一结论通过 `--layout-order` 与 `--layout-source` 写入调用
序列表。两个参数必须同时给出；省略时 `layout.order` 保持 `null`，表示 S1 尚未确认，
不得进入执行。
