# 隔离复验

A3 全量轮有失败就必须做。**判据是「失败集合可不可信」**，不是「跑完没有」——
批内污染会让一条好用例被记成缺陷，逐条单独跑一遍才分得开。

**一轮 solo，不迭代。** `--mode isolate` 把 `--ids-from` 那份报告里的 `failed_ids`
拆成一条一个作业，摊到全部空闲卡上并发跑一遍，每条的结论只看它单独跑的结果：

| 单独跑的结果 | 桶 |
| --- | --- |
| 还是执行失败 | `exec_failures` —— 是它自己的问题 |
| 跑起来了但算错 | `accuracy_false` |
| 通过 | `batch_only` —— **不是缺陷**，挂它的是前面某条自己没报错的用例 |
| 被 `--max-isolate` 截断没跑 | `not_checked` —— 未判定，不是通过 |

`cascade` 字段保留但恒为空，只为兼容旧报告。

**为什么不能省这一步。** 存在与 device context 无关的批内位置效应：同一条用例
单跑通过、换一条前置用例也通过，跟在特定的另一条后面就挂，而那一条自己一路显示
通过。真凶不报错、受害者才炸，罪名会落在受害者头上，只有单独跑一遍分得开。

**复跑要换一张现查的空闲卡。** 在刚崩过的那张卡上复跑，通过的用例也会被判成
「单独跑也挂」，批内污染就被误报成真实缺陷。

**「跑通」必须同时排除精度不符。** ATK 报表里 `failed cases` 是执行失败，
`accuracy false cases` 是跑起来了但算错，两张表。只看前者会把「算错了」判成
`batch_only` 再计入通过——静默漏报。实测一轮里抓到过 4 条。

**两个维度都要进复检。** 批内污染在执行和精度上都会发生：前一条把显存弄脏，
后一条可能直接崩，也可能跑完但算错。只收执行失败的话，精度那一类永远进不了复检、
被当成真实缺陷写进报告——实测一轮里有 3 条批内精度不符的用例单独跑全部通过。

**复检结果按维度记进 `batch_only_detail`（ATK）/ `batch_only`（独立执行器）**，
每条带 `dim`：`exec` = 批内跑挂了，`accuracy` = 批内跑完了但算错。
报告要把这批显式列出来——只给条数的话，读报告的人无从判断失败集合可不可信。

**隔离复验与全量自动同口径**：比例都从 `facts.json` 读，用例 id 相同则布局相同，见上一节。

**同一个 `work/` 里不要起第二轮隔离复验。** 开跑前 `isolate/` 整个删掉——不删的话
上一轮的 `EZ9999` 会被扫成本轮的 aicore 证据，报告出现「0 条执行失败，成因是
aicore 异常」这种自相矛盾的结论。代价是上一轮那些 `isolate/solo/case<id>/` 里的
`run.log` 与 `atk_output/` 一并消失。**裁决产物 `stage/isolate.json` 不受影响**
（`verdict.py` 与 `make_repro.py` 只读它），丢的是逐条排错用的原始日志。
要在正式现场之外试跑，另建一个 `work/`。

### 成本

每条一次 `atk` 启动，`ThreadPoolExecutor(max_workers=min(条数, 卡数))` 连续调度
——**不是一波跑完再下一波**，先完成的槽位立刻接下一条。

**并发度由 `--isolate-devices` 的卡数决定，而卡不是约束。** 实测机上 15 张卡、
640 核全闲，瓶颈在别处（成因未查清）。后果是总耗时**对并发度非单调**，同一批
12 条送检、同机同时间窗、每档多次复现：

| 并发 | 墙钟 | 折合每条 |
| --- | --- | --- |
| 1 | 270s | 22s |
| 3 | 99–105s（4 次） | 25s |
| **4** | **80 / 83s** | **26s** |
| 6 | 317–318s（3 次） | 159s |
| 12 | 183–184s（3 次） | 183s |

**加并发可能变慢，而且不是单调变慢**：并发 6 比并发 12 还差近一倍。所以
**「用满空闲卡」既不是上界也不是最优**，当前 `auto` 取全部空闲卡只是省事。

规模一大行为又不同：106 条送检、并发 15 实测 480s（折合每条 68s），远好于
12 条那轮的每条 183s——**结论不能跨规模照搬**。

**成因未查清，不要据此调参。** 已排除两条：

| 假设 | 怎么排除的 |
| --- | --- |
| CPU 争用 | 实测机 640 核、load 32，CPU 远没跑满 |
| 并发进程同时初始化 device 互相碰撞 | 给最初那批起跑加 5s 递增错开，实测 12 条 183→**235s**、106 条 480→**514s**，两个规模都**变慢**，且慢的量正好等于加进去的错开总量——**每个任务本身耗时一点没变**，与"同时起跑"无关 |

**并发度不要写死。** 取的是 `min(送检条数, 现查空闲卡数, 占用上限)`，卡多就多跑；
虽然实测它不是最优（12 条时并发 4 只要 82s），但最优点随送检规模翻转——106 条那档
并发 4 反而更差——**没有一个固定数字能同时管住两端**，而按规模选并发的阈值同样是
这台机测出来的常数。在成因查清之前，维持现状比引入一个调不准的参数好。

**占用上限是另一回事，不要和调参混为一谈。** 上面说的是「哪个并发最快」，上限管的是
「一个验收任务能占机器多少」：机器公用，`auto` 现查到 15 张就用 15 张会把空闲卡吃光，
别人只能等或被迫共卡，而共卡会让性能结论静默作废。上限定在 4（`probe_env.MAX_AUTO_DEVICES`），
独占机器时 `--max-devices 0` 解开。代价说清楚：12 条那档并发 4 实测 82s，比用满还快；
**106 条那档没在并发 4 上测过，按轮数估算会变慢**，换的是不独占机器。

**所以这套算法的前提是失败集合小**——它假定 device 连带已经不存在（见下节）。
未修复的 ATK 上一条 aicore 异常会造出上百条连带失败，复检要为它们逐条各起一次
`atk`：实测 106 条送检 480s，而其中 89 条是连带、根本不该被送检。

并发的前提实测过：8 个 atk 实例同时跑、各占一张卡、各自独立工作目录，全部正常出
报告，墙钟 31s（单实例 25s）。唯一的冲突是 `sqlite_web` 调试 UI 抢 8881 端口，
不影响跑测，要消噪音就用 `--sqlite_web_port` 错开。

时间上限是 `--max-isolate`（默认 0 = 不限）。

### 装机 ATK 有没有带批内连带的修复

aicore 异常会把 device context 打废，未修复的 ATK 上同批后面的用例全部在初始化
阶段挂（报 `ACL stream synchronize failed, error code:507015`），一轮只能清掉每块
第一个污染者。修复见 [ATK issue #28](https://gitcode.com/Ascend/ATK/issues/28)
与 [MR !32](https://gitcode.com/Ascend/ATK/merge_requests/32)，**还没进上游**。

**判据：** 一轮跑完打印的「隔离复验 N 条」是三位数就说明连带还在，那是没用修复版。
要么换打过补丁的 ATK，要么接受轮数 = ⌈污染型失败数 ÷ 卡数⌉ 的耗时。

**`aicore_evidence` 空的时候不要写「aicore 异常」。** 触发复验的判据是「有执行
失败」，成因不一定是它。脚本只在日志里真有 `aic-error`、`EZ9999` 这些关键词时
才认领这个成因（词表见 troubleshooting.md「NPU aicore 异常」）。
