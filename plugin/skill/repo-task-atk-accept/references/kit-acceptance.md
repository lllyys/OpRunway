# 自带件路

任务书自带跑测件、要验的就是任务方那批用例时走这条。**整条生成侧不参与**：
标杆由自带件的 CPU 节点当场算，没有冻结 golden，也没有用例包。

自产用例那条线仍然有价值——自带件覆盖的是任务方对规格的一种解读，
任务书要求的泛化数据未必都在里面（实测一例：自带件的性能集规模只到 20000、
dtype 只有两种，覆盖不到它自己任务书的量化判据表）。但它是**并行的第二条线，
不是自带件路的前置**。

## 判据

| 手上有什么 | 走哪条 | A3 的标杆 |
| --- | --- | --- |
| 任务书 + 自带跑测件 + 算子工程 | 本节，`run_atk.py --nodes` | 自带件的 CPU 节点当场算 |
| 任务书 + 算子工程，没有可用的自带件 | 用例包那条，`run_atk.py --golden` | 生成侧冻好的 `golden/` |

自带件齐不齐按内容认，不按文件名认：

```bash
ls <任务自带件目录>                                  # 用例清单：JSON 数组或 {"cases": [...]}
grep -rl "BaseApi" <任务自带件目录> --include="*.py"   # 执行器插件
grep -rl "nodes" <任务自带件目录> --include="*.yaml"   # ATK 的节点拓扑
```

三样缺一样就回到用例包那条。

## 阶段

自带件路**不产出也不消费用例包**，`input/` 下只有自带件副本、修复件与 `facts.json`。
下表是每个阶段在这条路上的差别，没列到的与 `SKILL.md` 一致：

| 阶段 | 自带件路做什么 | 命令在哪 |
| --- | --- | --- |
| A1 | 建现场、`cp -r` 自带件进 `input/kit/`、写 `facts.json` | 本文「A1 的 facts.json」 |
| A1.5 | **精度用例扩到 1000 条**并补齐任务书要求的 dtype | 本文「A1.5 精度用例扩到 1000 条」 |
| A2 | 与用例包路相同 | `SKILL.md` A2 |
| A2.4 | **先过体检**，报出来的一次修完 | 本文「A2.4 先过体检」 |
| A2.5 | 冒烟，失败按脚本报的真因逐条修 | 本文「A2.5 冒烟」 |
| A2.6 | **由 `backend` 定，与本路无关** | `SKILL.md` 执行剖面表 |
| A3 | 直接跑全量 | 本文「精度」 |
| A3.5 | **由 `backend` 定，与本路无关** | `SKILL.md` 执行剖面表 |
| A4 | 倍率来自自带件自己的脚本 | 本文「性能」 |
| A5 | `verdict.py` 从 `facts.kit.cases` 取用例清单 | `SKILL.md` A5 |

A2.6 与 A3.5 那两行是**另一根轴**：走不走它们看 `facts.json` 的 `backend`，
与手上是自带件还是用例包无关。两根轴各判各的。

## A1 的 facts.json

自带件路的 `facts.json` **由 A1 从任务书写出来，不找生成侧要**。
全部字段跑一次 `<skill>/scripts/facts_schema.py` 就打成表，这里只说这条路的差别：

| 字段 | 这条路上填什么 |
| --- | --- |
| `kit.cases` | **必填**，指本轮实际跑的用例清单。修复过就指 `kit_fixes/` 里的副本，不指原件 |
| `kit.baseline` | 标杆节点名，不填就从 nodes yaml 认 |
| `performance.criterion` | 任务书性能要求的**原话**，达标线从原话里抠 |
| `adopted_files` | 原件的 sha256，证明跑的是任务方交付的那一份 |
| `group_attr` | 用例里那个分档参数名。缺了冒烟只抽得出一条 |
| `kit.dtype_map` | dtype 名到用例里那个整数的对应，A1.5 要。**值从自带件执行器的 dtype 字典抄，不从用例反推**——用例里只出现它实际用到的那两三个，缺的那些正是要补的 |

## A1.5 精度用例扩到 1000 条

自带件给多少条由任务方定，**验收按 1000 条测评**，dtype 一起补齐到任务书要求的
全集。两件事一条命令做完，中间量不摆给用户。

**dtype 那一轴加条数补不上。** 自带件的生成脚本把 dtype 写死在模块级常量里，
CLI 参数碰不到——实测一例只出 fp32 与 complex64，而任务书要四种。

### 需人工指定

**这一步不单独问用户。** 扩到多少条、补哪些 dtype 都由任务书定死，口径进 A1
那张范围表，用户在那里确认一次；这里只照着执行。

### 用法

```bash
<python> <skill>/scripts/expand_kit_cases.py \
    --cases <自带件的用例清单> --dtype-map '<facts.kit.dtype_map>' \
    --dtypes <任务书要求的 dtype，逗号分隔> \
    --generator-cmd '<python> <自带件的用例生成脚本> <条数参数> {n} --output-dir {dir}' \
    -o input/kit_expanded/cases.json
```

`{n}` 与 `{dir}` 由本命令自己填。**条数参数名各任务不同**，从生成脚本的 `--help`
读一次写进模板即可；`{n}` 收到的不是 1000，倒推由本命令做。

| 退出码 | 含义 | 去向 |
| --- | --- | --- |
| 0 | 扩好了 | `facts.kit.cases` 改指 `-o` 那份 |
| 3 | 用例清单或 `--dtype-map` 读不出 | 核路径与 JSON |
| 4 | dtype 轴推断不出来 | 屏幕上已列出候选，用 `--dtype-attr` 指定 |
| 5 | `--dtype-map` 里没有要补的 dtype | 回自带件执行器的 dtype 字典抄全 |
| 6 | 条数不够且没给 `--generator-cmd` | 补上它 |
| 7 | 生成脚本跑挂了，或没产出与原件同名的文件 | 屏幕上已列出它产了什么 |

**这一步排在 A2.4 体检之前，作用在原件上。** 体检的修复脚本常把 `outputs` 整个
删掉（装机 CaseConfig 只收 str/int），而 dtype 轴的推断要读 `outputs.<i>.dtype`；
顺序反过来时一条都识别不出。

### 工作原理

| 机制 | 说明 |
| --- | --- |
| 生成脚本收到的条数 | `1000 ÷ 任务书 dtype 数 × 生成器自己出的 dtype 数`。补 dtype 时条数还会涨，直接传 1000 最后是两倍 |
| 多出来的条数 | 每种 dtype 留前 `1000 ÷ d` 条，其余裁掉。只判下界的话，生成脚本被直接传了 1000 时每一步都退 0 而结果是 2000 条 |
| 1000 除不尽 dtype 数 | 按每种向下取整，实际条数打印出来 |
| dtype 名两种写法 | `float32` 与 `fp32` 都认。`dtype_map` 照执行器抄来的是 torch 名，用例里是 ATK 词表名，装机 ATK 自己也两种都收 |
| 精度阈值 | 不用配。ATK 的混合容差按 dtype 自己选门槛（装机 26.8.8 实测词表含 `fp16` 与 `bf16`） |
| 新增用例的 id | 从原件最大 id 之后接着排，原用例的 id 一个不改——验收报告要和任务方的自测报告逐条对照 |
| shape | 扩出来的与源 dtype 共享同一批，dtype 之间可横向比 |

### 范围之外

- **不改自带件的任何文件。** 扩展只产出新的用例清单，原件按 `adopted_files`
  记 sha256，证明跑的仍是任务方交付的那一份
- **报告里新增这批单独成节**，不与原件合并算通过率：原件是任务方自测口径，
  新增的是验收方按任务书要求补的。任务书要求的 dtype 从没跑过时整片失败是预期
  结果，那正是这一步要暴露的缺口

## A2.4 先过体检

自带件是「用例 + 插件 + 脚本」从**作者机搬到验收机**。跨这道边界只有三类东西会变，
体检覆盖前两类，几秒钟，不占卡：

| 真因类 | 表现 | 量具 |
| --- | --- | --- |
| ATK 版本错配 | 用例过不了装机版本的 schema；args/kwargs 分流约定与执行器读的对不上；比对前两侧 dtype 不同 | A、D 查得到；dtype 那条查不到 |
| 自带件内部不自洽 | 用例里的名字在插件里解析不到；按名字分派的判据恒假 | B、C、E 查得到 |
| 宿主环境假设不成立 | 作者机有 MKL、x86 或 GPU，验收机没有 | **查不到**，只有冒烟暴露 |

```bash
<python> <skill>/scripts/kit_lint.py --kit <自带件目录> \
    --cases <自带件的用例文件> --plugin <自带件的插件入口>.py
```

| 退出码 | 含义 | 去向 |
| --- | --- | --- |
| 0 | 没发现不兼容 | 进 A2.5 冒烟 |
| 4 | 逐条列出判据、证据与修法，并标出哪几条冒烟看不见 | 全部修进 `kit_fixes/`，再进 A2.5 |
| 3 | 自带件目录或用例文件读不出 | 核路径 |

**判据是解析不是匹配已知症状**：用例拿去过装机那一版的 `CaseConfig`，名字拿去查
装机那一版的注册表，按用例名分派的判据比对用例名集合。换算子、换 ATK 版本都成立。

**报出来的一次修完，不要留给冒烟一条一条试。** 每一条都带着装机 ATK 自己的拒绝
原文，必要性在报出来的那一刻就证明完了，不需要靠一轮冒烟再确认一遍；`FIXES.md`
里每条的依据直接抄体检的证据列，比「改完之后冒烟走得更远」的推断硬。

体检查不到的只有一类：**宿主环境假设**——作者机有 MKL、x86 或 GPU 而验收机没有。
这一类只有冒烟暴露，所以**体检退 0 也必须跑冒烟**，体检替代不了它。

### 为什么排在冒烟之前

早先排在冒烟之后，理由是「跑得起来的问题冒烟一轮全会报出来，静态体检只补跑通
之后那一道」，依据是一次实测：先按体检报的全修完，冒烟照样连挂 4 轮。

改到之前的依据是两条：

| 判据 | 实测 |
| --- | --- |
| 体检报的是不是真的都得改 | 两份不同算子的自带件各报 7 处，逐条落在最终 `FIXES.md` 里真正改了的那几项上，误报 0 |
| 提前修会不会白费 | 体检报的每条都带 ATK 的拒绝原文，晚修早修工作量相同，先修只是把「读日志定位」那段循环并成一次 |

那次实测说明的是**体检替代不了冒烟**，不是前置有害——两条结论并存，所以冒烟
一步没减。

## A2.5 冒烟

**自带件路的主要工作量在这里**：让任务方那份跑测件在这台机器上跑起来。

**体检修完再跑，不要拿原件试。** 体检证明得了的在 A2.4 一次修完，冒烟负责
体检证明不了的那一类，主要是宿主环境假设。失败原因脚本自己打出来，
按报出来的那一条修，再跑。

```bash
cd <现场>/work && source evidence/env.sh && <python> <skill>/scripts/run_atk.py \
    --mode smoke --op <op> -c ../input/kit_fixes/cases.json \
    --nodes ../input/kit/<nodes yaml> -p ../input/kit_fixes/<插件入口>.py \
    --facts ../input/facts.json --install stage/install.json -o stage/smoke.json
```

没有修复件时 `-c` 指自带件原件、`-p` 指原件的插件入口。

**`-p` 给目录还是给单文件按注册对象的份数定**：

| kit_fixes 里的形态 | `-p` 给什么 |
| --- | --- |
| 执行器与比对器在同一个 `.py` 里 | 那个文件 |
| 分在多个 `.py` 里 | **目录**。收目录时 ATK 导入目录下所有 `.py` 全部注册，收单文件时只载那一个 |

冒烟与精度两步**必须给同一个**。给错的表现是冒烟过了、全量每条比对 KeyError，
一轮全量的钱白付。目录里所有 `.py` 都会被导入，所以**那个目录里不许放模块级会
`raise` 的脚本**——ATK 扫到就整轮起不来。

### 循环的规矩

| 规矩 | 违反的后果 |
| --- | --- |
| **一轮只改一件事** | 一轮改三处后跑通，不知道哪处是必要的，三处都要留在 `FIXES.md` 里向算子作者解释 |
| 每改一处立刻重跑冒烟 | 冒烟一轮几十秒，攒着改到全量轮才暴露，一轮几分钟起 |
| 失败原因**读脚本摘出来的那几行**，不去翻 `run.log` 全文 | 全文里 ATK 的 celery 栈占几百行，真因在中间 |
| 修复一律落 `kit_fixes/`，原件一个字节不改 | `adopted_files` 的 sha256 对不上，「跑的是任务方那一份」这条链就断了 |

冒烟通过才进 A3 全量。**冒烟判「执行失败」与「精度不符」两类，都算没过**——
只看跑不跑得起来会放过整批同因的口径问题，那类问题要到全量轮才炸，一轮的钱白付。

| 冒烟的结果 | 去向 |
| --- | --- |
| 全过 | 进 A3 全量 |
| 挂 1 条且不是接口层拒绝 | 照常进全量，交给隔离复验测准 |
| **挂 2 条以上，或接口层拒绝** | 退 3。整批同因，先在这几条上把成因钉死；确认是算子缺陷再加 `--smoke-force` 进全量 |

### 三种修法

有一条硬约束：**原件的 sha256 进 `facts.json` 的 `adopted_files`，改一个字节，
「跑的是任务方交付的那一份」这条链就断了。** 所以修复只能在旁边加一层：

| 修法 | 落在哪 | 用于 |
| --- | --- | --- |
| 改用例字段 | `kit_fixes/adapt_cases.py`，读原件的用例、写一份副本当 `cases.json` | schema 不合、名字解析不到、args/kwargs 分流 |
| 派生覆盖 | `kit_fixes/` 里的插件入口，`import` 原件模块后派生子类覆盖那个方法 | 恒假分支、CPU 标杆用了本机没有的算子、dtype 不齐 |
| 另起件 | `kit_fixes/` 里一个新脚本，`import` 原件的构造与采集函数 | 自带件缺一整块，或它的口径与任务书对不上——判据表的场景不在它的用例集里、性能脚本要一层驱动才跑得起来 |

派生覆盖要另起一个注册名，不要占用原件那个——两个名字同时在注册表里，
报告里就能看出跑的是派生那份。

**第三种别当成前两种的变体硬塞。** 实测一轮四个修复件里有两个属于它
（判据表场景的量测件、驱动自带件 profile 脚本的外壳）；塞进 `adapt_cases.py`
会把「改用例」和「另跑一件事」混在一处，`FIXES.md` 里就说不清改了什么。
另起件同样受那条硬约束：**造数一律复用原件的构造函数**，自己另写一套的话，
两套造出来的数据结构不同，与自带件那轮的耗时和精度都不可比。

### `kit_fixes/` 里放什么

| 文件 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| `adapt_cases.py` | 产出用例副本 | 没有就是不需要改用例 |
| 插件入口 `.py` | `import` 原件并派生覆盖 | 没有就是不需要派生 |
| 另起件 `.py` | 补自带件缺的那块 | 没有就是不需要 |
| `run.sh` | 本轮实际跑通的那条命令，原样落盘 | `make_repro.py` 只搬不构造命令，缺了复现包里只能写「跑法见目录说明」 |
| `FIXES.md` | 逐条：改了什么、为什么、依据原件哪一行 | 指纹与任务仓不同而报告不说，结论追不回来源 |

同一批改动的一句话摘要另外写进 `facts.json` 的 `kit_fixes` 数组，
跑测侧把它逐行贴进复现包 README。

### 定位法

自带件跑不起来时报错方向常常不指向真因，实测五例：

| 报错 | 指向 | 真因 |
| --- | --- | --- |
| `not enough values to unpack (expected N, got 0)` | 执行器的解包语句 | ATK 按 `name` 把输入分流进了 kwargs |
| `... is not implemented for ... without MKL` | 环境缺库 | CPU 标杆挑了本机算不了的存储格式 |
| `Float did not match Double` | 比对器 | 标杆按更宽的 dtype 算，而装机 ATK 的归一化不覆盖这一对 |
| `Could not run 'aten::<op>'` | 算子没实现 | 待验收实现没在 ATK 的 worker 进程里注册；主进程 import 过不算 |
| `No such file or directory` | 文件真的不在 | 路径在子目录轮里解析偏了，或修复件没落到指定位置 |

**这五条冒烟失败时脚本已经打在屏幕上了**，连去向一起。这张表是没命中特征串时的
兜底：定位到新的特征串，补进 `run_atk.py` 的 `KIT_SYMPTOMS`，下一个人就不用再找一遍。

**算子工程里常另有一份不走 ATK 的自测脚本。** 它能跑而 ATK 那条跑不起来时，
排查范围就锁死在接入层，不必去 kernel 里找。修接入层时语义以那份脚本为准——
它是同一批交付里可执行的语义样本。**但它不能当验收结论**：它的容差是作者
自己写的，任务书口径落在自带件的比对器里。这份脚本不保证存在。

## 精度

```bash
cd <现场>/work && source evidence/env.sh && <python> <skill>/scripts/run_atk.py \
    --mode accuracy --op <op> -c <适配后的用例文件> \
    --nodes <自带件的 nodes yaml> -p <kit_fixes 里的插件入口> \
    --facts <facts.json> --install stage/install.json -o stage/accuracy.json
```

`--nodes` 一给就走自带件路：拓扑交给自带件自己描述，本脚本不再拼节点，
`golden/` 那三道校验整体跳过。标杆节点从 yaml 里认（backend 不是被测剖面那个），
拓扑里有多个候选时退出并要求 `--baseline-node <backend>:<name>` 给死。

字段要求见本文「A1 的 facts.json」。

**自带件的标杆可能与任务书口径相反，不要默认它是对的。** 自带件为了造判据会往
输入里注入特殊值，而任务书对同一情形的语义要求可能正好相反——实测一次：自带件在
`beta=0` 的用例里往 `input` 注入 NaN 与 Inf，而任务书与 ATen 文档都写明 `beta=0`
时 input 被忽略、非有限值不传播，于是**合规的实现被标杆判成失败**，304 条。

判据：某一组用例整批失败且集中在同一个 attr 取值上时，先核任务书对那个取值的
语义要求，再核标杆的行为，**不要先怀疑算子**。核出口径相反时按本文「A2.4 先过体检」
那张修复表在标杆侧落任务书口径，理由记进 `facts.kit_fixes`。

## 性能

任务书的口径 ATK 表达不了时（判据见 [run-performance.md](run-performance.md)），
倍率来自自带件自己的脚本：

```bash
cd <现场>/work && source evidence/env.sh && <python> <skill>/scripts/run_kit_perf.py \
    --script <自带件的性能脚本> --cases <自带件的性能用例> \
    --baseline <GPU 基线 csv 或 json> --metric kernel_total_us \
    --work stage/kit_perf --source "<谁采的>" -o stage/kit_perf_exchange.json
```

| 退出码 | 含义 | 去向 |
| --- | --- | --- |
| 0 | 全部跑出数 | 交给 `collect_perf.py` 收编 |
| 4 | 有条目没跑出数，交换格式仍然落盘 | 逐条原因在 `<work>/dev*.log` |
| 3 | 脚本或用例读不出，或必需参数探测不到 | 屏幕上列了探到哪些参数 |
| 2 | 一条都没跑出来 | 同上 |

它现查空闲卡分片并行（**最多 4 张**，机器公用；独占时 `--max-devices 0`），
按 `--help` 探测自带件脚本收哪些参数，自带件没汇总出数时
从 Profiler 产物回落。实测 50 条从 12 分钟降到 2 分 41 秒，回落出的数与自带件
自己汇总的逐条相对差中位 0.08%。

### 两套用例，两步跑

任务书的量化判据表与自带件的性能集常常不重合：达标线按任务书那张表算，自带件的
性能集只作泛化补充。实测一例，只跑自带件那 50 条，达标线一条都没测到。

| 步 | 跑什么 | 用什么 | 报告里算什么 |
| --- | --- | --- | --- |
| 第一步 | 自带件自己那批性能用例 | 上面那条 `run_kit_perf.py` | 泛化覆盖，单独一节 |
| 第二步 | 任务书性能判据表里的场景（表里每一行 × 每个 dtype） | **照抄 `assets/perf_harness.py` 改 `build_call`** | 达标线 |

判据、采样口径、哪几条不必跑满，全在
[external-perf.md](external-perf.md)：**口径从任务书读进
`facts.performance.sampling`，性能轮先 `--probe-only` 探一遍再决定跑不跑**。

第二步**不要现写一套量测脚本**：预热与采样循环、计时范围、统计量、输出格式
四件事各写各的，两步的数就没法比，而骨架件里这四样已经按验收口径固定了，
产出直接是 `collect_perf.py` 的交换格式。造数**复用自带件的构造函数**，
两套造数出的稀疏结构不同，耗时不可比。

判据表的场景全在自带件的用例集里时第二步不跑，报告里写明重合。

## 产物

| 落点 | 是什么 |
| --- | --- |
| `<用例包或现场>/kit_fixes/` | 修复件与 `run.sh`、`FIXES.md`。原件一个字节不改 |
| `repro/op-testcase/original/` | 自带件原件加 `MANIFEST.md`（sha256，与任务仓比对用） |
| `repro/op-testcase/fixed/` | 本轮实际跑通的那一份，开发者拿到就能跑 |
| `repro/perf/` | **性能单独一份**：量测件、分片用例、基线表、本轮命令。`rerun.sh perf` 跑的是 ATK 那轮，这条路上它整轮不跑，报告里的倍率全来自这里 |

本轮实际跑通的性能命令落进 `kit_fixes/run_perf.sh`，`make_repro.py` 只搬不构造——
缺了它复现包里只能写「跑法待补」。
