# 外部性能结果

任务书的性能口径 ATK 表达不了时读这份：判据表怎么核、采样口径从哪来、
哪几条不必跑满、交换格式长什么样。ATK 自己那四种形态在
[run-performance.md](run-performance.md)。

任务书要求的性能口径超出 ATK 能表达的范围时，倍率只能来自外部工具。
**判据是逐条比对，不是「有没有自带脚本」。**

### 判据

把任务书性能章节的每一条要求对着这张表勾：

| 任务书可能要求 | ATK `performance_device` |
| --- | --- |
| 预热 N 次、采样 M 次 | 能，`--performance_data N,M,n` |
| 单个 kernel 的 Device 耗时 | 能 |
| 分阶段耗时（算子内部几段各报一个数） | **不能**，一个节点一个数 |
| 中位数、p90 | **不能**,`perf_ntimes` 取的是后 n 次的平均值 |
| 复用描述符／workspace／输出再采样 | **不能**，每条用例独立走 dataset 到执行 |
| 两个独立计时范围各自对应采集 | **不能**，只有一个范围 |
| workspace 峰值、各 Kernel 耗时 | **不能**，要 Profiler |

**有一条落在「不能」上，A4 就是两步。** 实测一例（`aclsparseDenseToSparse`
任务书 3.3)：六条里五条不能。

### 标杆数值来自任务书，覆盖面不来自自带件

**这两件事要分开。** 性能这一档与精度不同：标杆不是本机跑出来的，是任务书给死的
一张表（常见形态是「NVIDIA A100 cuSPARSE NCU Kernel 总耗时」逐场景一个数）。
那张表**只能引用，产不出来**，所以走自产用例包时性能侧照样读它。

| 东西 | 从哪来 | 能不能自产 |
| --- | --- | --- |
| 达标门槛（倍率、均值门） | 任务书性能章节，抄进 `facts.json` 的 `criterion` | 不能 |
| 逐场景标杆耗时 | 任务书正表，或自带件里同源的基线 csv | **不能**，引用它不算依赖自带件的覆盖 |
| 采样口径（预热／采样次数） | 任务书，抄进 `performance.sampling` | 不能 |
| 跑哪些场景、造什么数 | 任务书的场景表 | **能**，而且默认自产 |
| NPU 侧的采集脚本 | 自带件，或 `assets/perf_harness.py` | 能 |

**先核这两套用例重不重合，再决定跑哪套。** 自带件的性能集是任务方对泛化能力
的一种覆盖，任务书的量化判据表才是达标线，两者可以完全不搭界。

| 来源 | 用途 | 核什么 |
| --- | --- | --- |
| 任务书性能章节的场景表 | **达标判据**。倍率门槛按它的原话算 | 每个「规模 × dtype」组合有没有对应用例 |
| 自带件的性能用例或基线 csv | 泛化补充，单独报告 | 规模区间与 dtype 覆盖到哪 |

对不上时按任务书里的生成规则补齐场景。**有自带件时造数复用它的构造函数**，
不另写一套：两套造数出的稀疏结构不同，耗时不可比。任务书通常会给确定性生成
规则（列索引怎么排、每行几个非零），核对的落点是输出的 `nnz(C)` 与表里的数一致；
没有自带件时按那条规则自己实现，核对落点不变。

### 两套 id 的对齐

达标场景与泛化基线常常各有一套编号（任务书正表 `P-01`／`P-02`，基线 csv
`addmm-float32-000`）。交换格式的 `cases[].id` 只有一个，**给达标场景用**：

| 这一组 | `id` 填 | `label` 填 | 进报告哪一节 |
| --- | --- | --- | --- |
| 任务书正表的达标场景 | 用例包 `perf/cases.json` 里对应那条的 id | 任务书的场景编号加 dtype，如 `P-02 fp16` | 达标裁决，逐条比门槛 |
| 泛化基线 csv 的那批 | 同上，对不上就不收编 | csv 自己的 id | 单独一节，只报倍率不判达标 |

**两组分开收编成两份 JSON，不要混在一份里。** 混在一起时 `verdict.py` 会把泛化
那批一起拿去比门槛——那批本来就不是达标线，拉低均值后总结论翻成不达标，
而报告里看不出多算了哪些条。

**`collect_perf.py` 的 `-c` 给的是这一批自己的用例文件**，不是精度用例包的
`cases.json`。判据表那批的用例由另起件带（如 `perf_cases_p_table.json`），
`-c` 给错时它拒收并报「这些 id 不在用例包里」——报错方向是对的，改 `-c` 就好。

实测一例：自带件 50 条的规模在 `[1000, 20000]`、dtype 只有 fp32 与 complex64；
任务书的判据表是 3 行规模（最大 2,449,029×2,449,029×256）乘各行的
dtype（fp32；fp16／bf16／fp32；fp16／bf16／fp32／complex64），共 8 个场景。
**只跑自带件那 50 条，达标线一条都没测到。**

### 自带件的性能脚本落盘在哪

自带件的脚本常把产物默认写进**它自己所在的目录**。原件目录一旦被写，
`adopted_files` 的指纹链就断了。跑之前一律显式给输出路径：

| 现象 | 判据 | 处置 |
| --- | --- | --- |
| 原件目录里多出 `results_*/` 与 `*_traces/` | 脚本的默认输出目录取的是脚本自身路径 | 显式传 `--output-dir` 与 `--trace-root` 指到工作目录 |
| 重跑时开跑即崩，报目录已存在 | trace 目录用 `mkdir` 不带 `exist_ok` | 每轮先清空 trace 根 |
| Profiler 汇总报找不到某个 csv | 产物文件名随 torch_npu 版本变（实测：只有 `kernel_details.csv`，没有 `op_statistic.csv`） | 派生覆盖那个汇总函数，按逐 kernel 的 `Duration(us)` 求和，除数沿用原件的 active steps |

### 交换格式

外部工具负责采，`collect_perf.py` 负责收编与核对，`verdict.py` 负责裁决。
中间只有这一份 JSON,**字段少是刻意的**——每多一个字段就多一处要和外部工具
对齐的地方，而它们不在同一个仓里。

```json
{
  "source": "任务方 benchmark_sparse_ops_npu.py",
  "unit": "us",
  "cases": [
    {"id": 0, "under_test_us": 41.2, "baseline_us": 34.688,
     "label": "P-01 CSR int8", "stage": "convert"}
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `source` | 是 | 谁采的，进报告。不写读报告的人分不清它和 ATK 那轮 |
| `unit` | 是 | 只认 `us`。别的单位在收编处换算等于把换算错误藏进结论 |
| `cases[].id` | 是 | 与用例包 `cases.json` 的 id 对齐，`collect_perf.py` 会对账 |
| `cases[].under_test_us` | 是 | 待验收实现的耗时 |
| `cases[].baseline_us` | 否 | 标杆耗时。**缺它这条就没有倍率**，报告如实写 |
| `cases[].label` `stage` | 否 | 进报告的行名与阶段名 |

**倍率 = `baseline_us` / `under_test_us`，大于 1 表示比标杆快。**
方向与任务书「性能倍率 = 标杆耗时 / NPU 耗时」一致，**反了结论也反**。

### 裁决

`verdict.py` 从 `criterion` 的原话里抠出倍数当门槛，逐条比。**认写法不认某一个字**：

| 原话 | 抠出的门槛 |
| --- | --- |
| `性能倍率达到 0.25 倍性能标杆以上` | 0.25 |
| `NPU性能 > 0.25 × GPU A100性能` | 0.25 |
| `性能不低于 A100 的 1.0 倍` | 1.0 |
| `耗时不超过基线的 4 倍` | 0.25（耗时口径与性能倍率互为倒数，自动折算） |
| `不劣于内置实现`、`达到 memory bound 的 80%` | 抠不到，不代判 |

倍数标记认 `倍`、`×`、`x`、`*`，数字必须紧挨着它——`case×dtype` 这种不会命中。
耗时口径的判据是「主语是耗时」且「比较词是不超过一类」两条同时成立，
只中一条按性能口径走。**没有倍数写法就不判**：抠错一个数比抠不到糟得多。


| 情形 | 状态 |
| --- | --- |
| 抠到门槛，全部达到 | `达标(全部 ≥ N)` |
| 抠到门槛，有条低于 | `不达标(x/y 条低于 N)`，失败 id 进报告 |
| 原话里没有数值门槛 | `待人工判定(<原话>)`，带上实测倍率 |
| 一条基线都没给 | 只报绝对耗时 |
| 没收到外部结果 | `待人工判定(<原话>)`，注明未收到 |

**只做这一件算术。** 折算理论峰值、判 roofline 那类仍然不代判——
那要机型的算力与带宽，跑测侧没有这两个数。

### 外部工具从哪来

| 情形 | 用什么 |
| --- | --- |
| 用例包的 `kit/` 里带性能脚本 | **优先跑那份**。口径与任务方交付的基线表同源，换一份就不可比 |
| 自带件有，但只覆盖泛化那批、没覆盖任务书正表的场景 | 仍跑那份采泛化数据，正表的场景另用骨架件采，**两份分开收编** |
| 自产用例包，`kit/` 不存在 | 照抄骨架件，只改扩展点。标杆数值仍从任务书正表取 |

两个骨架按**口径**分，不按算子分：

| 骨架 | 主口径 | 什么时候用 | 扩展点 |
| --- | --- | --- | --- |
| [perf_harness.py](../assets/perf_harness.py) | 一次 `invoke()` 两端的墙钟 | 任务书按调用耗时给指标 | `build_call` |
| [perf_harness_kernel.py](../assets/perf_harness_kernel.py) | Profiler 逐次调用的 Kernel 总耗时 | 任务书拿 GPU 的 NCU Kernel 总耗时当标杆，要同量纲 | `DTYPES`、`build_sparse`、`build_call` |

**改扩展点，别动下面的。** 采样循环、产物解析、统计量、输出格式四件事各写各的，
两轮跑出来的数就没法比。Profiler 产物的认列规则在 `scripts/kernel_trace.py`,
两个消费者共用一份——骨架件拷出 `assets/` 之后用 `--skill-scripts` 指回去，
不在骨架里复制一份。

判据表那类场景常常三处都要改，实测一例（SpMM 的 P-01/P-02/P-03）：

| 扩展点 | 自带件给的 | 判据表要的 | 依据 |
| --- | --- | --- | --- |
| `DTYPES` | fp32 / c64 | 加 fp16 / bf16 | 判据表的 dtype 列 |
| `build_sparse` | `nnz = rows × degree`，行长恒定 | 精确 nnz，行长 `base` 与 `base+1` 混合 | 判据表的 nnz 除以行数不是整数（10556 / 2708 = 3.898） |
| `build_call` | 自带件自己的调用 | 任务书写明的 alpha/beta 与调用范围 | 判据表的 alpha/beta 列 |

**自带件造的数踩不到行长方差那条路。** 它的 `nnz` 必须是行数的整数倍，所以每行
非零个数恒定；判据表的三个场景没有一个能整除，逐条都是两种行长混着。两批数据
覆盖的形态不同，泛化那批全过不能替代判据表。

**预热与采样次数是任务书规定的验收口径，不是骨架件的参数。** 通常写成硬性下限
（实测一例「NPU 侧每个 case 至少预热 10 次、正式采样 30 次」），低于它的数不能当
验收依据。读出来写进 `facts.json` 的 `performance.sampling`，`{warmup, samples,
source}` 三项都要，`source` 填任务书原话的出处。骨架件取不到就退 3 停下，
**不替你猜一个数**。

### 报告哪两个读数

**次数之后紧跟着的那半句同样是验收口径**，容易只读前半句就往下走。实测一例的
完整原话（sparse 三份任务书逐字相同）：

> NPU侧每个case至少预热10次、正式采样30次，报告耗时中位数及90%分位耗时
> （即约90%的正式采样耗时不高于该值）。每轮测试均须执行设备同步后计时。

拆成四条验收口径，逐条都有落点：

| 口径 | 落在哪 | 判据 |
| --- | --- | --- |
| 预热 N 次、采样 M 次 | `facts.json` 的 `performance.sampling` | 取不到退 3，不猜 |
| 报告**中位数** | 交换格式的 `under_test_us` | 倍率判据落在这个数上 |
| 报告**90%分位** | 交换格式的 `p90_us` | 与中位数并列进逐场景表 |
| 设备同步后计时 | 量测件用 NPU Event，`end.synchronize()` 之后取数 | 墙钟量的是 host 下发，小一到两个量级 |

**`under_test_us` 的口径是中位数，不是平均值。** 两者在同一批数上不可互换：
离群的首次调用会把平均拉走，而分位数正是拿来排除这种离群的。三个统计量在
真实读数上分得开——实测语料 100/100/100/500 的中位数 100、90%分位 500、
平均 200，取错哪一个都是另一个结论。

**90%分位按任务书括号里那句取**：不高于该值的采样占比达到九成的最小观测值
（`ordered[ceil(0.9 × n) - 1]`）。不做线性插值——插出来的数不是任何一次真实采样，
而任务书要的是「采样耗时不高于该值」这件事本身。口径在
`scripts/kernel_trace.py` 的 `summarize()`，骨架件各有一份同口径实现，
`tests/test_kernel_trace.py` 拿同一份语料把两处钉在一起。

**自带件汇总的那一列不是任务书口径。** 实测一例的 `kernel_total_us` 是
`总耗时 / 步数`，一个平均值，任务书要的两个统计量它一个都不是。所以
`run_kit_perf.py` 一律从 Profiler 产物自己算这两个数；只有逐次读数认不出时才
退回那一列，这时交换格式打 `stat_kind=mean`，逐场景表标成「平均值(非任务书口径)」
并在正文写出是哪几条。**两种口径不能在版面上长得一样。**

### 现场级排他锁

**性能采集期间，本现场不并发第二个 NPU 任务。** 同一张卡上重叠采样，两轮的数
互相污染，而两边的退出码都是 0。实测一例：自带件 50 条（25 分钟）与判据表 8 个
场景重叠在卡 0 上，中间还并发了十几次最小复现。

`probe_env.device_busy` 拦不住这一类。那道闸查的是设备上有没有**别人**的进程，
靠 `own_pids()` 把自己的进程树排除掉；一个现场里前后两条命令是两棵进程树，
谁也不是谁的后代。

`run_kit_perf.py` 自己持锁。另起的量测件不必改代码，用命令包住：

```bash
python3 <skill>/scripts/perf_lock.py --stage stage --who "判据表 8 场景" --devices 0 -- \
    python3 <另起件>.py --cases <用例> -o stage/perf_p_table_raw.json
```

| 判据 | 长什么样 | 去哪改 |
| --- | --- | --- |
| 有别的采集在跑 | 退 3，打印持有者的 pid、起始时刻、在跑什么、占哪几张卡 | 等它跑完，或换一个现场 |
| 持锁进程已经不在 | 打印「接手陈锁」后照常开跑 | 不用手工删锁 |
| 锁文件 | `<现场>/work/stage/perf.lock` | 进程正常或异常退出都会删掉自己那把 |

**锁只管同一个现场内部。** 跨现场共卡由 `probe_env.device_busy` 与
`free_npu.py` 现查空闲卡管，两者不重叠。

### 性能轮一律先探针

`--probe-only` 每条只调一次，出「单次耗时 / 估计总时长 / 倍率」，成本是全量的
`1/(预热+采样)`（口径 10+30 时是 2.5%）。**不设「什么算长场景」这种要猜的前置
条件**，一律先跑。

### 两批的覆盖分工

**两批都跑，不问用户跑哪几批。** 两批对应任务书两条不同的要求，少跑一批就有
一条没测到；探针已经把代价压到全量的 2.5%，先探再全量跑不需要人来批。

| 批次 | 任务书依据 | 证明什么 |
| --- | --- | --- |
| 自带件泛化集 | 「必须实现算子泛化能力，覆盖不同 shape、nnz、稀疏度、空行、长尾行分布及合法边界输入，验收阶段将采用规格内泛化数据进行测试」 | 泛化面 |
| 任务书判据表 | 「以每个 case×dtype 组合为一个性能场景，所有场景的性能倍率均须大于 0.25 倍，全部量化场景性能倍率的算术平均值须不低于 0.35 倍」 | 达标线 |

**达标线只能按判据表算，泛化集全过替代不了它。** 实测一例把这件事摆得很清楚：
泛化 50 条中位数 1.05、最低 0.30，逐条都在 0.25 之上；判据表 8 个场景里 7 个
跑不起来，总结论不通过。

用户主动把范围缩到一批时，按实际跑到的那批写结论：

| 实际跑了 | 性能结论怎么写 |
| --- | --- |
| 两批 | 按判据表裁决，泛化集的倍率分布进报告正文 |
| 只有判据表 | 按判据表裁决，报告写明泛化面未测 |
| 只有泛化集 | **不出达标结论**，报告写明判据表未跑、达标线无从判定 |

### 哪几条不跑满

跑哪几批不问，这一节也不问。探针显示某些用例明显不达标而它们还要跑很久时，
**照判据自动不跑满，不摆给用户**：跳过的是采样次数，不是验收场景——那几条照样
出「不达标」的结论，只是数来自探针而不是完整采样。验收范围没缩，没有要人决定的。

**两条同时成立才算**，缺一条都要跑满：

| 判据 | 取值 | 判不到时 |
| --- | --- | --- |
| ① 已经明显不达标 | 探针倍率 < 任务书门槛 ÷ 10 | 门槛抠不出来就不判，全部跑满 |
| ② 这些用例还要跑很久 | 它们的估计时长合计 > 10 分钟（`--ask-after-s`） | — |

**合取的理由**：只看②会把「算子本来就要跑 20 分钟但性能达标」也算进来，那是正常
验收、必须采满；只看①会为十几秒就跑完的用例省时间，省下的还不够记一笔。合取之后
剩下的才是同一件事——**结论没有悬念，而把它测精确还要付很多时间**。门槛附近的一条
都不算，那些正是要采满才判得准的。两个常数都是制定值：10 分钟取自实测锚点（正常轮
2 分 41 秒 / 失控轮 1 小时以上）。

正式轮把这几条的 id 从用例子集里排除（换目录不换文件名，仍叫 `cases.json`），
报告里它们写「不达标（未完整采样，附探针倍率）」。要全部采满就把 `--ask-after-s`
调大到超过总估时。实测一例：八个场景按口径要一小时以上，而结论在第一个场景就
定了（倍率 0.0007 对门槛 0.25，差 346 倍）。

`--budget-s` 与 `--early-stop-factor` 能减采样次数，**默认都关**，只在摸底时开：
开了之后产出打 `off_spec`，`collect_perf.py` 拒收。
| 自带件的口径不合任务书 | 同上，并把差异写进 `facts.json` 的 `kit_fixes` |

骨架里四条口径写死：预热 10、采样 30、计时范围是一次 `invoke()` 的两端、
统计量取中位数与 p90。**描述符与 workspace 建在循环外**——建在里面量到的是
建立开销，数偏大且看不出异常。**计时用 NPU Event 不用墙钟**——墙钟量的是 host
侧下发，算子还没跑完就返回，小一到两个量级。

### 算子侧失败的处置

判据表的场景跑不起来时，性能轮的产出仍然成立——「无可测耗时」是结论的一部分，
不是缺数据。按下面三步走完就出报告：

| 步 | 做什么 | 落到哪 |
| --- | --- | --- |
| 1 | 记错误码与日志核心句（如 `ACL_ERROR_RT_VECTOR_CORE_EXCEPTION (507035)` 与 `The DDR address of the MTE instruction is out of range`） | 交换格式的 `label` |
| 2 | 确认量测件的**造数自检**过了 | 骨架件 `check_sparse` 造完就核；量测件没有自检就先补上，不要改用事后复验 |
| 3 | 失败场景按 `under_test_us = inf` 记，倍率算 0 | 交换格式，`collect_perf.py` 照收 |

**造数嫌疑在造数那一刻排除，不在事后排除。** 造数是本侧写的，本侧写的东西不能
自证——但证的方式是造完当场核合法性（nnz、crow 单调、行内列严格递增无重复、
列域），不是事后拿别的构造函数去对照。放到事后，对照结果还要再解释一轮，
实测一例为此花掉 8 分钟。

自检过了还想拿自带件的构造函数复跑一次也可以，但**结果只有一种读法**：

| 自带件构造函数复跑 | 本侧造数自检 | 结论 |
| --- | --- | --- |
| 也失败 | 通过 | 算子侧失败 |
| 通过 | 通过 | **仍是算子侧失败**。两种数都合法，只是形态不同，算子在本侧这个形态上失败——而本侧的形态是任务书要求的。记「算子在任务书要求的形态上失败」，不追触发条件 |
| 任意 | 不通过 | 量测件的缺陷。改造数重跑，这一轮的结论作废 |

中间那一行是最容易读错的：自带件的用例常常落在更规整的形态上（实测一例它的
`nnz = rows × degree` 必然整除，行长恒定），判据表的 nnz 除不尽就必然是两种行长
混着。**「自带件那份通过」不等于「本侧造错了」**，两批覆盖的形态本来就不同。

#### 范围之外

**缺陷的触发条件不在性能轮里定位。** 逐个试 nnz、换 dtype、换列索引模式、
换构造函数比对、拆开数值与结构分别试——这些都属于缺陷复现，出报告之后再做，
或者连同错误码一起交给算子作者。报告需要的是「哪些场景跑不起来、报什么错」，
第一次跑完就齐了。

代价是实测过的：一轮验收里这类扫描占 6.7 分钟，且与后台的性能采样挤在同一张卡上，
两边的数互相污染。现在这条路由「现场级排他锁」拦住——采集期间再起一个 NPU 任务
会退 3。
