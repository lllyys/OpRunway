# 覆盖策略

用例设计的目标是**发现算子缺陷**，不是把通过率做到 100%。一批全绿但从没碰过
tiling 切分边界的用例，没有验收价值。

## 四条覆盖轴

社区算子任务的缺陷集中在这四处，`check_coverage.py` 也按这四根轴量覆盖率：

| 轴 | 缺陷长什么样 | 覆盖手段 |
| --- | --- | --- |
| dtype | 新增 dtype 没走通、精度选路错、量化输出容差错 | dtype 列表全覆盖，任务书点名的新增 dtype 必测 |
| shape | tiling 切分边界算错、尾块处理漏、秩边界越界 | `dim_values` 用 2^n / 2^n−1 边界对 |
| 规模 | UB 装不下时的循环切分、多核切分、尾核处理 | 按字节数分三档，配比 40/30/30 |
| attr | 负数轴没归一化、边界轴越界、空数组分支漏 | attr 值域覆盖到合法区间两端与 0 |

### dtype：任务书点名的必测

社区任务书基本都是「给已有算子扩展支持某几种 dtype」，那几种就是缺陷最可能在的地方。

| 任务书 | 必测 dtype |
| --- | --- |
| roll | `complex64`（新增），且原有 dtype 不能回归 |
| indexfill | `int16` `int8` `uint8` `fp64`（新增），原有 `fp16 fp32 int32 int64 bool bf16` 保持 |
| median | 八种全测，任务书没点名新增就没有偏重 |

**新增 dtype 不能只测一两条。** 让 YAML 的 `dtypes.values` 覆盖全集，
`dtype_numbers` 按 dtype 数摊开，ATK 会为每个 dtype 各生成这么多条。

### shape：2^n 与 2^n−1 边界对

tiling 按块切分，缺陷藏在「刚好一块」「差一个元素」「刚好多一个元素」这三处。
`dim_values` 用成对的取值把这三处夹住：

```yaml
dim_values:
  values: [1, 2, 3, 7, 8, 9, 15, 16, 17, 31, 32, 33, 63, 64, 65,
           127, 128, 129, 255, 256, 257, 511, 512, 513, 1023, 1024]
```

这份取值是通用起点。算子文档写了特殊上限（如「维度 [1,8]」）就按它裁剪，
不要超过文档上限去测——那测的是参数校验不是计算。

秩用 `dim_numbers` 覆盖文档给的区间两端：文档写 0–8 维就填 `[0, 1, 2, 3, 4, 8]`，
中间的 5、6、7 与 4 同类，不必逐个列。

### 规模档：字节数，不是元素数

同样 65536 个元素，int8 是 64 KB，fp32 是 256 KB，落在算子搬运能力的不同区间。

| 档 | 字节 | 覆盖什么 | 目标占比 |
| --- | --- | --- | --- |
| `small` | < 32 KB | 单核单次搬运装得下 | 40% |
| `medium` | 32 KB – 2 MB | UB 装不下，要循环切分 | 30% |
| `large` | ≥ 2 MB | 多核切分、尾核处理 | 30% |

`check_coverage.py` 报实际占比，偏离目标超过 12 个百分点会标出来。

#### `max_length` 是硬顶

它按**元素数**限，规模档按**字节数**分，差一个 dtype 宽度。

| `max_length` | int8 | fp16/bf16 | fp32 | 够得到 large |
| --- | --- | --- | --- | --- |
| 262144 | 256 KB | 512 KB | 1 MB | 都够不到 |
| 1048576 | 1 MB | 2 MB | 4 MB | fp16 起 |
| 2097152 | 2 MB | 4 MB | 8 MB | 全部 |

样例 YAML 取 1048576。窄 dtype（int8、uint8、bool）在这个值下摸不到 large，
要覆盖它们就翻到 2097152。

#### 用 size_distributions 控配比

ATK 原生支持按规模配比生成，**单位是 MB**（`SIZE_UNIT` 是 1 MB 的比特数，
`atk/case_generator/generator/processor.py:317`）。写在 YAML 顶层：

```yaml
size_distributions:
  - values: [[0, 0.03125]]     # small  < 32 KB
    ratio: 0.4
  - values: [[0.03125, 2]]     # medium 32 KB - 2 MB
    ratio: 0.3
  - values: [[2, 16]]          # large  >= 2 MB
    ratio: 0.3
```

它对每条用例重抽 shape 直到落进配额档，最多重抽 1000 次，填不满会在
`atk.log` 里写 `Unable to satisfy the size restriction`。

**光配它还不够**，`max_length` 与 `dim_values` 得让目标档在数学上可达：

| 卡住的地方 | 表现 | 修法 |
| --- | --- | --- |
| `max_length` 太小 | 窄 dtype 永远到不了 large（int8 的 2 MB 要 2097152 个元素） | 提到 2097152 |
| `dim_values` 最大值太小 | **秩 1 结构上到不了 large**（一个维度最多 1024 个元素 = 8 KB） | 加 4096 / 65536 / 262144 / 1048576 |

真机实测 Roll：只配 `size_distributions` 全量 large 从 1 条到 6 条，
加大 `max_length` 到 11 条，再加大 `dim_values` 到 13 条。

#### 全量不追 large 占比，性能子集才追

追全量 30% large 意味着几十条数 MB 的张量：golden 涨到几百 MB，冻结时间也上去。
而 tiling 边界缺陷在 `2^n±1` 的小张量上就能暴露，大张量对**精度**轮没有额外收益。

`gen_cases.py` 抽性能子集时**先按规模档配额再按 dtype 补齐**，全量里有十几条
large 就够填满子集的 30%。实测代价：

| 配置 | 全量 large | 子集 large | golden 冻结 | golden 体积 |
| --- | --- | --- | --- | --- |
| 不配 `size_distributions` | 1 / 180 | 1 / 50 | 19s | 31 MB |
| 三样都配上 | 13 / 180 | **13 / 50** | 20s | 99 MB |

#### 形状上限

| 项 | 上限 | 越界会怎样 |
| --- | --- | --- |
| 单维 | `2^20` | 超过就撑爆单卡显存 |
| 总元素 | `2^31` | 同上，且 golden 冻结时间不可控 |

**`extra_numbers` 生成的上边界用例不受 `max_length` 约束**，它把某一轴硬编码成
`2^31+1`。要么在约束器里把该轴夹回 `2^20`，要么填 `extra_numbers: 0` 关掉。

实测 180 条 golden 冻结 17 秒（`max_length: 1048576`、`dim_values` 到 1024），
S4 超时上限 600 秒——**生成侧全程预算 20 分钟**，超时说明用例体积失控，
调 `max_length` 不调超时。
**不要为了跑得快砍掉 `large` 档**——那等于宣布不测多核切分。

### attr：值域两端与 0

轴类参数（`dim`、`dims`）的合法区间通常是 `[-rank, rank)`，三个位置必须覆盖：

| 位置 | 为什么 |
| --- | --- |
| `-rank` | 最负的合法值，归一化要做对 |
| `-1` | 最常用的负轴写法 |
| `0` | 首轴 |
| `rank-1` | 末轴 |

`ranges.valid.values: [[-8, 8]]` 让 ATK 在区间里随机取，配合足够的 `dtype_numbers`
能覆盖到；要精确点名就在约束器里写死几组，见 plugin-authoring.md。

## 张量取值：整型要覆盖到极值

生态标准的 `[-5, 5]` 是给**浮点**写的。整型套用它，`.to(dtype)` 后候选值只有
`{-5…5}` 共 11 个，**int8 的 ±127、uint8 的 255 附近一条用例都没有**——
饱和、溢出、符号扩展这几类缺陷撞不到。

### 怎么写

`ranges.valid.values` 是**列表的列表**，ATK 在里面均匀随机挑一项。多列几段，
浮点与整型各得其所：

```yaml
ranges:
  valid:
    values: [[-5, 5], [0, 127], [-128, 127]]
```

| 段 | 给谁用 |
| --- | --- |
| `[-5, 5]` | 浮点，守生态标准 |
| `[0, 127]` | 无符号 dtype，下界必须是 0 |
| `[-128, 127]` | 有符号整型，覆盖到极值区间 |

**无符号 dtype 在场时必须有一段下界为 0。** ATK 按 dtype 值域 clamp
（`data_torch.py:302`），负值段撞上 uint 会整块压成 0。

算子文档写了定义域限制（log 的正数、除法的非零）时以文档为准，不要套这张表。

### 值域上不要做的事

| 反模式 | 后果 |
| --- | --- |
| 整型也只写 `[[-5, 5]]` | 极值区间零覆盖 |
| 只放宽值域不管无符号下界 | 负值段整块压成 0 |
| 值域放到 dtype 满量程（如 int32 的 `[-2^31, 2^31-1]`） | 算术类算子中间结果溢出，把数据设计问题伪装成实现缺陷 |
| 盯着「单张张量唯一值少」去调 | 实测唯一值 ≥ 2 时错误就 100% 被检出，调它没有收益 |

## 用例规模

`dtype_numbers` 是**每个 dtype** 生成的用例数，总量约等于：

```text
总用例数 ≈ dtype 个数 × dtype_numbers + 边界用例数
```

回填算法：

| dtype 个数 | `dtype_numbers` | 预期总量 |
| --- | --- | --- |
| ≤ 3 | 60 | 180+ |
| 4–8 | 30 | 120–240 |
| > 8 | 20 | 160+ |

**目标是 150–400 条。** 少于 100 条覆盖不住四条轴；多于 500 条精度轮拖得很久，
而增加的用例大多是同一等价类的重复。

这个条数只约束**精度全量**。另外两份由它派生，不用单独设计：

| 用途 | 条数 | 谁产出 |
| --- | --- | --- |
| 精度全量 `cases.json` | 150–400 | `gen_cases.py` |
| 性能子集 `perf/cases.json` | 50，按 dtype × 规模档分层 | `gen_cases.py` 同一步 |
| 冒烟 `smoke/cases.json` | 5，等距挑 | 跑测侧 `run_atk.py` 现挑 |

S2 的 dry-run 阶段固定填 `1`——它只验证 YAML 与插件能不能组合出合法用例，
生成几百条纯属浪费。

## 等价类剪枝

同一等价类里多测几十条不增加发现缺陷的概率，把额度让给别的轴。

| 可以合并的 | 理由 | 怎么做 |
| --- | --- | --- |
| fp16 与 bf16 | 算子内核多半统一转 fp32 计算，两者走同一条路径 | 保留两者但降低 `dtype_numbers` |
| 中间秩（5/6/7 维） | 与 4 维走同一套通用分支 | `dim_numbers` 只列两端与常用值 |
| 多个 attr 的全组合 | 3 个 attr × 4 值 = 64 组合，两两组合就够 | **不用写代码**，ATK 随机取值实测两两覆盖已有 91–98%，跑 `check_coverage.py` 确认即可 |

**不能合并的**：任务书点名的新增 dtype、文档写了特殊分支的取值（如 median 的
「dim 维长度为 1」退化场景）、约束边界本身。

## 必须单独构造的场景

有些缺陷靠随机采样撞不到，要在约束器里显式构造：

| 场景 | 何时要 | 怎么构造 |
| --- | --- | --- |
| 退化维 | 文档写「dim 维长度支持为 1」 | 约束器把某条用例的 `shape[dim]` 强制设成 1 |
| 可选指针两态 | 文档写「为 nullptr 时表示……」 | `ranges` 里放 `"default"`，两种语义都要有用例 |
| 长度联动 | 文档写「shifts 与 dims 长度必须一致」 | 约束器里对齐两个数组长度 |
| 非连续张量 | 文档的「非连续Tensor」列打勾 | ATK 的 `align_32B: true` 生成对齐与非对齐两种 |
| 大规模张量 | 性能子集报 `large` 抽不够 | **不用约束器**，YAML 配 `size_distributions`，见「规模档」 |

## 不要做的事

| 反模式 | 后果 |
| --- | --- |
| 为了提高通过率缩小 `dim_values` | 测不到 tiling 边界，验收失去意义 |
| 把跑失败的用例从 `cases.json` 里删掉 | 掩盖算子缺陷 |
| 用工程 kernel 里的 assert 反推取值范围 | 拿被测实现当判据，写错的 assert 永远测不出 |
| `dtype_numbers` 调到 5000 硬凑覆盖 | 生成几小时，绝大多数是重复等价类 |
| 只测任务书新增的 dtype，不测原有的 | 漏掉回归，而任务书明确要求「保持原有功能不变」 |
