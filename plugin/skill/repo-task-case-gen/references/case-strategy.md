# 覆盖策略

用例设计的目标是**发现算子缺陷**，不是把通过率做到 100%。一批全绿但从没碰过
tiling 切分边界的用例，没有验收价值。

## 四条覆盖轴

社区算子任务的缺陷集中在这四处，`check_coverage.py` 也按这四根轴量覆盖率：

| 轴 | 缺陷长什么样 | 覆盖手段 |
| --- | --- | --- |
| dtype | 新增 dtype 没走通、精度选路错、量化输出容差错 | dtype 列表全覆盖，任务书点名的新增 dtype 必测 |
| shape | tiling 切分边界算错、尾块处理漏、秩边界越界 | `dim_values` 用 2^n / 2^n−1 边界对 |
| 规模 | UB 装不下时的循环切分、多核切分、尾核处理 | 按字节数分三档，配比 40/30/30 |
| attr | 负数轴没归一化、边界轴越界、空数组分支漏 | attr 值域覆盖到合法区间两端与 0 |

### dtype：任务书点名的必测

社区任务书基本都是「给已有算子扩展支持某几种 dtype」，那几种就是缺陷最可能在的地方。

| 任务书 | 必测 dtype |
| --- | --- |
| roll | `complex64`（新增），且原有 dtype 不能回归 |
| indexfill | `int16` `int8` `uint8` `fp64`（新增），原有 `fp16 fp32 int32 int64 bool bf16` 保持 |
| median | 八种全测，任务书没点名新增就没有偏重 |

**新增 dtype 不能只测一两条。** 让 YAML 的 `dtypes.values` 覆盖全集，
`dtype_numbers` 按 dtype 数摊开，ATK 会为每个 dtype 各生成这么多条。

#### 给新增 dtype 加权

`dtype_numbers` 是**一个整数**，对每个 dtype 一视同仁（`design_config.py:477`、
`base_generator.py:198`），YAML 里没有按 dtype 给不同条数的入口。所以新增 dtype
永远只占 1/N——四种 dtype 就是 25%，而缺陷几乎全在那一种上。

加权靠**跑两轮 `atk case` 再合并**，`atk case` 的 `-df/--dtype_filter` 是滤除列表。
下面两条是 `gen_cases.py` 自动拼出来的样子，**只在手上要单独验证某一轮时才自己敲**：

```bash
atk case -f <op>.yaml -df fp32,fp16,bf16 -dt 60   # 只出 uint8，60 条
atk case -f <op>.yaml -df uint8          -dt 20   # 只出其余三种，各 20 条
```

两组都是 ATK 自己按规模档与 shape 边界正常抽的，不是从一堆里挑剩的，也没有生成了
又扔掉的浪费。**这件事 `gen_cases.py` 自动做**：`facts.json` 填了 `focus_dtypes`
就拆两轮、合并、重编 id，让 focus 那几种占一半；没填就一轮跑完。手上要单独验证时
才用上面的命令。

合并后 id 必须重编（两轮都从 0 起），`gen_cases.py` 已经做了。golden 是合并之后才冻
的，所以重编是安全的。

#### 规模档按字节算，重点 dtype 尤其要当心

`large` 的门槛是 **2MB 字节数**，不是元素数。同一个形状对 fp32 是 4MB（够 large），
对 uint8 只有 1MB（落进 medium）。约束器里写死一组形状去凑规模档时，浮点够了，
新增的窄 dtype 会整档落空：浮点够 large 的形状，uint8 只有四分之一。
那一档一旦是 0 条，性能轮里这个 dtype 的多核切分路径一条都测不到。

**显式构造规模档时按当前用例的 dtype 现算元素数门槛**，不要写死形状：

```python
width = {"fp32": 4, "fp16": 2, "bf16": 2, "uint8": 1}[x.dtype]
need = LARGE_BYTES // width          # 要多少个元素才够 large
```

`check_coverage.py` 会对 `focus_dtypes` 逐个查三档齐不齐，缺档是返工判据。

### shape：2^n 与 2^n−1 边界对

tiling 按块切分，缺陷藏在「刚好一块」「差一个元素」「刚好多一个元素」这三处。
`dim_values` 用成对的取值把这三处夹住：

**具体取值在 `assets/skeleton.yaml`，本文不重复。** 那份是通用起点，算子文档写了
特殊上限（如「维度 [1,8]」）就按它裁剪，不要超过文档上限去测——那测的是参数校验
不是计算。

秩用 `dim_numbers` 覆盖文档给的区间，但**只抽到 4 为止**，中间的 5、6、7 与 4 同类，
不必逐个列；文档上界超过 4 时，高秩那几档改成显式构造，见下。

#### 高秩不靠抽样

ATK 抽 shape 是拒绝采样：从 `dim_values` 里抽 rank 个数相乘，超出元素预算就整条
丢掉重抽（`parameter_tensor.py:158`，ATK 自己在那行上面注了「max_number_ele较小时
可能无限循环」，并加了 300 秒守卫）。**接受率随秩指数下降**，实测（12 万次模拟，
`skeleton.yaml` 那份 `dim_values`，满预算 fp32 = 2^20 元素）：

| rank | 1 | 2 | 3 | 4 | 8 |
| --- | --- | --- | --- | --- | --- |
| 一次抽中的概率 | 96.9% | 78.0% | 41.6% | 13.7% | **0.01%** |
| 平均重抽次数 | 1 | 1 | 2 | 7 | **12000** |

后果分两种，**都不能接受**：

- 单张量算子：抽得出来，但每条 rank 8 要空转上万次，且抽中的只可能是各轴都极小的
  组合，形状分布被悄悄扭曲
- 张量列表算子（`type: tensors`）：ATK 在列表总量超预算时会把元素预算减半重来
  （`parameter_tensors.py:73-81`），预算越砍越小，接受率直接归零，打满 300 秒守卫

**在 `dim_values` 里塞一个 `0` 能让它跑起来，但那是后门不是解药**——numel 为 0
无条件通过，于是高秩那一档全部塌成空张量。真机上出现过 rank 8 的 186 个张量
100% 含 0 轴、一个数都没算，而覆盖报告显示 rank 8 有 186 条，看起来很好。

**为什么不在 YAML 里按秩分池。** 最自然的想法是「低秩用默认 `dim_values`，高秩
用一份小值池」，但 ATK 表达不了：`dim_values` 写成 list 时是按**轴的位置**取的
（`parameter_tensor.py:106-108`，`dim_values[i]` 对应第 i 根轴），不是按秩。
按轴分池也解不开——rank 1 只用第 0 根轴，要上 large 档它必须能抽到 2^20，
而 rank 8 也从第 0 根轴开始抽。两个钩子（`after_input_config` /
`after_case_config`）又都在形状生成之后才跑（`base_generator.py:178-190`），
插件拦不住那轮采样。

所以：**`dim_numbers` 只写 ≤4，高秩在约束器里显式写形状。**
轴长不用拍脑袋：**每根轴的上限就是元素预算开 rank 次方**，这样乘积必定在预算内，
一次都不用重抽。`assets/high_rank_constraint.py` 按这个式子现算轴长池：

| 目标秩 | 每轴上限（预算取 `max_length/8`，最窄 dtype 的最坏情况） | 轴长池 |
| --- | ---: | --- |
| 5 | 13.9 | 1, 2, 3, 7, 8, 9 |
| 6 | 9.0 | 1, 2, 3, 7, 8 |
| 7 | 6.6 | 1, 2, 3 |
| 8 | 5.2 | 1, 2, 3 |

`assets/` 里的约束器示例带了这段，注释标了「文档 rank 上界 >4 时打开」。
`check_coverage.py` 会拿 `facts.json` 的 `shape.rank` 对账，漏了哪几档它会点名。

### 规模档

判据与档位表在 [size-bands.md](size-bands.md)——**字节数不是元素数**，
档位阈值只在那一份里定，别处重算就是第二套阈值。

### attr：值域两端与 0

轴类参数（`dim`、`dims`）的合法区间通常是 `[-rank, rank)`，三个位置必须覆盖：

| 位置 | 为什么 |
| --- | --- |
| `-rank` | 最负的合法值，归一化要做对 |
| `-1` | 最常用的负轴写法 |
| `0` | 首轴 |
| `rank-1` | 末轴 |

`ranges.valid.values: [[-8, 8]]` 让 ATK 在区间里随机取，配合足够的 `dtype_numbers`
能覆盖到；要精确点名就在约束器里写死几组，见 plugin-authoring.md。

## 张量取值：整型要覆盖到极值

生态标准的 `[-5, 5]` 是给**浮点**写的。整型套用它，`.to(dtype)` 后候选值只有
`{-5…5}` 共 11 个，**int8 的 ±127、uint8 的 255 附近一条用例都没有**——
饱和、溢出、符号扩展这几类缺陷撞不到。

### 写法

`ranges.valid.values` 是**列表的列表**，ATK 在里面均匀随机挑一项。多列几段，
浮点与整型各得其所：

```yaml
ranges:
  valid:
    values: [[-5, 5], [0, 127], [-128, 127]]
```

| 段 | 给谁用 |
| --- | --- |
| `[-5, 5]` | 浮点，守生态标准 |
| `[0, 127]` | 无符号 dtype，下界必须是 0 |
| `[-128, 127]` | 有符号整型，覆盖到极值区间 |

**无符号 dtype 在场时必须有一段下界为 0。** ATK 按 dtype 值域 clamp
（`data_torch.py:302`），负值段撞上 uint 会整块压成 0。

算子文档写了定义域限制（log 的正数、除法的非零）时以文档为准，不要套这张表。

### 值域上不要做的事

| 反模式 | 后果 |
| --- | --- |
| 整型也只写 `[[-5, 5]]` | 极值区间零覆盖 |
| 只放宽值域不管无符号下界 | 负值段整块压成 0 |
| 值域放到 dtype 满量程（如 int32 的 `[-2^31, 2^31-1]`） | 算术类算子中间结果溢出，把数据设计问题伪装成实现缺陷 |
| 盯着「单张张量唯一值少」去调 | 实测唯一值 ≥ 2 时错误就 100% 被检出，调它没有收益 |

## 用例规模

`dtype_numbers` 是**每个 dtype** 生成的用例数，总量约等于：

```text
总用例数 ≈ dtype 个数 × dtype_numbers + 边界用例数
```

回填算法：

| dtype 个数 | `dtype_numbers` | 预期总量 |
| --- | --- | --- |
| ≤ 3 | 60 | 180+ |
| 4–8 | 30 | 120–240 |
| > 8 | 20 | 160+ |

**算出来低于 150 就往上调到 150 以上**：dtype 只有 2 种时按表填 60 才 120 条，
4 种填 30 也只有 120 条。表给的是档位。**100 是脚本的硬闸，150 是设计目标**，
过了闸不等于够用。

**填了 `focus_dtypes` 也照这张表填，不要自己乘 2。** 这个数始终是「假如一轮跑完，
每个 dtype 几条」，拆轮次是 `gen_cases.py` 在这个数之上自己算的：

```text
总量   = dtype_numbers × dtype 总数
focus 轮 -dt = 总量 × 0.5 ÷ focus 个数
其余 轮 -dt = 总量 × 0.5 ÷ 其余个数
```

四种 dtype、`focus_dtypes: ["uint8"]`、`dtype_numbers: 30` 就是总量 120，
拆成 `-dt 60`（uint8）与 `-dt 20`（其余三种各 20）——正是上面那两条手工命令。
**回填时不用去看脚本，也不用为拆轮次改任何别的字段。**

**目标是 150–400 条。** 少于 100 条覆盖不住四条轴；多于 500 条精度轮拖得很久，
而增加的用例大多是同一等价类的重复。

**上限只提示不拦**，下限是硬闸：少于 100 条是覆盖不住四条轴，条数多不构成同类
问题——覆盖面由 YAML 设计决定，多出来的用例落在已有等价类里，浪费的是时间不是
正确性。用户点名要每 dtype 几条时用 `--dtype-numbers`，边界见 SKILL.md 的 S3；
**用户没点名就照上面这张表回填进 YAML**，`dtype_numbers` 跟着用例包交到跑测侧，
命令行参数不会。

这个条数只约束**精度全量**。另外两份由它派生，不用单独设计：

| 用途 | 条数 | 谁产出 |
| --- | --- | --- |
| 精度全量 `cases.json` | 150–400 | `gen_cases.py` |
| 性能子集 `perf/cases.json` | 50，按 dtype × 规模档分层；`cross_dtype` 是 50 **对**共 100 条 | `gen_cases.py` 同一步 |
| 子集清单 `perf/manifest.json` | 逐条规模档；`cross_dtype` 还带配对表 | `gen_cases.py` 同一步，落盘用 |
| 冒烟 `smoke/cases.json` | 5，等距挑 | 跑测侧 `run_atk.py` 现挑 |

S2 的 dry-run 阶段固定填 `1`——它只验证 YAML 与插件能不能组合出合法用例，
生成几百条纯属浪费。

## 等价类剪枝

同一等价类里多测几十条不增加发现缺陷的概率，把额度让给别的轴。

| 可以合并的 | 理由 | 怎么做 |
| --- | --- | --- |
| fp16 与 bf16 | 算子内核多半统一转 fp32 计算，两者走同一条路径 | 保留两者但降低 `dtype_numbers` |
| 中间秩（5/6/7 维） | 与 4 维走同一套通用分支 | 抽样只到 4，上界那一档显式构造 |
| 多个 attr 的全组合 | 3 个 attr × 4 值 = 64 组合，两两组合就够 | **不用写代码**，ATK 随机取值实测能把两两组合铺满，跑 `check_coverage.py` 看「组合空缺」确认即可 |

**不能合并的**：任务书点名的新增 dtype、文档写了特殊分支的取值（如 median 的
「dim 维长度为 1」退化场景）、约束边界本身。

## 必须单独构造的场景

有些缺陷靠随机采样撞不到，要在约束器里显式构造：

| 场景 | 何时要 | 怎么构造 |
| --- | --- | --- |
| 退化维 | 文档写「dim 维长度支持为 1」 | 约束器把某条用例的 `shape[dim]` 强制设成 1 |
| 高秩（≥5） | `facts.json` 的 `shape.rank` 上界 >4 | 约束器按序号改写整个 shape，见「高秩不靠抽样」 |
| 可选指针两态 | 文档写「为 nullptr 时表示……」 | `ranges` 里放 `"default"`，两种语义都要有用例 |
| 长度联动 | 文档写「shifts 与 dims 长度必须一致」 | 约束器里对齐两个数组长度 |
| 非连续张量 | 文档的「非连续Tensor」列打勾 | **生成侧什么都不做**，`facts.json` 的 `non_contiguous.required` 填 `true`，跑测侧加 `--slice_input non_contiguous`，见下 |
| 大规模张量 | 性能子集报 `large` 抽不够 | **不用约束器**，YAML 配 `size_distributions`，见「规模档」 |

### 非连续张量在跑测期切，不在生成期造

ATK 的开关是执行参数不是 YAML 字段（`atk/bin/task.py:118-135`）：

```bash
atk ... --slice_input non_contiguous --slice_input_ratio 0.3
```

做法是**开 2 倍存储、取步长 2 的视图、再把原张量拷进去**
（`atk/configs/dataset_config.py:296-313`）——**逻辑值一位不变，只有 stride 变了**。
所以冻好的 golden 依然有效，打开这个开关不用重冻。

`align_32B` 与它无关，那个控的是总字节数是不是 32 的倍数。

## 覆盖判据解读

`check_coverage.py` 是纯度量，两张表给自己对判据用，不转贴给用户。SKILL.md 的 S3 列了
四条返工判据，这里说清楚**哪些看着像问题但不是**。

| 观察到 | 是不是判据 | 为什么 |
| --- | --- | --- |
| 结构上就是单值的轴（量具照样报「轴退化」） | **不是** | 文档写死长度的数组参数（`outputSize` 的 size 恒为 1）、文档写死秩的算子，只有一个取值是对的。秩那一根按 `facts.json` 的 `shape.rank` 自动豁免，值域那几根量具已经单列成「值域」行，别的轴自己判一次 |
| 「值域」行说只有一段 | **不是** | 那是 YAML 的 `ranges.valid.values` 只写了一段的直接结果，不是覆盖缺口。任务书点名要测 NaN/inf/边界值时才是——那时按本文「必须单独构造的场景」加段 |
| 组合空缺 N 处 | **不是** | 里面混着结构上不可达的组合：秩 0 只能是 `scalar`、两个等长列表只有对角线可达。填不满是常态 |
| 全量里 `large` 占比低 | **不是** | 抽子集时先按规模档配额，全量十几条 `large` 就够填满子集的 30%；追全量 30% 只会让 golden 涨到几百 MB |
| 性能子集报「抽不够」 | **是** | 见本文「规模档」 |

「重点 dtype 缺规模档」那条只在 `facts.json` 填了 `focus_dtypes` 时出现，拦的是「新增
dtype 只测了小张量」：`large` 的门槛按**字节**算，同一个 shape 对 fp32 够 large，对
uint8 只有四分之一，写死形状必然漏掉。修法见本文「规模档按字节算」。

不构成返工的观察在交付简表的「遗留」行陈述一句即可，不要拿去问用户要不要补。

## 不要做的事

| 反模式 | 后果 |
| --- | --- |
| 为了提高通过率缩小 `dim_values` | 测不到 tiling 边界，验收失去意义 |
| 把跑失败的用例从 `cases.json` 里删掉 | 掩盖算子缺陷 |
| 用工程 kernel 里的 assert 反推取值范围 | 拿被测实现当判据，写错的 assert 永远测不出 |
| `dtype_numbers` 调到 5000 硬凑覆盖 | 生成几小时，绝大多数是重复等价类 |
| 只测任务书新增的 dtype，不测原有的 | 漏掉回归，而任务书明确要求「保持原有功能不变」 |


## 张量声明不能跳过

ATK 分三层：用例声明张量的 shape/dtype、`DATATYPE_REGISTRY` 定这个 dtype 的
数值怎么造、`api_type` 定怎么把算子调起来。**中间那层是正式扩展点**,
自带的实现里就有造稀疏矩阵的（`data_coo.py` 的 `coo`，阈值 0.7 置零）
和造结构化矩阵的（`matrix_profiles.py` 的 `well_conditioned_matrix`、
`controlled_rank_deficient_matrix`)。

所以**输入有强结构约束时不要把张量从用例里拿掉**——那正是这一层存在的理由。
见过的反例是把一条用例编码成若干标量当"配方"，在执行器里自己造张量。
它跑得起来，ATK 不报错，代价是这五项静默失效：

| 跳过张量声明，失去什么 | 后果 |
| --- | --- |
| `--input_data` 冻结输入字节 | 冻下来的是那几个标量。**两侧是不是同一批输入没有机制保证**，只剩「seed 相同」这个约定 |
| `--slice_input non_contiguous` | 切的是 ATK 造的张量。**用例声明了真张量就切得到**，入参全是 attr、张量由执行器现造时才切不到（那一档 `non_contiguous.required` 填 `false`，见 interface-facts.md「用例形态」） |
| 报表按 dtype 分组 | 取不到 dtype，全部用例塌成一行，整类失败看不出来 |
| 规模档按字节分 | 取不到字节数，`size_band` 全落 `unknown` |
| `boundary` 的五个 `has_*` 开关 | **只有 tensor 类型能设**，别的类型设了直接报错。跳过张量声明等于把边界值机制整个关掉 |

最后一条的代价可以量化：实测见过一份自带件的造数走 `torch.randn`,
**产不出 ±0、INF、NAN**，而它自己的任务书要求 10% 覆盖这些。
两件事是因果——绕开了 ATK 的边界值机制，就得自己实现，自己实现就漏了。

结构约束落在哪一层，按这张表挑：

| 约束 | 落点 |
| --- | --- |
| shape、dtype、取值范围、边界值 | YAML 的 `inputs`，不用写代码 |
| 参数之间要自洽（A 的长度等于 B 的秩） | 约束器 `after_case_config`，改的是用例描述 |
| **张量数值的分布或结构**（稀疏度、pattern、条件数） | `DATATYPE_REGISTRY` 注册一个数据类型，照 `data_coo.py` 改 |
| 调用形态特殊（原地输出、参数顺序不对应） | 执行器 `api_type` |
