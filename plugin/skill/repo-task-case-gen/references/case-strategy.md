# 覆盖策略

用例设计的目标是**发现算子缺陷**，不是把通过率做到 100%。一批全绿但从没碰过
tiling 切分边界的用例，没有验收价值。

## 三条覆盖轴

社区算子任务的缺陷集中在三处，覆盖面按这三条轴组织：

| 轴 | 缺陷长什么样 | 覆盖手段 |
| --- | --- | --- |
| dtype | 新增 dtype 没走通、精度选路错、量化输出容差错 | dtype 列表全覆盖，任务书点名的新增 dtype 必测 |
| shape | tiling 切分边界算错、尾块处理漏、秩边界越界 | `dim_values` 用 2^n / 2^n−1 边界对 |
| attr | 负数轴没归一化、边界轴越界、空数组分支漏 | attr 值域覆盖到合法区间两端与 0 |

### dtype：任务书点名的必测

社区任务书基本都是「给已有算子扩展支持某几种 dtype」，那几种就是缺陷最可能在的地方。

| 任务书 | 必测 dtype |
| --- | --- |
| roll | `complex64`（新增），且原有 dtype 不能回归 |
| indexfill | `int16` `int8` `uint8` `fp64`（新增），原有 `fp16 fp32 int32 int64 bool bf16` 保持 |
| median | 八种全测，任务书没点名新增就没有偏重 |

**新增 dtype 不能只测一两条。** 让 YAML 的 `dtypes.values` 覆盖全集，
`dtype_numbers` 按 dtype 数摊开，ATK 会为每个 dtype 各生成这么多条。

### shape：2^n 与 2^n−1 边界对

tiling 按块切分，缺陷藏在「刚好一块」「差一个元素」「刚好多一个元素」这三处。
`dim_values` 用成对的取值把这三处夹住：

```yaml
dim_values:
  values: [1, 2, 3, 7, 8, 9, 15, 16, 17, 31, 32, 33, 63, 64, 65,
           127, 128, 129, 255, 256, 257, 511, 512, 513, 1023, 1024]
```

这份取值是通用起点。算子文档写了特殊上限（如「维度 [1,8]」）就按它裁剪，
不要超过文档上限去测——那测的是参数校验不是计算。

秩用 `dim_numbers` 覆盖文档给的区间两端：文档写 0–8 维就填 `[0, 1, 2, 3, 4, 8]`，
中间的 5、6、7 与 4 同类，不必逐个列。

### attr：值域两端与 0

轴类参数（`dim`、`dims`）的合法区间通常是 `[-rank, rank)`，三个位置必须覆盖：

| 位置 | 为什么 |
| --- | --- |
| `-rank` | 最负的合法值，归一化要做对 |
| `-1` | 最常用的负轴写法 |
| `0` | 首轴 |
| `rank-1` | 末轴 |

`ranges.valid.values: [[-8, 8]]` 让 ATK 在区间里随机取，配合足够的 `dtype_numbers`
能覆盖到；要精确点名就在约束器里写死几组，见 plugin-authoring.md。

## 用例规模

`dtype_numbers` 是**每个 dtype** 生成的用例数，总量约等于：

```text
总用例数 ≈ dtype 个数 × dtype_numbers + 边界用例数
```

回填算法：

| dtype 个数 | `dtype_numbers` | 预期总量 |
| --- | --- | --- |
| ≤ 3 | 60 | 180+ |
| 4–8 | 30 | 120–240 |
| > 8 | 20 | 160+ |

**目标是 150–400 条。** 少于 100 条覆盖不住三条轴；多于 500 条冒烟和全量都拖得很久，
而增加的用例大多是同一等价类的重复。

S2 的 dry-run 阶段固定填 `1`——它只验证 YAML 与插件能不能组合出合法用例，
生成几百条纯属浪费。

## 等价类剪枝

同一等价类里多测几十条不增加发现缺陷的概率，把额度让给别的轴。

| 可以合并的 | 理由 | 怎么做 |
| --- | --- | --- |
| fp16 与 bf16 | 算子内核多半统一转 fp32 计算，两者走同一条路径 | 保留两者但降低 `dtype_numbers` |
| 中间秩（5/6/7 维） | 与 4 维走同一套通用分支 | `dim_numbers` 只列两端与常用值 |
| 多个 attr 的全组合 | 3 个 attr × 4 值 = 64 组合，实际两两组合就够 | 约束器里做 pairwise 采样 |

**不能合并的**：任务书点名的新增 dtype、文档写了特殊分支的取值（如 median 的
「dim 维长度为 1」退化场景）、约束边界本身。

## 必须单独构造的场景

有些缺陷靠随机采样撞不到，要在约束器里显式构造：

| 场景 | 何时要 | 怎么构造 |
| --- | --- | --- |
| 退化维 | 文档写「dim 维长度支持为 1」 | 约束器把某条用例的 `shape[dim]` 强制设成 1 |
| 可选指针两态 | 文档写「为 nullptr 时表示……」 | `ranges` 里放 `"default"`，两种语义都要有用例 |
| 长度联动 | 文档写「shifts 与 dims 长度必须一致」 | 约束器里对齐两个数组长度 |
| 非连续张量 | 文档的「非连续Tensor」列打勾 | ATK 的 `align_32B: true` 生成对齐与非对齐两种 |

## 不要做的事

| 反模式 | 后果 |
| --- | --- |
| 为了提高通过率缩小 `dim_values` | 测不到 tiling 边界，验收失去意义 |
| 把跑失败的用例从 `cases.json` 里删掉 | 掩盖算子缺陷 |
| 用工程 kernel 里的 assert 反推取值范围 | 拿被测实现当判据，写错的 assert 永远测不出 |
| `dtype_numbers` 调到 5000 硬凑覆盖 | 生成几小时，绝大多数是重复等价类 |
| 只测任务书新增的 dtype，不测原有的 | 漏掉回归，而任务书明确要求「保持原有功能不变」 |
