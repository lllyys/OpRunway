# 巡检失败与结论存疑

只在 `page_inspect.py` 退出码为 2、或报告结论明显不对时读这一份。

## 退出码 2 的五种原因

脚本停下时打印的第一行以 `阻塞·` 开头，对应下表：

| 打印 | 原因 | 处置 |
| --- | --- | --- |
| `阻塞·缺少 httpx` / `缺少 playwright` | 依赖没装 | `pip install httpx playwright`。**不要跑 `playwright install`**，脚本用 `channel="chrome"` 复用本机 Chrome |
| `阻塞·入口页 X 返回 4xx/5xx` | 站点在维护或改了路径 | 手动打开那个 URL 确认。站点确实挂了就等，不要改脚本绕过 |
| `阻塞·入口页 X 不可达` | 本机网络或 DNS | 先 `curl -I https://www.hiascend.com/cann` 确认 |
| `阻塞·X 取链塌成外壳` | 该页渲染没跟上，只拿到页头页脚，且静置重取仍失败 | 直接重跑一次。连续两轮同一页塌陷见下一节 |
| `阻塞·N 页去重后正文链接为 0` | 站点结构改版 | 见「站点改版」一节 |

## 取链塌成外壳：某页只拿到 40 条上下

`run.log` 里出现 `S2 X 取到 40 个 <a>`，随后脚本以退出码 2 停在
`阻塞·X 取链塌成外壳`。40 条是服务端直出的页头页脚，正文由 JS 渲染，
此刻一条正文链接都没测到，所以本轮不出报告。

脚本已经自己重试过一次：塌陷页会静置 `SHELL_RETRY_WAIT` 秒后串行重取，
重取成功就照常出报告，只有重取仍塌才停机。所以看到这条，说明那一页连试两次都没渲染出来。

**第一处置仍是重跑整轮，不是改脚本。** 取链是「链接数连续 3 次不变才算取全」，
上限 `LINKS_STABLE_TIMEOUT_MS`。

**塌陷概率随一轮内的持续负载升高。** 2026-08-29 实测：19 页 4 并发跑到第 2 分钟时
有 3 页塌成 37 条，而同样这 3 页单独重取全部正常（70 / 119 / 79 条），
3 页 4 并发也不塌。所以连续塌陷时先降 `PAGE_WORKERS`，别动超时。

连续两轮同一页塌陷再往下查，按顺序：

1. **先降 `PAGE_WORKERS`（默认 3）。** 这是唯一实测有效的旋钮
2. **不要调大 `NAV_TIMEOUT_MS` / `SETTLE_TIMEOUT_MS`。** 实测调到 90000 / 45000 后
   链接数仍是 40，只把失败路径从 3m44s 拖到 6m59s。失败不是时间不够
3. **确认 DOMContentLoaded 到底有没有触发**。脚本用 `wait_until="domcontentloaded"`，
   若 `<head>` 里某个第三方阻塞脚本吊住，这个事件永远不来，页面就停在外壳。
   挂 `pg.on("request")` / `pg.on("requestfinished")` 记录挂起清单，看超时那一刻
   哪些请求没回来——**这一条尚未在真实塌陷现场验证过，是待测项不是结论**
4. 排除以上三条后，才考虑站点改版，见下一节

## 报告里链接数远超预期或规则命中暴涨

扩到 19 个页签后正文链接约 336 条。若某轮骤增到上千条，多半是某个页签塌成外壳
却没被拦住，导致「各页共有的页头页脚」交集缩小、页头页脚被算进正文。
对比 `run.log` 里各页的 `<a>` 数，明显偏低的那页就是元凶。

`mailto:` / `tel:` / `javascript:` / 纯锚点已经被 `is_probeable()` 排除在判定之外——
它们会让 httpx 报 `UnsupportedProtocol`，被 A1 误判成链接失效。
报告检查域表的「不可探测」列就是这些。**再出现 `UnsupportedProtocol` 命中，
先看是不是又冒出一种新协议前缀，而不是去改 A1。**

## 站点改版：正文链接为 0 或骤降

脚本靠「各页共有的链接就是页头页脚」来分离正文。2026-08-29 全量实测：
19 页共有 54 条，正文 336 条。如果正文链接数掉到两位数以下，多半是这三种情况之一：

1. **页头页脚变了**，导致共有集合把正文也吞了。对比 `run.log` 里三页各自的 `<a>` 数，
   若某页总数正常而正文为 0，就是这种
2. **懒加载没触发完**。取链已改成等链接数稳定，上限 `LINKS_STABLE_TIMEOUT_MS`，
   页面特别长时把它调大再跑
3. **页面改成需要登录才展示内容**。手动打开确认

三种都不该靠调阈值绕过——先确认站点真实状态，再决定改常量还是改流程。

## 结论可疑时的自查顺序

报告里的命中看着不对，按这个顺序查，不要直接改判据：

1. 打开 `last-run.json`，找到那条的 `实测` 字段——它记了当时测到的原始事实
2. 手动打开目标 URL，用**浏览器**而不是 curl。站外站点对命令行客户端会返 403/418/429，
   脚本对这三个码会自动用浏览器复核，但你手工验证时容易踩这个坑
3. 确认是判据问题再改脚本顶部常量。**改判定逻辑前先想清楚会不会引入假阳性**

## 已知会误导人的两个坑

**别用正文字数判空壳。** 实测站内失效页的空壳正文 330 字，而 `/cann/contrib-guide`
是一张图为主的正常页、正文 352 字，两者字数几乎相同。任何字数阈值都会把图文页
判成失效。判空壳只认失败标记字符串。

**别用固定 sleep 等渲染。** 站内 CSR 页在渲染完成前的空壳正文约 285 字，
等待不足时真页和假页拿到的正文完全一样，会同时误报。脚本改用「正文长度连续三次
不变」判渲染完成，不要换回固定秒数。
